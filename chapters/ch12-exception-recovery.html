第三部分 · 容错与扩展

第12章 异常处理与恢复 Exception Handling and Recovery

把智能体的执行设计为可重试、可熔断、可降级、可从检查点恢复的状态机，并用幂等与补偿保证"失败后重走"不会造成二次伤害。

一句话定义：为智能体的每一步预先设计失败路径——瞬时错误用退避重试、持续错误用熔断降级、长流程用检查点续跑、副作用用幂等与补偿兜底——使"失败"成为可恢复的常态而非灾难。 解决什么问题：智能体执行链路上模型、工具、编排、语义四层都会失败，默认行为（崩溃或静默吞掉）都不可接受 ｜ 适用场景：长时自治任务、有副作用的操作链、调用不稳定外部依赖的工作流 ｜ 核心机制：错误分类 → 重试/熔断/降级 → 检查点恢复 → 幂等与补偿 ｜ 代价：代码复杂度与状态管理成本上升；重试与恢复本身消耗资源；恢复语义（恰好一次的幻觉）需要小心设计。

本章速读　智能体的模型、工具、编排、语义四层都会失败，崩溃与静默吞错都不可接受。解法：先分类再行动——瞬时错误退避重试（必须加抖动），持续错误熔断＋降级，长流程检查点续跑，写操作幂等键＋SAGA 补偿。三步：①给每类错误映射策略；②整条链只在一层重试；③检查点存"结果＋完整上下文"。何时别用：纯内存、可整体重算的短任务——直接失败重抛更简单，容错复杂度须与任务价值匹配。

12.1 模式概述

12.1.1 问题背景：为什么需要这个模式

一个生产级智能体的故障面远大于传统程序。传统程序只担心自己的代码和依赖，而智能体叠加了四层不确定性：模型层（限流、超时、内容策略拒绝，以及输出本身的随机性——同样的输入两次调用结果不同）、工具层（网络抖动、权限过期、返回格式突变、部分成功）、编排层（死循环、状态丢失、并发写冲突）、语义层（调用"成功"返回 200，内容却是错的）。更麻烦的是 LLM 应用的依赖质量普遍低于传统分布式系统：重试一个 HTTP 接口，第二次大概率还是同样的错误；重试一次模型调用，第二次可能就对了——非确定性让"重试"这个老工具的适用边界发生了位移。

默认的两个行为都不可接受。直接崩溃：一个跑了四十步的自治任务在第三十九步崩掉，全部进度作废。静默吞掉（catch 后继续）：错误状态渗入后续步骤，最终产出一个"看似完整实则错误"的结果，比崩溃更难排查。异常处理与恢复模式的立场是：失败是智能体运行的常态输入，必须像设计正常路径一样显式设计失败路径——每一步都要回答四个问题：失败了重试几次？重试无果怎么办（降级到什么）？崩掉之后从哪续跑？如果这一步有副作用，重走一遍会不会造成二次伤害？

12.1.2 核心机制：它如何工作

机制由四层组成，逐层递进。第一层：错误分类。拿到异常先分类再行动——瞬时错误（限流 429、超时、网络抖动）可重试；永久错误（参数非法 400、权限不足 403）重试无意义，直接走失败路径；语义错误（返回了但错了）不能原样重试，要修改输入或校验后再试。第二层：重试与退避。可重试错误用指数退避加抖动（full jitter），配合重试次数上限与总预算；只重试幂等操作。第三层：熔断与降级。某依赖连续失败超过阈值就熔断——在一段时间内直接快速失败，不再发起真实调用，让依赖喘息、让自己止损；同时提供降级路径（备用模型、缓存、静态结果），保证主链路不可用时业务仍能以低质量继续。第四层：检查点与恢复。把工作流状态（已完成步骤与结果、当前上下文）持久化，进程崩溃后从最近检查点恢复，已完成的步骤凭幂等记录跳过而不是重做；对有副作用的写操作，用幂等键去重，对无法重做的复合操作用 SAGA 式补偿（逆序执行补偿动作回滚）。四层机制的协同关系如下图所示。

12.1.3 与相邻模式的关系与组合

与目标监控（第 11 章）互为攻守：监控判定"预算耗尽、连续失败"后把控制权交给恢复机制；恢复机制的重试与降级动作又必须被监控记录，否则降级会悄悄变成常态。与工具调用/MCP的关系在边界上：超时、重试、熔断应实现于工具调用包装层（客户端一侧），让业务编排代码保持干净。与规划/路由的关系是恢复的两种出口：可修复的失败（瞬时错误）就地恢复，不可修复的失败改道（换工具、换模型、换路径）。与人机协同的关系是最后一道闸：所有自动恢复手段穷尽后，正确动作是把现场打包升级给人，而不是假装问题不存在。

12.2 源起：它从哪里来

本章的每个构件都不是智能体时代的新发明，而是三个传统的接力。语言传统解决"如何表达失败"：PL/I 的 ON 条件让异常首次成为语言机制。分布式传统解决"跨系统操作如何干净退回"：1987 年的 SAGA 把长事务拆成子事务链、失败时逆序补偿。在线服务传统解决"真实故障率下如何活下来"：Nygard 2007 年的《Release It!》系统化熔断与舱壁，Brooker 2015 年给出退避抖动的定量设计。智能体框架把三个传统的成果组装进"LLM 步进执行"这个新运行时，检查点恢复随之成为框架标配。演化细节与定量的退避账见 12.5.7。

12.3 发挥的作用：为什么重要

第一，它把长任务的平均完成率从"运气"变成"设计值"。工具调用失败率哪怕只有 3%，一个 30 步的任务全程无故障的概率也不到 40%；没有重试，多数任务死于偶发抖动而非能力不足。重试、降级、检查点这三件事把存活曲线重新拉直。

第二，它保护系统不被故障放大摧毁。没有熔断的智能体集群遇到模型服务故障时，所有智能体同时疯狂重试——这本身就是一次自造的 DDoS（重试风暴）；退避加抖动控制重试节奏，熔断控制总量，错误预算控制整体风险敞口。容错设计的第一受益者常常不是当前这次任务，而是整个共享依赖。

第三，它让"有副作用的智能体"成为可能。读操作失败可以重来，写操作失败重来可能双倍扣款。幂等键、检查点、SAGA 补偿共同给出工程答案：至少一次的投递 + 恰好一次的效果。没有这一层，智能体永远只能停留在"只读"的安全区。

12.4 实际应用与案例

模型 API 调用加固。场景：智能体核心的每一次推理调用都依赖外部 API。做法：429/超时用指数退避加抖动重试（带次数上限与总时长预算），内容策略拒绝不重试原文而是改写后重试一次，连续失败触发熔断并降级到备用模型。关键设计点：区分"可重试"与"不可重试"的 HTTP 语义；重试计数要随请求头透传，避免中间层重复叠加重试造成放大。

结构化输出解析失败重试。场景：要求模型输出 JSON，偶发返回带注释或截断的非法 JSON。做法：解析失败时把解析器的报错原文（哪个字段、什么类型错）附回给模型重问，两次失败换更宽松的修复提示词或降级到规则抽取。关键设计点：报错信息要具体可执行（"total 应为数字，实际为字符串'120元'"），这正是 Instructor 类库把校验错误自动回传的思路。

带支付的多步订单流程。场景：查库存→扣款→发货，任何一步后都可能崩。做法：扣款用客户端生成的幂等键（同键重试服务端去重），发货失败用 SAGA 补偿（先退款再取消，逆序回滚），全程状态落检查点，崩溃后从检查点续跑且已扣款步骤凭幂等记录跳过。关键设计点：补偿动作本身要幂等（退款接口可安全重复调用），补偿失败进人工队列。

长时研究/爬取任务断点续跑。场景：数小时的采集任务，浏览器崩溃、机器重启随时可能发生。做法：每完成一个单元（一个页面、一个子问题）即写检查点；重启后从检查点恢复，跳过已完成单元。关键设计点：检查点粒度按"可安全重做的最小副作用单元"划，太细则开销大，太粗则重做面大。

熔断降级保可用。场景：检索依赖抖动，智能体答不了问题。做法：熔断器打开后自动降级到缓存答案或"基于本地知识 + 明确标注信息可能过期"的答复，并在响应里打降级标记。关键设计点：降级必须可观测（指标与日志标记降级原因），否则用户默默忍受低质答案、没人知道系统早已带病运行。

批量作业的失败隔离。场景：一千条工单的批量处理，个别工单触发模型异常。做法：单条失败落死信队列带完整上下文，不阻断整批；整批结束统一重放死信。关键设计点：失败条目要记录原始输入与错误分类，重放前先修根因，避免重放风暴。

真实世界实例

Temporal 的 durable execution 生产舰队。Temporal 官方客户数据显示：Netflix 有 150 多个工程团队、500 多个命名空间跑在 Temporal 上，每月执行超过 70 亿次动作且仅由 3 名全职工程师运维；OpenAI 在不到一年内把 Temporal 用量提升 60 倍，Snap、Salesforce、NVIDIA 亦在其客户名单——"进程可以死、流程必须活"正是本章检查点恢复模式的基础设施化。来源：Temporal 官方客户与规模数据页。

Stripe 的幂等键设计。Stripe API 对所有 POST 型写操作要求客户端生成并在重试中复用 Idempotency-Key 请求头，服务端在窗口期内对同键请求去重并返回首次结果——本章"至少一次投递 + 客户端幂等键 + 服务端去重 = 恰好一次效果"公式的行业标杆实现，也是智能体涉及支付的写操作必须对齐的接口契约。来源：Stripe API 幂等请求官方文档。

AWS Step Functions 的声明式 Retry/Catch。Step Functions 把本章机制做进了状态机语言：每个状态可配 Retry（IntervalSeconds、MaxAttempts、BackoffRate，退避乘数默认 2.0），重试穷尽后由 Catch 把错误路由到回退状态，形成声明式的"错误分类 → 重试 → 失败路径"；其 Standard 工作流另提供恰好一次的状态转移语义。来源：AWS Step Functions 错误处理官方文档。

12.5 深度讲解

12.5.1 agent 特有的故障分类：四层故障与策略映射

智能体故障的分类学直接决定策略，值得给出完整映射。模型故障：限流（429）与过载（5xx）是瞬时的，退避重试有效；上下文超限是永久的，重试无益，要裁剪上下文；内容策略拒绝介于两者之间——原样重试大概率再拒，改写输入后重试可能通过；生成质量随机劣化（幻觉、跑题）属于语义故障，重试同 prompt 是抛硬币。工具故障：网络与超时是瞬时；权限与配额是永久（需人工或换凭据）；格式漂移（上游改了返回结构）是"语义故障的工具版"，要靠输出校验发现；部分成功（批量操作完成一半后断连）最危险，盲目重试=重复执行，必须先查幂等记录。编排故障：死循环、状态丢失、并发写冲突；这类故障重试的是"代码"而不是"请求"，检查点与状态版本化是对策。语义故障——返回了但错了，是 agent 特有且最阴险的一层：它不抛异常，没有错误码，只有第 11 章的判据与校验能抓住它。抓住后的正确动作不是原样重试（同输入大概率同错误），而是改变条件再试：换提示词、加约束、换模型，或把校验错误作为反馈注入。一句话原则：抛异常的错误用重试治，不抛异常的错误用校验治。

12.5.2 重试与退避：节奏设计的定量细节

重试策略的三个参数——次数、间隔、抖动——都有讲究。次数与总预算：重试次数应换算为总时间预算（如"最多 4 次、总等待不超过 30 秒"），因为指数退避下次数与等待时间是乘法关系，不设总预算的次数上限会拖垮调用方。间隔：capped exponential backoff，sleep = min(cap, base * 2^attempt)。抖动：Brooker 在 2015 年的分析揭示了纯退避的盲区——并发客户端即使各自指数退避，重试时刻仍会同簇出现（大家的节奏一致），服务端收到的是周期性脉冲而非平滑流量；解法是 full jitter：sleep = random.uniform(0, min(cap, base * 2^attempt))，把每次的重试时刻在区间内随机化。模拟数据显示 full jitter 在总完成时间与调用总量上都显著优于无抖动退避。另一个常被忽略的放大器是多层重试：客户端重试 3 次 × 网关重试 3 次 × SDK 重试 3 次 = 一次故障最多 27 发请求。原则是整条调用链只在一层做重试（通常在最外层），或把重试预算作为元数据沿调用链传递并逐层递减。

12.5.3 熔断、舱壁与错误预算

熔断器是一个三态状态机：闭合（正常放行，滑动窗口内统计失败率）→ 失败率超阈值 → 打开（一切调用立即快速失败，不打扰依赖）→ 冷却期结束 → 半开（放行少量探测请求）→ 成功则闭合、失败则重回打开。它治的病是"对已死依赖的持续骚扰"：依赖已经过载，每个重试都在给它补刀；熔断用快速失败给依赖恢复窗口，也把调用方的资源从无限等待中解放出来。舱壁是隔离维度：按依赖划分资源池（并发数、连接数），一个依赖的饱和不会拖垮其他依赖——智能体系统里至少要把"模型调用""检索调用""写操作"分池。错误预算是治理维度：为每个依赖设定滑动窗口错误率上限（如 1%），超出即触发自动熔断与新版本发布冻结。三者共同的哲学是：可用的降级服务优于不可用的完美服务。落地陷阱两个：熔断阈值按依赖分级设置（核心依赖阈值高、容忍度高，边缘依赖阈值低、熔断快）；半开状态的探测流量要小而可控，否则探测本身就是一次小型风暴。

12.5.4 检查点与恢复：非确定性带来的新难题

传统 durable execution 的假设是"步骤可确定性重放"——同样的输入重跑同样的代码得到同样的结果，所以只需存输入。LLM 智能体打破了这个假设：步骤的输出是模型生成，不可重放。因此智能体的检查点必须存结果而非仅存输入：每步完成后，把（步骤标识、输入摘要、完整输出、上下文增量）原子写入持久层；恢复时，已完成步骤直接复用存下的输出，只有未完成步骤才真正重执行。三个工程细节决定成败。其一是原子性：检查点写入与副作用提交的顺序——先写检查点再提交副作用，崩溃在两者之间会漏记已完成的事实；先提交再写检查点，崩溃在中间会导致重做。工程解法是把幂等键放进副作用请求里，让"重做"在服务端去重，两个顺序就都安全了。其二是上下文一致性：恢复后的对话历史必须与检查点时刻完全一致，包括工具返回的原始文本（不只是摘要），否则模型基于失真的记忆继续工作。其三是恢复的迭代上限：同一步骤反复失败反复从检查点恢复，应该计数并在达到上限后升级，避免"恢复风暴"。

12.5.5 幂等与补偿：副作用世界的两把钥匙

幂等解决"同一操作执行多次，效果如同一次"。HTTP 语义里 GET/PUT/DELETE 天然幂等而 POST 不幂等（RFC 9110）；工程实践是客户端生成幂等键（UUID，随请求携带，服务端在窗口期内去重）——支付、下单、发消息这些 POST 型操作都必须补上这层。智能体的特殊性在于"重试决策是自动做出的"，人尚可在重试前想一下"是不是已经扣过款了"，自动重试不会想，所以幂等保护必须内建于工具实现而非依赖调用方自觉。补偿解决"已经发生、无法撤销的操作如何退回"。SAGA 的洞见是把长事务拆成子事务链，每个子事务登记对应的补偿动作，失败时逆序执行补偿：下单的补偿是取消，扣款的补偿是退款，发邮件的补偿是……没有（不能撤回，只能发更正邮件）。这提示补偿设计的分级：可精确撤销（数据库写）、可业务对冲（退款）、不可撤销只能披露（外发消息）——第三类必须在执行前的确认闸门里拦截，而不是事后补救。补偿链自身的故障处理常被遗忘：补偿也可能失败，补偿要幂等、要重试、最终失败进人工队列；同时记录"补偿中"状态，防止系统在半回滚状态下接受新请求。

12.5.6 降级链与失效模式

降级链是一张预先画好的能力阶梯：主模型 → 备用模型 → 缓存答案 → 静态话术 + 转人工。设计要点：每一级的触发条件明确（不是"感觉不行了"就降）、每一级的效果损失被明确接受、降级动作全程打标（响应头、日志、指标），并有"自动回梯"机制——依赖恢复后自动切回主路径。最危险的反模式是降级成为常态：主依赖故障两周无人发现，因为用户拿到的"都还行"。对策是降级率本身进告警。

失效模式清单，每一条都值得当作 review checklist：无限重试（没有次数与总预算上限）；重试非幂等操作（双倍扣款制造机）；吞异常继续（except: pass 让错误状态污染后续所有步骤）；把重试当修复（永久错误重试十次只是把失败变贵）；检查点不含上下文（恢复后模型失忆，行为断裂）；降级路径从未被测试（真出事时降级路径自己崩）；半开探测风暴（熔断恢复期的探测没限流）；死信队列无消费者（失败被"记录"了，但没人重放）。何时可以不用这套机制：纯内存、无副作用、可整体重算的短任务，直接失败重抛最简单——容错机制的复杂度必须与任务的价值和不可重做性匹配。

12.5.7 演化谱系、定量的退避账与"恰好一次"的真相

把演化脉络并成一句话：失败处理的重心不断上移。语言层（1960 年代 PL/I 的 ON 条件，1990 年代 C++/Java 的 try/catch）解决单进程内失败的表达与清理；事务层（1987 SAGA）解决跨系统原子性——长事务持锁不可行，就用补偿把"回滚"变成显式业务动作；服务层（2007《Release It!》系统化熔断/舱壁/超时，2012 Hystrix 微服务间工程化）解决依赖故障的隔离与止损；平台层（2017 年 Uber Cadence 发布 durable execution 引擎，后由其团队独立发展为 Temporal）把"进程可以死、流程必须活"变成基础设施承诺。智能体框架承接全部四层，并补上本领域特有的两笔：Instructor 在 2023 年普及了"结构化输出校验失败→带错误信息重问"，把语义故障纳入重试版图；LangGraph Checkpointer（2024）让检查点恢复成为框架标配——而模型输出不可重放，检查点必须连同上下文快照一起存（12.5.4）。

定量证据一：抖动的收益可以算出来。 Brooker 在 2015 年的退避分析中给出的定量结论：100 个并发客户端的场景下，full jitter 相比无抖动的指数退避把调用总量减少了一半以上，且全部调用更早完成；文章同时指出总工作量随客户端数按 N² 增长，抖动不改变量级，但"在合理的竞争水平上大幅减少工作量"。数学直觉值得一讲：无抖动时所有客户端的退避节奏相同——同样失败、同样的 sleep 序列，重试时刻周期性聚簇成脉冲，服务端刚缓过气就被下一波齐射打倒；full jitter 把每次 sleep 在 [0, 上限] 内均匀随机化，单次期望不变，但 N 个客户端的重试时刻被摊成近似均匀分布，聚合负载从"脉冲"变成"平纹"。这套结论已被基础设施默认采纳：Envoy 的重试退避就是 fully jittered exponential（基准间隔 25ms、上限 10 倍）。

定量证据二：重试上限要按"占总量百分比"计，而不是按次数计。 这就是重试预算（retry budget）。Envoy 的 retry budget 把并发重试数限制在"活跃请求+等待请求"总和的百分比内，默认 20%（另设最小并发 3 兜底）——故障时重试永远不超过正常流量的两成，重试风暴挤垮共享依赖的路径被从总量上封死。它与 12.6 代码里"次数+总时长双预算"互补：单请求维度防拖死，总量维度防放大。多层重试相乘的账（12.5.2 的 3×3×3=27 发）说明为什么两个维度都必须有。

反直觉点："恰好一次"在分布式系统里是幻觉。 大家默认"重试到成功=没丢也没重"，基本事实是：发送方发出请求后，能观测到的只有"收到回复"或"没收到"，而"没收到"分不清是"没执行"还是"执行了但回复丢了"。于是只有两个诚实的选择：要么重试——至少一次投递，代价是可能重复；要么不重试——至多一次，代价是可能丢失。工程上的"恰好一次"从来不是投递属性，而是合成物：至少一次投递 + 幂等键 + 服务端去重 = 恰好一次的效果。Stripe 的实现是行业标杆：所有 POST 型写操作要求客户端生成并在重试中复用 Idempotency-Key，服务端对同键请求去重并返回首次结果。但要清醒地看到合成物的边界：幂等键有窗口——Stripe 的键默认保留约 24 小时，超窗后同键重放会作为新请求再次真实执行。跨天的批处理任务若重放周期超过幂等窗口，必须升级为业务层去重（状态机判断"这笔是否已支付"），而不是信任传输层。

边界条件：容错机制何时开始伤害系统。其一，长尾延迟敏感的在线路径——重试直接拉长 P99，重试预算要在线上路径收紧；其二，依赖已确认死亡（熔断打开）后继续重试纯属自伤；其三，幂等窗口短于任务最长重放周期时，"恰好一次效果"失效（见上）；其四，纯内存、可整体重算的小任务——全套机制是负资产，容错复杂度必须与任务价值匹配。

12.5.8 怎么用：运用判断

适用信号：调用链上有不可重做的副作用（支付、外发、下单）；任务步数多到"崩了从头来"不可接受（十步量级以上）；依赖失败率不可忽略（外部 API、模型服务）；多个智能体共享同一批依赖（重试风暴风险）。四条占两条以上，就值得把四层机制配齐。

与最近替代方案的对比：

方案 与本章四层机制的关键差异
裸 try/except + 手写重试 只有第一层；无熔断、检查点、幂等，失败放大与重复副作用无人拦截
tenacity 等重试库 退避参数化做得好；但熔断、检查点、幂等、降级仍在库外，要自建
Temporal / Step Functions 等 durable execution 检查点与重试全托管，重基础设施；小规模任务的收益撑不起引入成本

落地三步：第一步，给每次外部调用包一层"错误分类 + capped exponential + full jitter + 次数与总时长双预算"的调用包装——12.6.1 片段二的 full_jitter_sleep 与错误类层次可以直接拿去用。第二步，写操作一律携带客户端生成的幂等键（UUID），只读操作按输入哈希缓存，减少对不稳定依赖的真实调用。第三步，任务超过十个步骤就引入检查点：每步成功后原子落盘"结果+上下文快照"，重启从检查点续跑——12.6.1 的 Checkpointer 就是可运行的最小版。三步之后再按 12.6.3 清单补熔断、降级演练与可观测。

片段一：错误分类——先分类再行动的类型基础。

"""健壮执行器：full jitter 退避重试 + 熔断器 + 检查点恢复 + 幂等跳过 + 降级链。
依赖：仅标准库；生产中 step.fn 内接模型/工具调用，错误分类不变"""
import json
import random
import time
from dataclasses import dataclass, field
from enum import Enum
from pathlib import Path
from typing import Callable


class StepError(Exception):
    """步骤错误基类。"""
class RetryableError(StepError):
    """瞬时错误（限流 429、超时、网络抖动）：策略=退避重试。"""
class FatalError(StepError):
    """永久错误（参数非法、权限不足）：策略=不重试，走降级。"""
class CircuitOpenError(StepError):
    """熔断打开期的快速失败：策略=直接降级。"""

▸ 代码怎么读：这五类就是 12.1.2 第一层"错误分类"的可执行形态。异常类型即策略标签——后面的执行器靠 except 的类型匹配选动作，而不是在 except 块里写一串 if 判断错误码。CircuitOpenError 也归入 StepError 家族是刻意的：熔断打开本质是"调用方自知必败"的特殊失败，走同一条降级管线。读者接入自己的系统时，把 HTTP 状态码、SDK 异常映射到这三类即可——分类错了，后面全错（把永久错误标成瞬时，重试只是把失败变贵）。

片段二：熔断器三态机与 full jitter 退避。

class CircuitState(str, Enum):
    CLOSED = "closed"; OPEN = "open"; HALF_OPEN = "half_open"   # 闭合(放行)/打开(快速失败)/半开(探测)


class CircuitBreaker:
    """三态熔断器：连续失败达阈值即打开，冷却期满转半开放行探测。"""
    def __init__(self, failure_threshold: int = 3, recovery_seconds: float = 30.0) -> None:
        self.failure_threshold = failure_threshold
        self.recovery_seconds = recovery_seconds
        self.state, self.failures, self.opened_at = CircuitState.CLOSED, 0, 0.0
    def allow(self) -> bool:
        if self.state is CircuitState.OPEN:
            if time.monotonic() - self.opened_at < self.recovery_seconds:
                return False                    # 冷却未满：快速失败，不打扰已过载的依赖
            self.state = CircuitState.HALF_OPEN # 冷却期满：放行探测
        return True
    def record_success(self) -> None:
        self.failures, self.state = 0, CircuitState.CLOSED
    def record_failure(self) -> None:
        self.failures += 1
        if self.state is CircuitState.HALF_OPEN or self.failures >= self.failure_threshold:
            self.state, self.opened_at = CircuitState.OPEN, time.monotonic()


def full_jitter_sleep(attempt: int, base: float = 0.2, cap: float = 8.0, scale: float = 1.0) -> None:
    """full jitter 指数退避：sleep 在 [0, min(cap, base*2^attempt)] 内均匀随机（Brooker 2015）。"""
    delay = random.uniform(0, min(cap, base * (2 ** attempt))) * scale
    time.sleep(delay)                       # scale=0 时 delay 恒为 0，演示免等待

▸ 代码怎么读：熔断器是 12.5.3 三态状态机的最小实现，三个参数各有讲究。failure_threshold=3：连续三次失败才打开——阈值太低会把抖动误判成故障，太高则打开前已自伤过多。recovery_seconds=30：冷却期给依赖恢复窗口；time.monotonic() 而非 time.time() 是因为单调时钟不受系统对时影响。半开态不单独计数：探测请求若成功，record_success 直接闭合；若失败，record_failure 的第一个条件立即重回打开——探测失败说明依赖没好，继续等。full_jitter_sleep 就是 12.5.7 的公式本体：random.uniform(0, min(cap, base*2^attempt))，把重试时刻在区间内均匀随机化，抹平并发重试的同步脉冲；scale 参数专为演示而生（置 0 免等待），生产里保持 1.0。

片段三：检查点与步骤定义——"存结果而非存输入"。

class Checkpointer:
    """已完成步骤的结果原子落盘；恢复时凭记录跳过 => 重走不重复执行副作用。"""
    def __init__(self, path: str) -> None:
        self.path = Path(path)
        self.data = (json.loads(self.path.read_text())
                     if self.path.exists() and self.path.stat().st_size > 0 else {"steps": {}})
    def get(self, step_id: str) -> dict | None:
        return self.data["steps"].get(step_id)
    def save(self, step_id: str, result: dict, degraded: bool = False) -> None:
        self.data["steps"][step_id] = {"result": result, "degraded": degraded}
        tmp = self.path.with_suffix(".tmp")  # 先写临时文件再原子替换，防写坏检查点
        tmp.write_text(json.dumps(self.data, ensure_ascii=False))
        tmp.replace(self.path)


@dataclass
class Step:
    step_id: str
    name: str
    fn: Callable[[dict], dict]                                  # 正常实现
    fallback: Callable[[dict, Exception], dict] | None = None   # 降级实现（能力阶梯下一级）
    max_retries: int = 3                                        # 重试次数上限
    breaker: CircuitBreaker = field(default_factory=CircuitBreaker)

▸ 代码怎么读：Checkpointer 对应 12.5.4 的两个关键点。存的是结果：save 记录的是步骤产出（外加 degraded 标记），恢复时 get 直接复用——模型输出不可重放，所以必须存结果而不是只存输入。原子写：先写 .tmp 再 replace，进程崩溃在写一半时不会留下损坏的检查点文件——replace 在同一文件系统上是原子操作。Step 把四层策略参数化：fn 是正常实现，fallback 是降级阶梯的下一级（可为 None，表示无降级、失败即升级），max_retries 与 breaker 让每步有独立的重试与熔断预算——按依赖分级设置正是 12.5.3 的落地要求。

片段四：执行器四层管线与端到端演示。

class RobustExecutor:
    """单步四层管线：幂等跳过 -> 熔断检查 -> 退避重试 -> 降级 -> 检查点。"""
    def __init__(self, checkpoint: Checkpointer, sleep_scale: float = 1.0) -> None:
        self.checkpoint, self.sleep_scale = checkpoint, sleep_scale
    def run_step(self, step: Step, ctx: dict) -> dict:
        saved = self.checkpoint.get(step.step_id)
        if saved is not None:               # 1) 幂等跳过：已有结果不重做（副作用恰好一次）
            return saved["result"]
        if not step.breaker.allow():        # 2) 熔断打开：快速失败，直接进降级
            err: Exception = CircuitOpenError(f"{step.name} 熔断打开中")
        else:
            for attempt in range(step.max_retries + 1):   # 3) 重试：瞬时错误退避重试
                try:
                    result = step.fn(ctx)
                    step.breaker.record_success()
                    self.checkpoint.save(step.step_id, result)
                    return result
                except FatalError as exc:   # 永久错误：重试无意义，立即退出
                    err = exc; break
                except StepError as exc:
                    err = exc
                    step.breaker.record_failure()         # 计入熔断统计
                    full_jitter_sleep(attempt, scale=self.sleep_scale)
        if step.fallback is None:           # 4) 降级：有降级实现则落盘（degraded=True），无则升级
            raise err
        result = step.fallback(ctx, err)
        self.checkpoint.save(step.step_id, result, degraded=True)
        return result
if __name__ == "__main__":
    ckpt = Path("order_checkpoint.json"); ckpt.unlink(missing_ok=True); calls = [0]
    def charge(ctx: dict) -> dict:      # 前 2 次限流，第 3 次成功；幂等键让重试安全
        calls[0] += 1
        if calls[0] <= 2: raise RetryableError("支付网关 503")
        return {"charged_cny": 129.0, "idempotency_key": "key-ORD-9"}
    step = Step("charge", "支付", charge,
                lambda ctx, err: {"charged": False, "reason": f"降级货到付款（{err}）"}, max_retries=4)
    r1 = RobustExecutor(Checkpointer(ckpt), sleep_scale=0.0).run_step(step, {})
    r2 = RobustExecutor(Checkpointer(ckpt), sleep_scale=0.0).run_step(step, {})
    assert r1 == r2 and calls[0] == 3   # 恢复运行命中检查点：真实支付只执行 3 次，无重复副作用
    print(f"演示通过：{r1}；检查点：{ckpt.resolve()}")

▸ 代码怎么读：run_step 的四层结构与图 12-2 一一对应，每层都是一个早退出口：命中检查点立即返回（不重做副作用）；熔断打开直接跳到降级（不骚扰已过载的依赖）；重试环里 FatalError 与 StepError 分道——前者 break 立即放弃重试，后者计入熔断统计后再退避；四层全过仍失败，才轮到降级，且降级结果同样落盘并带 degraded=True 标记——恢复运行会复用降级结果，不会"恢复正常后偷偷再执行一次副作用"。注意熔断检查放在重试环之外：打开态下连第一次尝试都不发起。演示里第二次运行新建了整个执行器实例（模拟进程崩溃重启），calls[0]==3 证明重试恰好发生两次、恢复运行零重复执行——这就是"至少一次投递加幂等跳过等于恰好一次效果"的可运行证据。读者改哪里：把 charge 换成真实模型/工具调用、按依赖设 max_retries 与阈值，其余不动。

12.6.2 框架差异速览

各框架托管了四层管线的一部分，托管边界各不相同：

框架 同名能力 与本章实现的差异
LangGraph Checkpointer（InMemorySaver/SqliteSaver/PostgresSaver） 图每个节点后自动存状态，按 thread_id 命名空间，恢复用增量 invoke；检查点层托管，重试/熔断仍需自建
AWS Step Functions 状态级 Retry（IntervalSeconds/MaxAttempts/BackoffRate）与 Catch 声明式"错误分类→重试→回退状态"；退避为固定倍数乘法，抖动需留意
Temporal Activity 的 RetryPolicy 自动重试 + 事件溯源恢复 每步可确定性重放，检查点即事件历史，基础设施级；引入成本最高
Instructor 校验失败自动回传错误重问 只覆盖语义故障"改条件重试"一支，与本章机制互补

（官方文档：LangGraph、Step Functions 错误处理、Temporal、Instructor。）

12.6.3 生产化改造清单

  • 错误处理：全链路错误分类（可重试/永久/语义）落到统一的错误类型；任何 except 都必须记录并分流，禁止裸吞。
  • 超时：模型调用、工具调用、整个步骤三层都要有超时；超时错误按可重试处理，但计入熔断统计。
  • 重试治理：full jitter 退避 + 次数与总时长双预算；调用链只在一层重试，重试深度随请求头传递递减。
  • 并发：共享依赖分舱壁（按依赖设并发上限）；批量任务限速，失败条目进死信队列带全量上下文。
  • 缓存与幂等：写操作一律携带客户端幂等键；只读结果按输入哈希缓存，减少对不稳定依赖的真实调用。
  • 可观测：重试率、熔断状态、降级率、恢复次数做成一等指标；每次降级在响应与日志打标，降级率超阈值告警。
  • 检查点：检查点含完整上下文快照（含工具原始输出）；写入原子化（临时文件+替换或事务）；同一步骤恢复重试设上限，超限升级人工。
  • 成本控制：重试与降级都消耗 token，按任务设金额预算；语义错误的"改条件重试"次数单列限额，防止"校验-重试"循环烧钱。
  • 演练：降级路径与恢复路径要定期演练（混沌工程式注入故障），从未运行过的恢复代码等于不存在。

12.7 概览 / 核心要点 / 结论

本章小结

异常处理与恢复把智能体执行从"祈祷不失败"改造为"失败按剧本走"：先分类（瞬时/永久/语义）再选策略，瞬时错误用带抖动的退避重试，持续错误用熔断止血、用降级维持服务，长流程靠检查点断点续跑，副作用靠幂等键与 SAGA 补偿保证"重走无伤害"。这套机制没有一件是智能体时代的新发明——从 PL/I 的异常、SAGA 的补偿到 Nygard 的稳定性模式与 durable execution 引擎——智能体工程做的是把它们组装进一个输出不可重放的新运行时，并为"返回了但错了"的语义故障补上校验这一环。

核心要点

  • 四层故障四类对策：模型故障退避重试/裁剪上下文，工具故障重试+幂等，编排故障检查点+状态版本化，语义故障只能靠校验抓、改条件重试。
  • 重试三原则：只重试幂等操作、指数退避必须加 full jitter、次数与总预算双上限。
  • 整条调用链只在一层重试，多层重试相乘是重试风暴的根源。
  • 熔断器三态（闭合/打开/半开）+ 舱壁隔离 + 错误预算：可用的降级优于不可用的完美。
  • 智能体检查点必须存"结果+完整上下文"而非仅存输入——模型输出不可确定性重放。
  • 副作用安全公式：至少一次投递 + 客户端幂等键 + 服务端去重 = 恰好一次效果。
  • SAGA 补偿逆序回滚；补偿自身要幂等、要重试、最终失败进人工队列；不可撤销动作必须在事前确认闸门拦截。
  • 降级链预画能力阶梯且全程打标；降级率进告警，防止降级悄然成为常态。

结论

判断一个智能体系统是否生产就绪，看的不是演示时的流畅，而是故障时的剧本：重试是否克制、熔断是否及时、降级是否有标、恢复是否无副作用。这些剧本的每一行都来自半个多世纪的工程积累，智能体并没有推翻它们，只是让"语义故障"加入进来、让"不可重放"提高了检查点的成本。把失败路径当作一等公民来设计的团队，才能把智能体放进真正重要的业务流程里。
