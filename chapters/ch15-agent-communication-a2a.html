第四部分 · 高级架构

第15章 智能体间通信 Agent-to-Agent Communication (A2A)

用开放协议连接分属不同团队与框架的智能体：Agent Card 发现能力、Task 状态机管理长任务、消息信封跨组织传递，与 MCP 构成纵横互补。

一句话定义：A2A 用开放协议让分属不同框架、不同组织的智能体互相发现、委托任务并交换产物——每个 agent 发布一张能力名片，任务以带生命周期的状态机流转，双方不暴露内部实现。 解决什么问题：跨团队/跨框架的 agent 互调没有统一协议，点对点集成爆炸 ｜ 适用场景：跨组织协作、多供应商 agent 生态、企业内跨部门 agent 互操作 ｜ 核心机制：Agent Card 能力发现 + Task 状态机 + Message/Part/Artifact 信封 + 流式与推送通知 ｜ 代价：多一跳网络与序列化、信任与认证配置成本、业务 schema 仍需双方另行约定。

本章速读　A2A 用开放协议连接分属不同团队与框架的智能体：每个 agent 在约定路径发布一张 Agent Card 自述能力，调用方凭名片发现与匹配；任务（Task）以标准状态机流转（submitted→working→input-required/completed/failed/canceled），消息用统一信封（Message/Part/Artifact）封装，传输复用 Web 安全体系。它管"组织边界"：对方的部署、发布、权限都不归你管时才用；同进程同框架用框架内编排，纯工具调用用 MCP。业务 schema 协议不管，需双方另行约定。

15.1 模式概述

15.1.1 问题背景：为什么需要这个模式

第 7 章的多智能体协作用于一个前提：所有 agent 在同一个进程、同一个框架里，协调器和专家共享语言与运行时。这个前提一跨出组织边界就碎了。你的客服 agent 想把售后工单委托给供应商的售后 agent——对方是用另一个框架写的、跑在别人机房里、由别人维护的自治系统。硬接会遇到三层问题。发现：对方是谁、能干什么、接口在哪？总不能每接一家就打电话问一遍。协作语义：对方不是函数——它可能要跑十分钟，可能中途要向你追加问题（甚至要问你的用户），可能失败，可能被取消。函数调用的 request/response 语义表达不了这些，你需要任务（Task）而非调用（Call）。封装：对方凭什么把内部工具、提示词、会话状态暴露给你？合理的边界是"只接任务、只交产物"，内政不容过问。协议要回答的正是这三层：怎么发现、怎么委托、怎么在不暴露实现的前提下协作。A2A（Agent2Agent）给出的答案结构：每张 agent 发布一张 Agent Card 自述能力，任务以标准状态机流转，消息用统一的信封封装，传输复用成熟的 Web 安全体系。

15.1.2 核心机制：它如何工作

A2A 的对象模型有四个核心构件。Agent Card：每个 agent 在约定的 well-known 地址（v0.2.x 为 /.well-known/agent.json，v0.3.0 起依 IANA 反馈更名为 /.well-known/agent-card.json）发布一张 JSON 名片，声明身份、描述、端点、能力开关（是否支持流式、推送通知）、技能清单（skills，含 id、名称、描述）与安全方案。客户端拿名片做能力发现——像浏览器读 robots.txt 一样，约定路径、自述格式。Task：协作的基本单元，有完整生命周期——submitted（已受理）→ working（执行中）→ input-required（挂起等补充）/ completed / failed / canceled（v0.3 还定义了 rejected 与 auth-required），另有历史（history）与产物（artifacts）挂在任务上。Message 与 Part：双方交换的消息信封，role 区分 user/agent 侧，内容由 Part 组成——文本、结构化数据或文件，同一消息可混装。通知机制：短任务同步等响应；长任务可走 SSE 流式增量接收状态与产物，也可注册 webhook 让远端完成时主动推送。传输层面，规范以 JSON-RPC over HTTP 为主绑定，另有 gRPC 与 REST 风格的 HTTP+JSON 绑定；v1.0 起三者列为对等绑定。认证不发明新体系——OAuth2、API key、mTLS 直接复用 Web 世界的成熟方案。

15.1.3 与相邻模式的关系与组合

与 MCP（第 10 章）的关系是官方口径的互补而非竞争：MCP 连 agent 与工具/数据（纵向），A2A 连 agent 与 agent（横向）；一个 A2A agent 节点内部照常用 MCP 接自己的工具。与多智能体协作（第 7 章）的关系是边界扩展：框架内的协调拓扑解决"怎么分工"，A2A 解决"跨出框架与组织后怎么握手"——协调器委派给外部 agent 时，外部 agent 在协调器眼里就是一个拥有名片与状态机的对等体。与人在回路（第 13 章）的关系藏在 input-required 状态里：跨组织场景中"信息不足需要补充"被提升为协议一等状态，挂起的可能是对方的用户、你的用户或双方的人——第 13 章的闸门在协议层有了统一的挂起表达。与异常处理（第 12 章）的关系是失败的可观测：failed/canceled 是标准终态，任务可随时 tasks/get 查询现场，断线后可重新订阅——跨网络的异常处理从"各自发明"变成"共同剧本"。

15.2 起源与历史：最早是谁提出来的

agent 间通信语言的谱系比 LLM 早三十年。1993 年，UMBC 的 Tim Finin 等人发布 KQML（Knowledge Query and Manipulation Language），这是第一代 agent 通信语言：消息按"言语行为"（speech act）分类——ask、tell、achieve、broker 等原语表达的不只是内容，还有发送者对内容的意图（是询问、断言还是请求行动），这一设计哲学来自奥斯汀与塞尔的言语行为理论。2000 年，FIPA 组织批准 FIPA-ACL 标准，沿袭言语行为框架但给出更严格的形式语义（每类通信行为附带可行前置条件与理性后果），并与 FIPA 的 agent 管理与发现规范配套。此后十余年，multi-agent 系统研究热潮退去，通信语言停留在学术与少数工业部署中。转折发生在 2024 年 11 月 Anthropic 发布 MCP：工具侧的协议化让 agent 能力暴涨，agent 之间的连接需求随之显形——每个 agent 都成了"潜在的服务方"，缺的只是一张统一名片和一套任务剧本。2025 年 4 月 9 日，Google 在 Cloud Next 大会发布 A2A 协议，发布即有 50 余家合作伙伴背书（Atlassian、Box、Cohere、Intuit、LangChain、Microsoft、MongoDB、SAP、Salesforce 等）；同年 6 月 23 日，Google 将协议捐入 Linux Foundation，走向供应商中立治理，技术指导委员会由多家厂商共同组成；7 月 31 日发布 v0.3.0，包含 well-known 路径更名、Agent Card 签名等破坏性变更；同年 8 月，IBM 的 Agent Communication Protocol（ACP）宣布并入 A2A。2026 年，规范发布 v1.0 稳定版（当前 v1.0.1），Python/JS/Java/.NET 官方 SDK 齐备。

演化脉络有一个值得驻足的细节：KQML 与 FIPA-ACL 死在了"语义过重"上——消息的每个原语都要求双方对形式语义达成共识，工程成本高到没有生态。A2A 的做法几乎相反：协议只约定信封、状态与发现，语义（这条文本到底什么意思）完全交给端到端的 LLM 去理解——大模型把"相互理解的成本"降到了零，协议因此只需要做"传输与生命周期"这一件小事。三十年的螺旋：语义进协议失败，语义进模型成功。

15.3 发挥的作用：为什么重要

第一，把跨 agent 集成从 M×N 压到 M+N。没有协议时，每对接一个外部 agent 就要写一次定制集成；有了统一的名片格式与消息信封，客户端代码写一次就能调用任何兼容 agent——这与 MCP 对工具侧的压缩是同一个逻辑，只是发生在水平方向。第二，边界封装让协作不牺牲自治。被调用的 agent 不暴露提示词、工具与会话状态，只承诺名片上写的技能与状态机语义；内部换模型、换框架、重构实现，调用方无感——这是"服务化"在 agent 时代的重演，也是组织间协作的唯一可行边界。第三，长任务成为一等公民。input-required、异步流式、webhook 推送、断线重订阅，这些原语让"跑几小时的调研任务""要向用户追问的任务"有了标准的挂起与恢复姿势，而不必把长任务伪装成同步调用。第四，生态位扩张。对 agent 提供方，A2A 是把自有能力作为服务出售的标准接口；对使用方，组合外部 agent 像浏览网页一样——找到名片、看技能、发任务。协议中立化（Linux Foundation 治理）与云厂商原生支持（Google Cloud、AWS、Azure 均已接入）让这张网络有了跨厂商生长的土壤。

15.4 实际应用与案例

客服网络的跨组织工单流转。 品牌方客服 agent 识别出售后问题后，把工单按 A2A 委托给供应商售后 agent，任务状态与处理结论回流品牌方。关键设计点：品牌方只依赖供应商的 Agent Card 与状态机语义；input-required 时品牌 agent 向自己的用户追问再补充给远端。

企业内跨部门 agent 互查。 HR agent 与财务 agent 分属不同团队、不同框架，经 A2A 互查"某员工今年还剩几天年假"。关键设计点：认证走企业 OAuth；权限在各自 agent 内部强制执行——财务 agent 只返回该调用方有权看到的数据。

多供应商旅行助手生态。 主旅行 agent 按用户行程委托航司 agent 查票、酒店 agent 查房、租车 agent 报价，多路并行收产物后聚合。关键设计点：远端任务时长不一，统一用流式订阅 + 超时取消（canceled）管理；聚合层对各家产物的 schema 差异做适配。

编码 agent 的外部安全审查。 开发者侧编码 agent 把 diff 委托给安全公司的扫描 agent，异步等 webhook 通知取报告。关键设计点：报告以 Artifact 返回带结构化 Part；扫描 agent 内部用 MCP 接自己的漏洞库——纵向横向在同一任务里各就各位。

数据分析的外包可视化。 主分析 agent 完成数据处理后，把结果委托给可视化 agent 生成图表。关键设计点：产物用结构化 Part 传数据集引用而非内联大文本；双方对数据 schema 的共识在协议之外单独维护。

个人助理聚合多家服务。 个人助理 agent 凭用户授权发现并调用日程、邮件、账单等 SaaS 的官方 agent。关键设计点：每家服务的授权范围独立管理；调用留痕满足用户侧审计（见 15.5.5）。

真实世界实例

Google Cloud 发布 A2A：50 余家首发伙伴的行业共识。 2025 年 4 月 9 日，Google 在 Cloud Next 大会发布 Agent2Agent 协议，Atlassian、Box、Cohere、Intuit、LangChain、MongoDB、PayPal、Salesforce、SAP、ServiceNow、Workday 等 50 余家技术与服务商作为创始伙伴共同背书——协议要解决的正是"跨厂商、跨框架的 agent 无法互相委派任务"这一企业级痛点。见 Google Cloud 官方博客。

捐入 Linux Foundation：从厂商协议到中立标准。 2025 年 6 月 23 日，Google 在 Open Source Summit NA 宣布把 A2A 规范、SDK 与开发者工具全部捐给 Linux Foundation，AWS、Cisco、Google、Microsoft、Salesforce、SAP、ServiceNow 共同担任创始成员——单一厂商的协议从此变成供应商中立的开放标准，这直接回答了"凭什么信任这张名片体系"的治理问题。见 Linux Foundation 官方公告。

LangChain 生态接入：LangGraph agent 的一行暴露。 LangChain 是 A2A 首发合作伙伴，其 LangGraph 编排的 agent 可经官方 a2a-samples 仓库中的 LangGraph 示例暴露为 A2A 服务端（名片 + 状态机），被任何框架的客户端发现与调用；Google ADK 也提供对称能力（to_a2a 导出、RemoteA2aAgent 消费外部名片，见 15.6.2）——"框架自由、协议握手"从口号变成了两行配置。见 LangGraph 官方文档。

15.5 深度讲解

15.5.1 为什么不能直接用 MCP 连 agent

最常见的架构问题是："MCP 已经连了工具，把对方 agent 包成一个 MCP tool 不就行了？"不行，根因是抽象层级的错配。MCP 的原语是 tools/resources/prompts，语义是"被动的资源与函数"：调用即执行、返回即完成。而 agent 是自治方，这个差异在四个方面撞墙。调用语义装不下生命周期：MCP tool call 是同步的请求-响应，没有 submitted→working→completed 的中间状态，无法表达"跑十分钟""中途挂起""被取消"；硬要模拟只能超时返回"还在跑"，然后自己发明轮询协议——等于在 MCP 之上重新发明半个 A2A。能力发现装不下多轮：工具描述是一段静态文本，够模型决定"调不调"；但 agent 协作常常需要追问与澄清（input-required），工具的输入 schema 表达不了"我可以追加问题给你"。没有产物概念：函数返回值即时即弃，长任务的核心资产是挂在任务上的 artifacts，可查询、可追溯。身份不对等：MCP server 是被调用方，按客户端的请求办事；agent 是对等体，可以拒绝（rejected）、要求授权（auth-required）、按自己的策略决定怎么做——把自治方压平成工具，既得不到它的判断力，也管不住它的自由度。类比：MCP 是 USB，插上就用，主从关系固定；A2A 是工单系统加邮件，双方各自独立、按剧本协作。正确的组合姿势是每个 A2A agent 内部用 MCP 接工具（纵向），对外用 A2A 接同行（横向）——官方分工"MCP 装备 agent，A2A 连接 agent"说的就是这个。

15.5.2 能力发现：Agent Card 与中心注册表

A2A 的发现机制刻意走了 Web 的去中心化传统：约定路径（well-known URI）+ 自述文档，像 robots.txt 与 sitemap。好处是零基础设施——一个 agent 上线，把名片文件放到约定路径就完成了全部"注册"；坏处是"谁在找 agent"没有答案：名片解决"找到后知道你能干嘛"，不解决"我根本不知道你存在"。企业场景因此长出第二层：注册表（registry）——组织内维护一份可信 agent 目录（含内部与经过审批的外部 agent），客户端先查目录再取名片。两层分工明确：注册表管"有哪些、可不可信"，名片管"怎么调、能干嘛"。工程上还有三个细节值得注意。其一，名片是自述，"说自己会什么"与"做得好不好"之间没有协议背书——技能描述的质量直接影响被选中的概率，写法上与第 5 章的工具描述纪律相同（动词开头、写清适用与不适用场景）。其二，v0.3 起名片支持签名（JWS），客户端可验证名片未被篡改、确系署名方发布——公网场景应优先消费签名卡。其三，名片可按认证状态区分公开与完整版本：公开卡只露最小信息，认证后才返回完整技能清单。

15.5.3 任务状态机与长任务：把"等待"做成协议原语

Task 状态机是 A2A 最有工程价值的部分，值得逐状态拆解。submitted 到 working 是受理确认；working 到 input-required 是最有设计意味的一跳——远端声明"我需要更多信息才能继续"，任务原地挂起，不占远端资源，等待可以是几秒也可以是几天（等人类上班）。客户端收到 input-required 后，把补充信息作为新消息发往同一 task，状态回到 working 续跑——第 13 章的人工闸门在跨组织场景里被协议化了：挂起的裁决者可能是远端 agent 的用户、客户端的用户或双方的人。终态三个：completed（有产物）、failed（有失败原因）、canceled（客户端取消或超时）。状态转移的合法性由服务端保证，客户端按状态驱动自己的逻辑（轮询到终态才聚合产物）。

长任务的感知方式有三档，按任务时长与交互性选择。同步等待：几秒内完成的任务，message/send 直接等终态。SSE 流式（message/stream）：交互式任务与进度可见性需求，增量接收状态更新与产物片段，断线后可重订阅续读。Webhook 推送：小时级长任务，客户端注册回调地址后即可释放连接，远端状态变化时主动 POST 通知——这是"挂起不占资源"的最后一环。三档的选择标准是"谁扛等待成本"：短任务客户端扛，长任务网络扛不了就用推送。工程提醒：任务 ID 是跨组织的关联键，所有日志都应带上它；重试与超时策略挂在任务状态而非连接上——连接会断，任务不会。

15.5.4 跨框架互操作：协议之下的框架自由

A2A 承诺"跨框架互调"，机制上其实很朴素：客户端依赖的只有两样——名片 JSON schema 和消息信封格式。远端 agent 内部是 LangGraph、ADK、CrewAI 还是手写 Python，协议层完全不可见。第 15.6.1 节的模拟代码正说明了这一点：ResearchExecutor.run() 的位置可以塞进任何框架的执行器，A2AServer 的路由与状态机纹丝不动。真实的跨框架调用（例如 LangGraph 编排器调 ADK agent）因此只是一个装配问题：LangGraph 侧写一个调用远端名片的 A2A 客户端节点，ADK 侧用官方 to_a2a 工具把 agent 暴露成 A2A 服务端（ADK 也提供 RemoteA2aAgent 把外部名片包装成子 agent，见 15.6.2）。

互操作的真实边界不在协议层，而在语义层：协议规定的 Part 只有文本/文件/结构化数据三种形态，业务 schema 协议不管。两个 agent 约定产物里 data 部分的字段含义，靠的是双方私下的接口约定（或行业共同体制定的 profile）。这是自由度也是坑：文本 Part 万能但脆弱（LLM 靠理解力兜底），结构化 Part 高效但要求版本化的 schema 治理。工程建议：对外技能的产物尽量文本优先（跨组织边界上，自然语言是唯一有兜底语义的格式），结构化 Part 留给已建立 schema 契约的伙伴之间，并在名片或文档里声明数据格式版本。

15.5.5 信任与认证边界

跨组织的 agent 调用引入了全新的信任问题面。认证方面，协议不发明新机制：企业内用服务账号与 mTLS，组织间用 OAuth2 客户端凭证或 API key，名片的安全方案字段声明"我接受哪些认证方式"，客户端按自己能提供的凭证选择端点。授权的关键原则是最小技能暴露：对外名片只列你愿意被外部调用的技能，内部技能不进公开卡。信任链上最容易被忽视的一环是输出即输入：远端 agent 返回的 artifact 与 history 对本地调用方而言是不可信输入——它是另一个组织的 LLM 产物，可能包含提示注入载荷。调用方把远端产物拼进自己的上下文之前，必须过与处理用户输入同级的防线（第 5 章的幻觉调用防线、内容过滤），绝不能因为"这是 agent 不是人"就放松。审计方面，跨组织调用的对账依赖三件套：task_id 关联全链、消息历史留存、认证身份与任务绑定——出问题时能回答"哪个身份、哪个任务、谁给的产物"。最后是恶意名片的风险：名片可以撒谎（夸大技能、隐藏限制），公网消费名片前应经注册表或人工审批，签名卡只解决"没被篡改"，不解决"本身是假的"。

15.5.6 何时不用 A2A

协议再好也是成本，三种情况不该上。同进程同框架：第 7 章的多智能体编排，直接用框架原生 sub-agent 机制——同内存传递、类型紧耦合、零序列化，A2A 的网络跳与信封解析纯属浪费。组织内但框架不统一：优先评估企业内部的 agent 网关/目录方案，A2A 的开放治理与公网语义在企业内未必是加分项；不过当组织内团队边界已经"像外部"（各自部署、独立发布节奏）时，A2A 反而是诚实的选择——把团队边界当网络边界设计。纯工具调用：对方是资源不是自治方，用 MCP。判断的尺子一句话：A2A 解决的是组织边界——出现了"对方的部署、发布、模型、权限都不归你管"这一事实，才需要名片与状态机；没有这条边界，就用更轻的机制。

15.6 工程落地：实践代码示例

15.6.1 框架无关实现（完整可运行）

下面的实现用两个"假 agent"完整模拟 A2A 的协议形状：Agent Card 发现、表驱动的 Task 状态机（非法转移直接拒绝）、Message/Part/Artifact 信封、input-required 挂起与跟进恢复、JSON-RPC 风格错误、任务取消与查询。纯标准库，HTTP 层用进程内 handler 模拟——真实部署把 handle() 换成 HTTP 服务端即可，协议骨架不变。

"""第 15 章 框架无关实现：两个"假 agent"之间的 A2A 风格消息协议模拟。

纯标准库、不依赖真实网络：HTTP 层用进程内 handler 模拟（handle(request)->response），
协议形状与真实 A2A 一致——Agent Card 发现、Task 状态机、Message/Part/Artifact 信封、
input-required 挂起与恢复、JSON-RPC 风格错误。字段命名对齐 A2A v0.3 规范
（状态值为小写连字符；v1.0 起改为 SCREAMING_SNAKE_CASE，工程上以所用 SDK 为准）。
"""
from __future__ import annotations

import uuid
from dataclasses import dataclass, field
from datetime import datetime, timezone


def now() -> str:
    return datetime.now(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")


# ---------- Task 状态机：转移合法性由表驱动，非法转移直接拒绝 ----------

VALID_TRANSITIONS: dict[str, set[str]] = {
    "submitted": {"working", "canceled"},
    "working": {"input-required", "completed", "failed", "canceled"},
    "input-required": {"working", "canceled"},
    "completed": set(), "failed": set(), "canceled": set(),  # 终态
}


@dataclass
class Part:
    """消息/产物的最小内容单元：文本或结构化数据。"""

    kind: str            # "text" | "data"
    text: str = ""
    data: dict | None = None


@dataclass
class Message:
    """一条消息：role 为 "user"（客户端侧）或 "agent"（服务侧）。"""

    role: str
    parts: list[Part]

    @classmethod
    def text(cls, role: str, content: str) -> "Message":
        return cls(role=role, parts=[Part(kind="text", text=content)])


@dataclass
class Artifact:
    """任务的最终产物。"""

    name: str
    parts: list[Part]


@dataclass
class Task:
    """协作的基本单元：有生命周期、有历史、有产物。"""

    task_id: str
    state: str = "submitted"
    history: list[Message] = field(default_factory=list)
    artifacts: list[Artifact] = field(default_factory=list)
    updated_at: str = now()

    def transition(self, new_state: str) -> None:
        if new_state not in VALID_TRANSITIONS[self.state]:
            raise ValueError(f"非法状态转移：{self.state} -> {new_state}")
        self.state = new_state
        self.updated_at = now()

    def to_dict(self) -> dict:
        return {
            "taskId": self.task_id,
            "status": {"state": self.state, "timestamp": self.updated_at},
            "artifacts": [{"name": a.name,
                           "parts": [{"kind": p.kind, "text": p.text} for p in a.parts]}
                          for a in self.artifacts],
            "history": [{"role": m.role,
                         "parts": [{"kind": p.kind, "text": p.text} for p in m.parts]}
                        for m in self.history],
        }


# ---------- Agent Card：能力自描述文档 ----------

@dataclass
class Skill:
    """agent 声明自己会做什么：客户端按 skill 匹配任务。"""

    skill_id: str
    name: str
    description: str


@dataclass
class AgentCard:
    """A2A 的"名片"：真实部署发布在 /.well-known/agent-card.json（v0.3 起路径）。"""

    name: str
    description: str
    url: str
    version: str
    skills: list[Skill]
    capabilities: dict = field(
        default_factory=lambda: {"streaming": False, "pushNotifications": False})
    default_input_modes: list[str] = field(default_factory=lambda: ["text/plain"])
    default_output_modes: list[str] = field(default_factory=lambda: ["text/plain"])

    def to_dict(self) -> dict:
        return {
            "name": self.name, "description": self.description,
            "url": self.url, "version": self.version,
            "capabilities": self.capabilities,
            "defaultInputModes": self.default_input_modes,
            "defaultOutputModes": self.default_output_modes,
            "skills": [{"id": s.skill_id, "name": s.name,
                        "description": s.description} for s in self.skills],
        }


class NeedInput(Exception):
    """executor 需要更多信息：触发 input-required 挂起，等客户端补充后再恢复。"""

    def __init__(self, question: str) -> None:
        super().__init__(question)
        self.question = question


# ---------- 远端 agent（服务侧）：自己的逻辑、自己的"内政" ----------

class ResearchExecutor:
    """调研 agent 的执行器：假 LLM（确定性回复），真实实现里这里跑你自己的框架。"""

    def run(self, task: Task) -> str:
        text = " ".join(p.text for m in task.history if m.role == "user" for p in m.parts)
        if "主题：" not in text:
            raise NeedInput("请按「主题：<内容>；范围：<时间/边界>」给出调研要求")
        topic = text.split("主题：")[1].split("；")[0]
        return (f"调研完成：围绕「{topic}」检索了 6 个来源，"
                "核心结论已整理为要点清单（模拟产物）。")


class A2AServer:
    """进程内模拟的 A2A 服务端：一张卡 + 一个 executor + JSON-RPC 风格路由。"""

    CARD_PATH = "/.well-known/agent-card.json"

    def __init__(self, card: AgentCard, executor: ResearchExecutor) -> None:
        self.card = card
        self.executor = executor
        self.tasks: dict[str, Task] = {}

    def handle(self, request: dict) -> dict:
        """模拟 HTTP 入口：GET 卡片用 method="GET"+path；其余走 JSON-RPC method。"""
        rid = request.get("id", "req-0")
        if request.get("method") == "GET" and request.get("path") == self.CARD_PATH:
            return {"jsonrpc": "2.0", "id": rid, "result": self.card.to_dict()}
        method = request.get("method")
        params = request.get("params", {})
        try:
            if method == "message/send":
                return {"jsonrpc": "2.0", "id": rid, "result":
                        self._message_send(params).to_dict()}
            if method == "tasks/get":
                task = self.tasks[params["taskId"]]
                return {"jsonrpc": "2.0", "id": rid, "result": task.to_dict()}
            if method == "tasks/cancel":
                task = self.tasks[params["taskId"]]
                task.transition("canceled")
                return {"jsonrpc": "2.0", "id": rid, "result": task.to_dict()}
            return {"jsonrpc": "2.0", "id": rid,
                    "error": {"code": -32601, "message": f"Method not found: {method}"}}
        except KeyError as exc:
            return {"jsonrpc": "2.0", "id": rid,
                    "error": {"code": -32602, "message": f"Invalid params: {exc}"}}

    def _message_send(self, params: dict) -> Task:
        msg = Message(role="user",
                      parts=[Part(**p) for p in params["message"]["parts"]])
        task = self.tasks.get(params.get("taskId") or "")
        if task is None:
            task = Task(task_id=f"task-{uuid.uuid4().hex[:8]}")
            self.tasks[task.task_id] = task
            task.transition("working")
        else:  # input-required 的跟进消息：恢复为 working 继续跑
            task.transition("working")
        task.history.append(msg)
        try:
            result_text = self.executor.run(task)
            task.artifacts.append(Artifact("research-report",
                                           [Part(kind="text", text=result_text)]))
            task.transition("completed")
        except NeedInput as exc:
            task.history.append(Message.text("agent", exc.question))
            task.transition("input-required")   # 挂起：等客户端（或人）补充
        return task


# ---------- 客户端 agent（编排侧）：发现 -> 匹配技能 -> 委托 ----------

class ClientAgent:
    """客户端只认协议：先取卡发现能力，再按 skill 挑 agent，然后委托任务。
    它不知道、也不需要知道远端用什么框架、什么模型。"""

    def __init__(self, name: str, server: A2AServer) -> None:
        self.name = name
        self.server = server  # 真实部署中持有的是 Agent Card 里的 url，此处直连模拟层

    def discover(self) -> AgentCard:
        resp = self.server.handle({"id": "d1", "method": "GET",
                                   "path": A2AServer.CARD_PATH})
        card = resp["result"]
        print(f"  [发现] {card['name']} v{card['version']}：{card['description']}")
        print(f"  [技能] {[(s['id'], s['name']) for s in card['skills']]}")
        return card

    def delegate(self, text: str, followup: str | None = None) -> Task:
        resp = self.server.handle({
            "id": f"req-{uuid.uuid4().hex[:6]}", "method": "message/send",
            "params": {"message": {"role": "user",
                                   "parts": [{"kind": "text", "text": text}]}}})
        task = Task(task_id=resp["result"]["taskId"])
        task.state = resp["result"]["status"]["state"]
        print(f"  [委托] {text[:30]}... -> 状态 {task.state}")
        if task.state == "input-required":  # 挂起了：读远端的问题，补一个跟进消息恢复
            question = next(p["text"] for m in reversed(resp["result"]["history"])
                            if m["role"] == "agent" for p in m["parts"])
            print(f"  [挂起] 远端要求补充：{question}")
            resp = self.server.handle({
                "id": f"req-{uuid.uuid4().hex[:6]}", "method": "message/send",
                "params": {"taskId": task.task_id,
                           "message": {"role": "user",
                                       "parts": [{"kind": "text", "text": followup or ""}]}}})
            task.state = resp["result"]["status"]["state"]
            print(f"  [恢复] 补充信息后 -> {task.state}")
        for a in resp["result"].get("artifacts", []):
            print(f"  [产物] {a['name']} :: {a['parts'][0]['text'][:40]}...")
        return task


if __name__ == "__main__":
    server = A2AServer(
        card=AgentCard(
            name="research-agent", version="0.3.0",
            description="文献与网络调研 agent（模拟）",
            url="http://127.0.0.1:0",  # 模拟层无真实监听
            skills=[Skill("deep-research", "深度调研",
                          "给定主题与范围，产出带来源的要点清单")],
        ),
        executor=ResearchExecutor(),
    )
    client = ClientAgent("orchestrator", server)

    print("== 场景 1：能力发现 ==")
    client.discover()

    print("\n== 场景 2：需求完整，一路到 completed ==")
    client.delegate("主题：A2A 与 MCP 的分工；范围：近一年")

    print("\n== 场景 3：信息不足 -> input-required 挂起 -> 补充后恢复 ==")
    client.delegate("帮我调研一下", followup="主题：A2A 任务状态机；范围：v0.3 规范")

    print("\n== 场景 4：错误路径——未知方法与任务取消 ==")
    err = server.handle({"id": "e1", "method": "message/teleport", "params": {}})
    print(f"  [错误] {err['error']}")
    r = server.handle({"id": "e2", "method": "message/send", "params": {
        "message": {"role": "user", "parts": [{"kind": "text", "text": "帮我调研一下"}]}}})
    tid = r["result"]["taskId"]
    r2 = server.handle({"id": "e3", "method": "tasks/cancel", "params": {"taskId": tid}})
    print(f"  [取消] 任务 {tid} -> {r2['result']['status']['state']}")
    r3 = server.handle({"id": "e4", "method": "tasks/get", "params": {"taskId": tid}})
    print(f"  [查询] tasks/get 复核终态：{r3['result']['status']['state']}（终态不可再转移）")

15.6.2 框架集成实现（Google ADK：本地转交 + 远端 A2A 互调）

Google ADK 把两种协作方式放进同一个模型：本地子 agent 用框架原生的 agent transfer（根 agent 的 LLM 决定何时转交），外部 agent 用 RemoteA2aAgent 包装一张 Agent Card 地址——两者对根 agent 都是 sub_agents 列表里的普通成员。在 google-adk==2.12.0、a2a-sdk==1.2.3 实测构造与接线（对话运行需另配模型密钥）；注意 ADK 的 A2A 集成组件目前标注为实验性（库内警告），协议与官方 SDK 本身稳定。

"""Google ADK 集成：本地子 agent 委托 + RemoteA2aAgent 跨框架互调。
google-adk==2.12.0、a2a-sdk==1.2.3 实测构造与接线（对话运行需另配模型密钥）。

依赖：pip install google-adk a2a-sdk
"""
from __future__ import annotations

from google.adk.agents import LlmAgent
from google.adk.agents.remote_a2a_agent import RemoteA2aAgent

# 本地子 agent：ADK 的 agent transfer 由根 agent 的 LLM 决定何时转交
researcher = LlmAgent(
    name="researcher",
    model="gemini-2.5-flash",
    description="文献与网络调研 agent，负责收集带来源的要点",
    instruction="你是调研员。只输出带来源的要点清单，每条标注出处。",
)

# 远端 agent：对方团队自己框架实现的调研 agent，本方只依赖它的 Agent Card
# （A2A 的核心承诺：跨框架、跨厂商互调，远端用什么 LLM 是它的内政）
external_researcher = RemoteA2aAgent(
    name="external_researcher",
    description="外部团队的调研 agent（跨框架，经 A2A 协议调用）",
    agent_card="http://research.internal:8080/.well-known/agent-card.json",
)

coordinator = LlmAgent(
    name="coordinator",
    model="gemini-2.5-flash",
    description="总控 agent：调研类请求按内外分工转交，其他自行回答",
    instruction=(
        "你是总控 agent。文献类调研转交 researcher；"
        "需要外部团队知识库的调研转交 external_researcher；其余问题自行回答。"
    ),
    sub_agents=[researcher, external_researcher],
)

if __name__ == "__main__":
    print("本地接线：", coordinator.name, "->", [a.name for a in coordinator.sub_agents])
    print("远端名片地址：http://research.internal:8080/.well-known/agent-card.json")
    # 运行对话：配好模型密钥后用 Runner（或 adk web）发起，例如
    #   Runner(agent=coordinator, app_name="demo").run_async(...)
    # 也可 `adk web` 打开调试界面，输入调研类请求观察转交行为。

服务端侧的对称操作是把自家 agent 暴露成 A2A 服务端：ADK 官方提供 google.adk.a2a.utils.agent_to_a2a 把 LlmAgent 连同自动生成的 Agent Card 一起包装为可部署的 A2A 应用（依赖同一套 a2a-sdk；具体参数以所用版本的官方文档为准——SDK 迭代较快，此处不落伪代码细节）。

15.6.3 生产化改造清单

  • 错误处理：远端 failed/canceled 是一等结果，调用方必须处理三种终态分支；网络中断不等于任务失败，用 tasks/get 核实后再决定重试。
  • 超时与取消：按技能设任务级超时；超时走 tasks/cancel 而非直接弃单——远端可能在继续消耗资源。
  • 长任务感知：短任务同步、交互任务 SSE、小时级任务 webhook；webhook 回调端点要验签与幂等（推送可能重复到达）。
  • 认证与授权：凭证按远端 agent 单独管理，最小技能暴露；公网消费名片优先选签名卡并走注册表审批。
  • 输出防线：远端 artifact/history 进本地上下文前过注入过滤，与用户输入同级别对待。
  • 可观测：task_id 串联全链日志；状态转移时延（submitted→working、input-required 停留时长）做成指标，升级率与取消率告警。
  • 版本兼容：名片带版本号，客户端按协议版本分支处理（v0.3 与 v1.0 的字段命名不兼容）；SDK 升级先跑 TCK（官方兼容性测试套件）。
  • 成本控制：轮询间隔随任务时长指数放宽；流式订阅断线要重订阅而非重发任务（重发等于从头计费）。

15.7 概览 / 核心要点 / 结论

本章小结

A2A 把 agent 之间的连接从点对点定制变成了开放协议：名片解决发现，信封解决通信，状态机解决长任务与挂起，Web 安全体系解决认证。它与 MCP 的分工清晰——MCP 纵向装备 agent、A2A 横向连接 agent——两者合起来，agent 才同时拥有了"自己的手"和"可以求助的同行"。协议设计上最深的启示来自它的克制：KQML 时代把语义塞进协议失败了，A2A 把语义留给端到端的模型，只做传输与生命周期——三十年的探索证明，模型足够聪明之后，协议只需诚实。

核心要点

  • A2A 连 agent 与 agent，MCP 连 agent 与工具/数据，纵向横向互补而非竞争；一个 A2A 节点内部照常用 MCP。
  • 不能把对方 agent 包成 MCP tool：调用语义装不下任务生命周期、多轮澄清、产物与身份对等。
  • Agent Card 是自述名片（v0.3 起在 /.well-known/agent-card.json），解决"找到后知道你能干嘛"；"有哪些 agent"靠注册表补齐。
  • Task 状态机是协议的价值核心：input-required 把跨组织的挂起等待（含等人类）做成一等状态。
  • 长任务三档感知：同步等、SSE 流式、webhook 推送，按"谁扛等待成本"选择；断线重订阅不重发任务。
  • 跨框架互操作只依赖名片 schema 与信封格式；真正的边界在业务 schema——文本 Part 万能，结构化 Part 需要契约。
  • 远端产物是不可信输入，进本地上下文前要过注入防线；跨组织审计靠 task_id + 消息历史 + 认证身份三件套。

结论

智能体间通信的三十年的确走了一段弯路：上世纪九十年代的通信语言把太多智能塞进了协议，重到没人用得起；A2A 把协议减到只剩发现、信封与状态机，把理解交还给模型，反而第一次让跨组织协作有了落地的生态。对工程师而言，真正要掌握的不是协议细节——那些会随版本漂移——而是边界判断：什么时候该把一个 agent 当工具（MCP），什么时候当同行（A2A），什么时候当同事（框架内编排）。边界画对，协议各归其位；边界画错，再好的协议也救不了错误的架构。
