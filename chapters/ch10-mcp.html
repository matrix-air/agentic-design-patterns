第二部分 · 认知机制

第10章 模型上下文协议 Model Context Protocol (MCP)

MCP 用一个开放协议把"模型应用×工具数据源"的 M×N 集成爆炸压成 M+N，是智能体工具生态的事实标准接口层。

一句话定义：MCP 是一个开放协议，用统一的服务器接口把工具、数据和提示模板暴露给任意 AI 应用，让"每个应用对接每个数据源"的 M×N 集成退化为"每个应用实现一次协议 + 每个数据源实现一次协议"的 M+N。 解决什么问题：模型应用与外部工具/数据源之间两两定制集成，重复造轮子且无法复用 ｜ 适用场景：智能体工具接入、企业数据连接、跨应用能力复用 ｜ 核心机制：宿主内嵌客户端，与若干服务器以 JSON-RPC 2.0 通信，协商能力、动态发现工具、受控调用 ｜ 代价：多一层进程间/网络协议开销，安全边界和工具语义质量成为新的治理负担。

本章速读　MCP 用一个开放协议把"应用×数据源"的 M×N 集成压成 M+N：宿主内嵌客户端，与各服务器以 JSON-RPC 2.0 通信，初始化协商、动态发现、受控调用。三步落地：选传输（本地 stdio／远程 Streamable HTTP）→ 把能力封装成工具（描述当 prompt 写）→ 套上 OAuth、超时与审计。记住：集成成本从乘法变加法，治理成本一项不少。何时别用：单应用少量函数、不存在多宿主复用需求——协议反而是负资产。

10.1 模式概述

10.1.1 问题背景：为什么需要这个模式

在 MCP 出现之前，给大模型接外部能力是一件"纯手工活"。每个 AI 应用（聊天客户端、IDE 插件、自动化平台）都要为每个想接入的数据源或工具写一份定制胶水代码：定义自己的工具 schema、处理鉴权、解析返回、管理进程或连接。反过来，GitHub、Slack、Postgres、文件系统这类"大家都想接"的数据源，也被 N 个应用各包了一遍。假如有 M 个应用和 N 个数据源，最坏情况下要写 M×N 份集成代码。这就是集成爆炸：每新增一个应用，成本乘以 N；每新增一个数据源，成本乘以 M。

更深一层的问题是语义不统一。同样是"搜索代码库"，A 应用的参数叫 repo，B 应用叫 repository；同一个数据库工具，在不同宿主里鉴权方式完全不同。工具的元数据（只读还是破坏性？超时多久？失败怎么报告？）没有任何约定；工具描述质量参差不齐，直接决定智能体能不能把工具用对。

这个困境并不新鲜。编辑器行业在 2016 年就遇到过同构问题：M 个编辑器想支持 N 种编程语言，语言支持（补全、跳转、诊断）各自实现一遍，复杂度同样是 M×N。微软给出的解法是语言服务器协议（Language Server Protocol, LSP）：语言支持只实现一次成为语言服务器，编辑器只需实现一次协议客户端，M×N 就塌缩成了 M+N。LSP 的成功证明了一件事——当"能力提供方"与"能力消费方"都能接受一个中间协议时，生态会自发地向协议收敛。MCP 就是把这套思路搬到了大模型应用生态。

10.1.2 核心机制：它如何工作

MCP 于 2024 年 11 月 25 日由 Anthropic 开源发布（同时开放规范与 Python/TypeScript SDK），官方给它的定位是一句类比——"AI 应用的 USB-C"：一个标准插口，任何设备插上来就能工作。

架构上，MCP 采用宿主-客户端-服务器三层结构。宿主（host）是用户直接使用的 AI 应用（桌面聊天客户端、IDE、智能体框架），内部为每个 MCP 服务器维护一个客户端（client）实例负责协议通信；服务器（server）是独立的轻量进程或服务，把某类能力（读数据库、查工单、操作浏览器）按协议暴露。宿主与服务器之间的一切消息都是 JSON-RPC 2.0 报文，传输有两种：本地 stdio（标准输入输出管道），远程 Streamable HTTP。

协议能力围绕三对原语组织。服务端三类能力：Tools（模型可调用的函数，如"查询订单"）、Resources（可供读取的上下文数据，如文件、数据库行，用 URI 标识）、Prompts（预置的提示模板）。客户端三类能力：Sampling（服务器反过来请求宿主侧的 LLM 完成一次推理，结构上是一次"反转"）、Roots（宿主告知服务器允许操作的文件系统边界）、Elicitation（服务器在执行中向用户请求补充输入，用于确认与人机协同）。一次完整的会话经历生命周期三步：初始化（版本与能力协商）→ 发现（宿主调用 tools/list 等拿到能力清单）→ 使用（tools/call、resources/read 等）。发现是动态的：服务器更新后，宿主可以重新拉取工具列表，模型看到的能力集随之变化——这是 MCP 与编译期固定集成的本质区别。协议官网与各版本规范统一入口见 modelcontextprotocol.io。整体架构可概括为下图。

10.1.3 与相邻模式的关系与组合

MCP 与工具调用/函数调用（function calling）最容易被混为一谈，但两者处在不同层次：function calling 是模型与推理服务之间的接口约定，回答"模型如何表达'我想调一个函数'"；MCP 是宿主应用与工具提供方之间的协议约定，回答"这些函数从哪来、怎么发现、怎么鉴权、怎么安全地执行"。MCP 定义的工具最终仍要转换成模型上下文里的 function calling schema 才能被模型"看见"。二者是互补的上下层，本书第 3 章讨论的工具使用模式讲的是上层语义，MCP 讲的是接入层标准化。

与智能体间协作协议（A2A，Agent2Agent）的分工同样清晰：MCP 解决"智能体↔工具/数据"的纵向连接，A2A 解决"智能体↔智能体"的横向协作。Google 于 2025 年 4 月 9 日发布的 A2A 协议在官方博客中明确把自己定位为"MCP 的补充而非竞争"；此后 A2A 也进入 Linux 基金会中立治理，与 MCP 同属一个开源生态。实践中常见组合是：一个库存智能体用 MCP 读数据库，发现缺货后通过 A2A 委托采购智能体下单。

与其他模式的组合：MCP 为路由提供动态能力清单，为多智能体协作提供统一工具层；第 12 章的超时、重试、熔断策略落在 MCP 客户端的调用路径上；而工具调用 trace 又是第 11 章监控模式最重要的信号源之一。

10.3 发挥的作用：为什么重要

第一，它改写了智能体工具层的经济学。M×N 塌缩为 M+N 之后，工具开发者只需实现一次服务器，就能被 Claude、Cursor、VS Code、ChatGPT 等所有支持 MCP 的宿主使用；应用开发者只需实现一次客户端，就能接入整个服务器生态。Anthropic 在捐赠公告中给出的量级是：一年内活跃公开 MCP 服务器超过一万个，Python 与 TypeScript SDK 月下载量合计超过九千七百万——接入越多、生态越大、新接入的边际成本越低的正反馈已经成形。

第二，它把"能力发现"变成运行时行为而非编译期决策。智能体可在启动甚至运行中枚举工具，为动态场景（权限变化、新数据源上线、按任务裁剪工具集）提供抓手，也催生了工具检索技术——Anthropic 2025 年推出的 Tool Search 与程序化工具调用，正是为工具数量膨胀到成百上千时控制上下文开销而生。

第三，它给安全治理提供了抓手。协议显式定义了信任边界（服务器不可信、令牌不得透传、用户确认必须真实发生），让"权限最小化""破坏性操作人工确认"落到协议字段与客户端策略上，而非散落在各家胶水代码里——智能体安全从倡议变成可实现的工程检查单。

10.4 实际应用与案例

编码助手连接开发环境。Claude Code、Cursor、VS Code 等编码工具通过 MCP 连接文件系统、Git、终端、数据库。关键设计点：用 Roots 限定服务器可操作目录，破坏性命令（删除、force push）走客户端确认或工具注解过滤，本地 stdio 传输避免代码资产出内网。

企业知识库统一检索。把 Confluence、飞书文档、内部 Wiki 各自封装为一个 MCP 服务器，向上暴露同构的 search/read 工具，供客服、销售、研发等多个智能体复用。关键设计点：Tools 面向模型（可自由组合），Resources 面向宿主（可预取、可订阅），按消费方式选择原语；检索工具描述里写清适用场景，减少模型误选。

数据库问答与 BI 智能体。数据库以只读 MCP 服务器接入，提供 list_tables、read_query 等工具。关键设计点：服务器层面强制只读账号与 SQL 白名单校验，把"模型可能写出危险语句"这类语义风险挡在协议实现层；查询审计日志在服务器侧统一落盘。

浏览器自动化。Playwright 类 MCP 服务器把网页导航、点击、截图暴露为工具，智能体据此完成跨系统操作（如 ERP 录单）。关键设计点：会话状态（登录态、页面上下文）由服务器持有，宿主重启可重连；操作粒度要细（navigate/click/fill），"一键完成 X"式的粗粒度工具反而让模型失去纠错机会。

SaaS 连接器生态。Slack、Jira、GitHub、CRM 等服务由官方或社区提供 MCP 服务器，一次接入、全宿主可用。关键设计点：远程服务器走 Streamable HTTP + OAuth，用 RFC 8707 把每个服务的令牌绑定到该服务，防止令牌跨服务器挪用。

内部微服务网关。企业把内部 REST API 批量包装成 MCP 服务器，作为智能体的"标准工具市场"。关键设计点：服务器归类为 OAuth 资源服务器并发布受保护资源元数据（RFC 9728），网关层做租户隔离与速率限制；工具描述即文档，必须随 API 版本一起评审。

真实世界实例

Anthropic Claude Desktop 与 Claude Code。2024 年 11 月 25 日 MCP 开源发布时，Claude Desktop 即内置本地 MCP 服务器支持，并同步放出 Google Drive、Slack、GitHub、Git、Postgres、Puppeteer 六个预构建服务器；公告同时点名 Block（其 CTO 称开放协议是"连接 AI 与现实世界应用的桥梁"）与 Apollo 为已集成方，Zed、Replit、Codeium、Sourcegraph 为接入中的开发工具厂商——"编码助手连接开发环境"场景由此定型。来源：Anthropic 官方公告。

OpenAI Agents SDK。2025 年 3 月 OpenAI 宣布 Agents SDK 正式支持 MCP：本地 stdio 服务器与远程服务器都可用 mcp_servers 参数挂到任意 Agent 上，SDK 自动完成工具发现、调用与结果回传，Responses API 此后又加入托管式 MCP 工具与逐工具审批流——竞对主导的协议被竞对官方采纳，是 MCP 跨厂商标准化的标志性事件。来源：OpenAI Agents SDK MCP 文档。

Cursor 与开发工具宿主阵营。Cursor 在设置中以统一入口添加、管理 MCP 服务器，让编码智能体在 IDE 内动态接入数据库、文档与内部 API，是使用最广泛的 MCP 宿主之一；Anthropic 在 2025 年 12 月的捐赠公告中把 Cursor 与 ChatGPT、Gemini、Microsoft Copilot、VS Code 并列为已采用 MCP 的代表产品。来源：Cursor MCP 文档、Anthropic 捐赠公告。

10.5 深度讲解

10.5.1 M×N→M+N：这笔账到底省在哪，又不省在哪

把集成成本写成公式最容易看清 MCP 的价值边界。设 M 个宿主、N 个数据源，传统模式的成本是 M×N 份"鉴权+schema+解析+运维"胶水代码；MCP 模式下是 M 份客户端实现加 N 份服务器实现。当 M、N 都大于 2 时，M+N 严格小于 M×N，且差距随规模拉大。LSP 时代这笔账已经算过一遍，结论照旧成立。

但有一个常被忽略的限定：MCP 只统一接口形状，不统一语义与运营成本。三个成本项并不随协议消失。其一，鉴权与合规仍按 N 份发生——接 GitHub 还是要配它的 OAuth 应用，接数据库还是要管账号密码，MCP 只标准化了"令牌如何安全递达工具"的传输环节。其二，语义质量仍按 N 份投入——工具描述写得含糊，模型照样选错；schema 设计得别扭，模型照样传错参。协议无法代替工具设计。其三，运维仍按 N 份发生——一万个服务器意味着一万个供应链信任决策：谁发布的？更新后会不会引入恶意行为？所以对 M+N 的准确理解是：集成开发成本从乘法变加法，而治理成本线性于 M 与 N，一项都没有少。把 MCP 当成"接了就完事"的银弹，是这一模式最常见的认知偏差。

10.5.2 协议解剖：JSON-RPC 之上，三对原语的分工逻辑

MCP 的全部报文都是 JSON-RPC 2.0：请求-响应用于同步语义（tools/call），通知用于单向事件（如工具列表变更）。选 JSON-RPC 而非 REST 或 gRPC 是刻意取舍：报文要在 stdio、HTTP 流等多种传输上同构，且对弱环境友好——一个脚本就能实现服务器。

理解三对原语的关键在于"它们分别为谁服务"。Tools 为模型的推理循环服务：工具由模型自主决定调用，结果回到模型继续推理，天然非确定性；因此 schema 要求高（参数名、类型、描述直接影响模型行为），2025-06-18 版又补上 structuredContent 与 outputSchema，让宿主能机器可验证地解析输出——规范刻意采用"软契约"：工具应当返回符合 schema 的结构化输出、客户端应当校验，但文本回退始终保留，模型输出的概率性被当作前提接受。Resources 为宿主的上下文管理服务：数据由应用逻辑决定何时读取（或由用户选择），URI 寻址、支持订阅，消费方是确定性代码而非模型。Prompts 为用户的交互服务：模板由用户显式选用。一个数据源三类原语都暴露时，分野是：模型要"用"的进 Tools，应用要"读"的进 Resources，人要"点"的进 Prompts。实践中最常见的错误是把一切都塞进 Tools，让模型每次对话都背着只需偶尔批量读取的资源清单，白白吃掉上下文。

客户端三原语则体现了协议的"反转"设计。Sampling 允许服务器请求宿主的 LLM 做一次推理——服务器本身可以没有模型，只在需要智能（如总结检索结果）时借用宿主能力；这把"MCP 服务器"从哑工具提升为可以内置小型智能体逻辑的单元，同时把模型选择权与成本留在宿主与用户手里。Roots 把文件系统边界从服务器单方面声明改为宿主授予。Elicitation（2025-06-18 引入）让服务器可以在执行中向用户请求结构化输入或确认——例如删除前请用户确认、缺失参数请用户补填。三者共同确立了一条原则：能力向下暴露，控制权向上收敛。服务器永远不比宿主更可信，任何越权动作必须经过宿主与用户的策略关卡。

10.5.3 与 function calling 的分层关系：一次调用要过两道翻译

一个常见误解是"用了 MCP 就不需要 function calling"。真实的调用链上两者缺一不可，一次完整的 MCP 工具调用要经历两道翻译。第一道在发现时：客户端执行 tools/list 拿到服务器的工具定义（名称、JSON Schema 参数、描述），宿主把它转换为模型推理服务认识的 function/tool 定义，注入系统上下文——这一步决定了模型"知道"有哪些能力。第二道在执行时：模型生成一次 function call（结构由推理服务的接口层定义），宿主把参数回填成 tools/call 的 JSON-RPC 请求发给对应 MCP 服务器，执行结果（content 块与 structuredContent）再翻译回工具消息角色送入下一轮模型推理——这一步决定了模型"看到"什么执行反馈。整个回路如下图所示。

flowchart LR M["大模型发出 function call"] --> H["宿主应用翻译"] H --> C["MCP 客户端 tools/call"] C --> S["MCP 服务器执行"] S --> R["结果翻译回 tool 消息"] R --> M
图 10-2：一次 MCP 工具调用的"两道翻译"——发现时工具定义翻译为 function calling schema，执行时模型调用翻译为 JSON-RPC 请求、结果再翻译回来。

这个分层视角解释了三个工程现象。第一，为什么 MCP 不会自动提升工具调用成功率：选工具、填参数由模型能力决定，MCP 只保证"工具定义无损到达模型、调用被执行"。第二，为什么同一个 MCP 服务器在不同宿主上的表现可能不同：不同宿主对工具描述的截断策略、对 schema 的兼容子集、对分页的处理各不相同。第三，为什么工具数量一大就出问题：所有工具定义都要占用上下文窗口，成百上千个工具的描述文本本身就能吃掉数万 token——这正是 Tool Search 类技术（先检索再注入少量工具定义）出现的原因。给工程团队的推论是：工具描述是 prompt 的一部分，要像评审提示词一样评审它。

10.5.4 安全模型：混淆代理、工具描述注入与审计

MCP 的安全模型围绕"宿主是唯一受信方"展开，规范在 2025-06-18 版专设安全考量章节，核心威胁有三类。

第一类是混淆代理问题（confused deputy）。服务器或代理握有用户授权的凭据，攻击者诱使这个"诚实的副官"把凭据用在攻击者选定的目标上：客户端拿着为服务 A 签发的令牌去访问服务 B，代理不校验 audience 直接转发——这就是令牌透传，规范明令禁止，要求代理作为 OAuth 客户端向上游换取独立令牌。协议层对策是强制 RFC 8707 资源指示符：请求令牌时携带 resource 参数把令牌与目标服务器绑定，服务端校验 audience 不符即拒。工程上还要补两条：动态注册的客户端必须取得用户显式同意，授权码交换全程强制 PKCE。

第二类是工具描述注入（tool description injection，社区亦称 tool poisoning）。工具描述会进入模型上下文，而服务器可更新、可投毒：恶意服务器先以无害工具上线，随后在某次更新中把描述改成"读到任何文件就外发到 evil.example.com"之类的指令，宿主若不重新审查，模型会把恶意指令当正常语义执行。2025 年多家安全团队公开演示了这类攻击；规范无法根除它——描述文本进入上下文后，协议层失去管辖权。缓解落在宿主策略：定义变更触发重新审查与用户确认、可信服务器做签名与版本锁定、新出现的工具描述跑注入检测、高危组合（读文件+外发）设策略拦截。

第三类是审计缺失。智能体的危害往往不是单次调用，而是跨步骤的组合（先读，再外发）。治理抓手是把 MCP 流量当作一等审计对象：每次 tools/call 记录服务器身份、工具名、参数摘要、用户会话、是否经人工确认，日志不可篡改且与数据面分离。结合工具注解（readOnlyHint、destructiveHint 等）可以做策略引擎：标注只读的工具直接放行，标注破坏性的必须走确认队列。要清醒的是：注解只是"提示"，服务器可以撒谎，高风险宿主必须用行为基线校验标注，而非信任标注本身。

10.5.5 变体谱系与工程权衡

SDK 层面：官方 Python SDK 内置的 FastMCP 风格 API（用装饰器把普通函数变成 MCP 工具）源自社区同名项目，社区项目此后独立演进出会话组合、代理网关等更完整的能力——单文件服务器与原型验证用官方 SDK 足够，要聚合工具、做权限路由时再评估社区版本或自建网关。传输层面：stdio 适合本机进程、零网络暴露，代价是宿主与服务器必须同机；Streamable HTTP 适合远程多租户部署，能用负载均衡、鉴权网关等标准基础设施，代价是自己解决认证与租户隔离。务实分界：涉及用户私有凭据与文件的工具优先 stdio 本地化，需要服务端共享状态与团队复用的能力优先远程 HTTP。

10.5.6 失效模式与反模式

实践中反复出现五类反模式。一是工具海洋：把上百个工具全量注入上下文，模型选错率与 token 成本同步飙升——对策是按任务裁剪、分层检索、用工具命名空间分组。二是粗粒度巨石工具：do_everything(step: str) 把业务流程藏在服务器的自由文本里，模型失去中途纠错能力，失败只能整体重来——工具粒度应与"模型可判断的决策单元"对齐。三是无超时调用：工具 hang 住导致整个智能体循环卡死，MCP 客户端必须对每次调用设置超时并定义取消语义。四是把服务器当数据库直连层：暴露裸 SQL 执行工具而不加白名单与只读约束，等于把注入风险从应用层搬到了模型层。五是忽略版本协商：初始化阶段不锁定协议版本，服务器升级后宿主行为悄然改变——生产环境应显式固定版本并在变更时走回归测试。

10.5.7 何时不要用 MCP

以下场景直接用更简单的方案更好：单应用自用的三五个内部函数，进程内注册加 function calling 即可；对延迟极敏感的内部调用路径，JSON-RPC 序列化与进程边界开销不可忽略；强 schema 契约的核心服务间通信（支付、订单），RPC 框架与 API 网关远比 MCP 成熟。判别标准一句话：当"多宿主复用"或"动态发现"是真实需求时才上 MCP，否则它是负资产。

10.6 工程落地：实践代码示例

10.6.1 框架无关实现（完整可运行）

最小 MCP 服务器，使用官方 Python SDK（PyPI 包名 mcp，本节代码在 1.28.1 版实测通过；安装：pip install "mcp[cli]"）。三个工具分别覆盖成功路径、业务失败路径与参数校验路径。

"""最小 MCP 服务器：三个工具演示成功、业务失败与参数校验路径。

运行方式（作为 stdio 服务器被宿主拉起）：
    python ch10_mcp_server.py
也可用官方调试器：
    mcp dev ch10_mcp_server.py
依赖：pip install "mcp[cli]"   # 在 mcp==1.28.1 上实测
"""
from typing import Any

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("demo-tools", instructions="演示用工具集：查询订单、退款、单位换算。")


@mcp.tool()
def get_order(order_id: str) -> dict[str, Any]:
    """按订单号查询订单状态。

    Args:
        order_id: 订单号，格式为 ORD-数字。
    """
    # 业务失败路径：不抛异常，而是返回结构化的"业务错误"，
    # 让模型能读到原因并决定下一步（重试/道歉/换参数）。
    if not order_id.startswith("ORD-"):
        return {"ok": False, "error": f"订单号格式非法: {order_id!r}，应为 ORD-<数字>"}
    if order_id == "ORD-404":
        return {"ok": False, "error": "订单不存在，请确认订单号"}
    return {"ok": True, "order_id": order_id, "status": "shipped", "amount_cny": 129.0}


@mcp.tool()
def refund(order_id: str, confirm: bool = False) -> dict[str, Any]:
    """为订单退款（破坏性操作：必须显式 confirm=True 才会执行）。

    Args:
        order_id: 订单号。
        confirm: 二次确认开关，模拟"人工确认"闸门。
    """
    if not confirm:
        # 策略闸门：破坏性操作未确认时拒绝执行，返回可读原因。
        return {"ok": False, "error": "退款是破坏性操作，必须 confirm=True 才能执行"}
    if not order_id.startswith("ORD-"):
        return {"ok": False, "error": f"订单号格式非法: {order_id!r}"}
    return {"ok": True, "refunded": order_id, "amount_cny": 129.0}


@mcp.tool()
def convert_temperature(celsius: float) -> dict[str, Any]:
    """摄氏温度转华氏温度。参数校验失败时抛 ValueError（协议层工具错误路径）。

    Args:
        celsius: 摄氏温度，必须在 -273.15 到 10000 之间。
    """
    if celsius < -273.15:
        # 抛异常 => MCP 协议返回 isError=True 的工具结果，
        # 模型会看到错误文本而不是令宿主崩溃。
        raise ValueError(f"温度低于绝对零度: {celsius}")
    return {"celsius": celsius, "fahrenheit": round(celsius * 9 / 5 + 32, 2)}


if __name__ == "__main__":
    # stdio 传输：宿主以子进程方式拉起本脚本，经标准输入输出交换 JSON-RPC。
    mcp.run(transport="stdio")

10.6.2 框架集成实现（官方 SDK：同文件内自举"服务器+客户端"端到端演示）

下面这个脚本把服务器与 MCP 客户端装进同一个文件：运行时把自身作为 stdio 子进程拉起，完成握手、工具发现、成功调用、业务失败、协议错误与资源读取，在 mcp==1.28.1 实测可直接 python ch10_mcp_e2e.py 运行；最后一段（可选）把 MCP 工具接到真实模型做一次最小的"模型选工具"循环，需配置环境变量，未配置自动跳过。

"""MCP 端到端演示：同一文件内实现 FastMCP 服务器 + 客户端自举调用。

依赖：pip install "mcp[cli]"   # 在 mcp==1.28.1 上实测通过
运行：python ch10_mcp_e2e.py
（可选的模型循环需要环境变量 AGENT_LLM_API_KEY，未设置则跳过该步。）
"""
import asyncio
import json
import os
import sys
from typing import Any

from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client
from mcp.server.fastmcp import FastMCP

# ---------- 第一部分：服务器定义（与 10.6.1 相同的工具集） ----------
mcp = FastMCP("demo-tools")


@mcp.tool()
def get_order(order_id: str) -> dict[str, Any]:
    """按订单号查询订单状态。order_id 需以 ORD- 开头。"""
    if not order_id.startswith("ORD-"):
        return {"ok": False, "error": f"订单号格式非法: {order_id!r}"}
    if order_id == "ORD-404":
        return {"ok": False, "error": "订单不存在"}
    return {"ok": True, "order_id": order_id, "status": "shipped"}


@mcp.tool()
def refund(order_id: str, confirm: bool = False) -> dict[str, Any]:
    """退款（破坏性操作，必须 confirm=True）。"""
    if not confirm:
        return {"ok": False, "error": "退款必须 confirm=True"}
    if not order_id.startswith("ORD-"):
        return {"ok": False, "error": f"订单号格式非法: {order_id!r}"}
    return {"ok": True, "refunded": order_id}


@mcp.tool()
def convert_temperature(celsius: float) -> dict[str, Any]:
    """摄氏转华氏。低于绝对零度抛 ValueError。"""
    if celsius < -273.15:
        raise ValueError(f"温度低于绝对零度: {celsius}")
    return {"celsius": celsius, "fahrenheit": round(celsius * 9 / 5 + 32, 2)}


@mcp.resource("config://app")
def get_config() -> str:
    """应用配置资源：宿主可直接读取，无需模型决策。"""
    return json.dumps({"env": "demo", "max_refund_cny": 500}, ensure_ascii=False)


# ---------- 第二部分：客户端调用流程 ----------
async def client_demo() -> None:
    # 把本文件作为 stdio 服务器子进程拉起（生产中服务器是独立进程/独立服务）。
    server_params = StdioServerParameters(command=sys.executable, args=[__file__, "--serve"])
    async with stdio_client(server_params) as (read, write):
        async with ClientSession(read, write) as session:
            # 1) 初始化：协议版本与能力协商。
            init = await session.initialize()
            print(f"[握手] 协议版本={init.protocolVersion} 服务器={init.serverInfo.name}")

            # 2) 发现：动态枚举工具与资源。
            tools = await session.list_tools()
            print(f"[发现] 工具: {[t.name for t in tools.tools]}")

            # 3) 成功路径。
            r1 = await session.call_tool("get_order", {"order_id": "ORD-1001"})
            print(f"[成功] get_order -> {r1.content[0].text}")

            # 4) 业务失败路径：工具正常返回，但业务层报错（isError=False）。
            r2 = await session.call_tool("get_order", {"order_id": "ORD-404"})
            print(f"[业务失败] get_order -> {r2.content[0].text}")

            # 5) 协议工具错误路径：工具抛异常 => isError=True。
            r3 = await session.call_tool("convert_temperature", {"celsius": -300})
            print(f"[工具错误] isError={r3.isError} -> {r3.content[0].text}")

            # 6) 策略闸门路径：破坏性操作未经确认被拒，随后确认通过。
            r4 = await session.call_tool("refund", {"order_id": "ORD-1001"})
            print(f"[未确认] refund -> {r4.content[0].text}")
            r5 = await session.call_tool("refund", {"order_id": "ORD-1001", "confirm": True})
            print(f"[已确认] refund -> {r5.content[0].text}")

            # 7) 资源读取：不经模型，宿主直接消费。
            resources = await session.list_resources()
            if resources.resources:
                uri = resources.resources[0].uri
                res = await session.read_resource(uri)
                print(f"[资源] {uri} -> {res.contents[0].text}")

            # 8)（可选）模型选工具回路：演示 10.5.3 的"两道翻译"。
            #    第一道：MCP 工具定义 -> function calling schema（自动转换）；
            #    第二道：模型的 tool call -> session.call_tool -> 结果回填给模型。
            if os.environ.get("AGENT_LLM_API_KEY"):
                mcp_tool = next(t for t in tools.tools if t.name == "get_order")
                oa_tool = {
                    "type": "function",
                    "function": {
                        "name": mcp_tool.name,
                        "description": mcp_tool.description or "",
                        "parameters": mcp_tool.inputSchema,
                    },
                }
                messages: list[dict[str, Any]] = [
                    {"role": "user", "content": "帮我查一下订单 ORD-404 的状态。"}
                ]
                first = llm_chat(messages, tools=[oa_tool])
                if first.tool_calls:
                    call = first.tool_calls[0]
                    args = json.loads(call.function.arguments)
                    print(f"[模型] 选择工具 {call.function.name}，参数 {args}")
                    result = await session.call_tool(call.function.name, args)  # 真实协议调用
                    messages += [
                        {"role": "assistant", "content": first.content or "",
                         "tool_calls": [t.model_dump() for t in first.tool_calls]},
                        {"role": "tool", "tool_call_id": call.id,
                         "content": result.content[0].text},
                    ]
                    final = llm_chat(messages)
                    print(f"[模型] 最终回答: {final.content}")
            else:
                print("[跳过] 未设置 AGENT_LLM_API_KEY，跳过模型选工具演示。")


def llm_chat(messages: list[dict[str, Any]], tools: list[dict[str, Any]] | None = None,
             temperature: float = 0.0):
    """统一的模型接入辅助函数（OpenAI 兼容协议，只读环境变量），返回完整消息对象。"""
    from openai import OpenAI

    client = OpenAI(
        base_url=os.environ.get("AGENT_LLM_BASE_URL", "https://api.openai.com/v1"),
        api_key=os.environ["AGENT_LLM_API_KEY"],
    )
    model = os.environ.get("AGENT_LLM_MODEL", "gpt-4o-mini")
    kwargs: dict[str, Any] = {"model": model, "messages": messages, "temperature": temperature}
    if tools:
        kwargs["tools"] = tools
    return client.chat.completions.create(**kwargs).choices[0].message


def llm(prompt: str, system: str = "", temperature: float = 0.3) -> str:
    """纯文本问答形式的模型接入辅助函数。"""
    messages = ([{"role": "system", "content": system}] if system else []) + [
        {"role": "user", "content": prompt}
    ]
    return llm_chat(messages, temperature=temperature).content or ""


async def main() -> None:
    await client_demo()


if __name__ == "__main__":
    if "--serve" in sys.argv:
        # 子进程模式：充当 MCP 服务器。注意 mcp.run 自己管理事件循环，
        # 必须从同步入口调用，不能包在 asyncio.run() 里（否则报嵌套事件循环错误）。
        mcp.run(transport="stdio")
    else:
        asyncio.run(main())

10.6.3 生产化改造清单

  • 认证与授权：远程服务器按规范实现 OAuth 2.1 资源服务器（RFC 9728 元数据），客户端强制 RFC 8707 资源指示符绑定令牌受众；禁止任何形式的令牌透传。
  • 超时与取消：每次 tools/call 设置调用超时与取消传播，长任务工具改异步任务模式，杜绝工具 hang 住拖死智能体循环。
  • 确认闸门：destructive 类工具强制二次确认（Elicitation 或宿主 UI），并默认开启工具注解过滤。
  • 工具治理：工具数量按任务裁剪，超量时用工具检索；工具描述纳入 prompt 评审流程；服务器更新触发工具定义 diff 审查与回归。
  • 供应链隔离：第三方服务器在容器/沙箱中运行，限定文件系统（配合 Roots）与网络出口，最小权限账号。
  • 可观测：每次调用记录 trace（服务器身份、工具、参数摘要、耗时、isError），错误率与延迟进入指标看板，与第 11 章监控打通。
  • 输出校验：有 outputSchema 的工具做结构化校验，校验失败计入工具健康分，触发熔断或摘除。
  • 成本控制：Sampling 调用设预算上限；按宿主会话缓存 tools/list 结果，变更通知驱动刷新而非轮询。
  • 版本锁定：初始化协商后锁定协议版本，服务器升级走灰度与兼容性测试。

10.7 概览 / 核心要点 / 结论

本章小结

MCP 把智能体工具层从"两两定制集成"重构为"协议化接入"：宿主通过客户端与服务器完成版本协商、动态发现与受控调用，三类服务端能力（Tools/Resources/Prompts）对应模型推理、宿主上下文与用户交互三种消费方式，三类客户端能力（Sampling/Roots/Elicitation）把控制权收敛回宿主与用户。它与 function calling 上下分层、与 A2A 横向分工，共同构成智能体互联互通的协议栈。协议统一了接口形状，但语义质量、安全治理与运维成本仍线性存在——理解 M+N 的真实边界，比记住类比更重要。

核心要点

  • MCP 解决 M×N 集成爆炸：M 份客户端 + N 份服务器替代 M×N 份胶水代码，但治理成本不随协议消失。
  • 架构三角色：宿主（用户应用）、客户端（每服务器一条连接）、服务器（能力提供方）；报文统一为 JSON-RPC 2.0。
  • 三对原语的分工：Tools 给模型用、Resources 给宿主读、Prompts 给人选；Sampling/Roots/Elicitation 体现"能力向下、控制权向上"。
  • 传输选择：本地 stdio、远程 Streamable HTTP；2025-03-26 版起的 OAuth 2.1 + RFC 8707 是企业部署底线。
  • 工具描述即 prompt：选工具、填参数的质量取决于描述质量，需纳入评审；工具数量需主动治理。
  • 安全面三害：混淆代理（令牌透传）、工具描述注入、审计缺失；对策是受众绑定、定义变更审查与全链路调用审计。
  • 分层协作：function calling 管模型接口层，MCP 管工具协议层，A2A 管智能体间协作层，三者互补而非互斥。
  • 采用判据：真实存在"多宿主复用/动态发现"需求才引入 MCP；单应用少量函数直接用进程内注册更简单。

结论

模型上下文协议的意义不在某个技术特性，而在于它证明了智能体生态可以像编辑器生态一样，通过一个中立协议完成分工重组：能力提供方专注把一件事做好并实现一次，应用方专注体验并实现一次，中间的信任、发现与控制由协议承载。对工程师而言，落地时真正要下的功夫在协议之外——工具语义设计、安全策略与审计体系；协议给了接口，质量仍在自己手里。
