第一部分 · 核心模式

第4章 反思 Reflection

让智能体以批评者视角审视自身输出，经"生成-批评-修订"循环与跨尝试教训沉淀提升质量，并明确其能力边界与停止条件。

一句话定义：反思让智能体把自己的输出当作审查对象，通过显式的"生成—批评—修订"循环迭代改进，并把跨尝试的教训沉淀为后续决策的输入。 解决什么问题：单次生成质量不可靠，人工审核又贵又慢 ｜ 适用场景：错误代价高、质量可以判定、允许多轮调用的任务 ｜ 核心机制：生成者与批评者角色分离，批评作为修订条件，配以明确停止条件 ｜ 代价：成倍的调用开销与延迟，且自反思存在能力天花板与自我偏爱。

4.1 模式概述

4.1.1 问题背景：为什么需要这个模式

大语言模型的单次生成是一个"一遍过"的过程：自回归地逐 token 写下答案，中途没有回头修正的机会。事实幻觉、约束遗漏、推理链断裂三类典型错误在单次生成里都没有被纠正的机会。麻烦在于发现成本分布极不均匀：格式错误可用正则和 schema 校验拦住，可执行代码可以跑测试，但"论证不完整""忽略隐含要求""这个事实根本不存在"这类问题程序判不了，人工审核又贵又慢、无法规模化。

反思的出发点是一个朴素的观察：模型输出是信息量最大的审查对象，而模型恰恰是识别这些偏差成本最低的审查者。换个角色把输出重读一遍，往往几秒钟就能指出人类评审员要十分钟才能定位的问题。把"生成"与"评价"拆成两次调用、两个角色，评价时模型的注意力不再被"写下一个 token"占据，而是全局重读整份输出——这是反思有效的机制基础。

4.1.2 核心机制：它如何工作

反思的最小闭环有四步：生成草稿，结构化批评，条件修订，终止判定。其中批评是整个模式的枢纽，工程上对批评有三个硬要求。其一是聚焦：评审提示必须明确评审维度，比如"只检查边界条件与错误处理"，而不是笼统的"看看有没有问题"——不聚焦的批评每轮指向不同的缺陷，循环永不收敛。其二是结构化：批评输出为分数加问题列表的 JSON，才能被程序解析并驱动控制流。其三是可执行：每条批评要指向一个可修改之处，"不够好"是无用批评，"函数没有处理空输入的情况"才是可执行批评。

修订以批评为条件而非简单"再写一遍"：把上一版输出和批评一起交给模型，要求逐条解决问题、保留未被质疑的部分。终止判定是第三要素，也最易被忽略：硬闸是最大轮数与成本预算，软闸是评审通过或分数收敛——没有终止判定的反思循环，就是一个烧钱的 while True。

批评者从哪里来决定了三条变体线：同一模型换系统提示扮演评审（Self-Refine 式）、外部工具提供客观反馈（CRITIC 式）、上个尝试的失败教训作为反馈（Reflexion 式）。三条线的机制与失效方式差异很大，4.5 节展开。

4.1.3 与相邻模式的关系与组合

反思与提示链的关系是"带反馈回边的链"：提示链是单向无环结构，反思引入循环——这既是力量来源，也是必须配停止条件的原因。反思与工具使用的关系是反馈来源：代码解释器、搜索引擎这些第 5 章的工具，正是外部反馈反思的反馈器，工具结果比模型自评可靠得多。反思与记忆的关系在 Reflexion 里最清楚：语言化自我反思写入情景记忆，跨任务、跨尝试复用。反思与多智能体的关系是批评者独立化：把评审者做成带不同系统提示、甚至不同模型的智能体，可部分缓解模型偏爱自己输出的倾向。最后，反思与规划互为前哨：执行失败后的复盘为第 6 章的重规划提供证据——先搞清哪里错了，再决定怎么重排。

4.2 起源与历史：最早是谁提出来的

"模型检查并修正自己的输出"作为思想，最早在训练侧落地。Anthropic 的 Constitutional AI 论文把"批评—修订"（critique-revise）循环用于改造训练数据：模型依据一组原则批评自己的回答，再依据批评修订出更好的回答，用两版回答构成偏好对，替代人工撰写的对比数据——这确立了"自我批评可以作为训练信号"的可行性。三个月后，两篇把循环搬到推理期的工作在同一个 arXiv 编号段（2303）里先后出现，方向却截然不同：Self-Refine 在单个任务内部迭代打磨一份输出，Reflexion 则让智能体在多次尝试之间积累教训。两个月后的 CRITIC 补上关键一刀：用实验证明纯自反思有明确能力边界，并给出工具增强的修正方案；此后的工作（如 CoVe）多是主线上的变体深化。

4.3 发挥的作用：为什么重要

第一重作用是免训练提质：Self-Refine 的实验量级是平均约 5%~20% 的提升，代价只是几次额外调用；对不能微调闭源模型的团队，这是唯一低成本的质量杠杆。第二重作用是错误预算管理：与其让评审员逐份审阅所有输出，不如让反思循环先拦掉大部分问题，人工只复核仍标红的少数案例——审核人力从"全量"降到"例外"，这是多数团队采用反思的真实动机。第三重作用是为训练供数：批评—修订的成对输出是现成的偏好数据，可回流偏好优化训练，让"推理期的拐杖"内化为"模型的能力"，Constitutional AI 展示的正是这条路。第四重作用在可观测性：结构化批评记录了系统为什么错、错在哪一步，生产排障时比最终输出的对错更有信息量——大量"模型错了"的案例，根因其实是任务没说清。

4.4 实际应用与案例

代码生成与修复。 Reflexion 在 HumanEval 上把 pass@1 推到 91%：首次生成失败后，把失败代码与报错摘要交给模型写语言化反思（"忘了处理除零""列表为空会越界"），存入记忆；下次尝试把反思连同任务一起给模型。关键设计点是反思只存语言教训，不存梯度——比微调便宜几个数量级，对闭源模型同样可用。

长文事实核查。 用 CoVe 式流程处理传记、综述类长文：先起草，再让模型列出验证问题（"某某是否确实在某某年担任某某职务"），逐条独立作答，最后合并修订。关键设计点是验证问题必须独立作答、不能看到原稿，否则模型会顺着原稿继续错，验证形同虚设。

Text-to-SQL 与数据查询。 生成的 SQL 先在数据库上 EXPLAIN 或试运行，把报错与执行计划作为外部反馈回给模型修订。关键设计点是执行器本身就是免费的评审员——凡有程序化反馈通道的任务，都应优先用外部反馈而非模型自评。

高风险外发文本质检。 客服回复、对外公告、合同摘要等发出后难以撤回的文本，出站前过一道聚焦批评（维度：事实一致性、承诺边界、语气合规），不通过则退回修订。关键设计点是批评维度与法务/品牌规范一一对应，每条批评需引用原文位置，便于人工快速复核。

4.5 深度讲解

4.5.1 三条变体线：反馈从哪里来

一切设计分歧归根结底是一问：反馈从哪里来。按反馈来源划出三条变体线，它们的适用面与失效方式几乎不重叠。

第一条线：单模型自反思。 代表是 Self-Refine 与 CoVe。同一个模型在同一任务内轮流扮演生成者与评审者，靠系统提示切换角色。Self-Refine 的流程是生成—反馈—修订的迭代，反馈要求具体、可执行，七项任务平均提升约 5%~20%；CoVe 是针对幻觉的专门化变体：起草后先计划一组验证问题，再逐条独立作答，最后把验证结果合并进修订稿。CoVe 的关键发现是"独立性"的价值——验证时若还能看到原稿，模型会顺着原稿继续错；把验证问题拆出来单独作答（factored 变体），验证准确率显著提高，幻觉随之下降。这条线的全部机制成本就是几次 API 调用，适合改进表达、逻辑、格式、指令遵循这类"模型有能力判断对错"的维度。

第二条线：外部反馈反思。 代表是 CRITIC。模型生成答案后，由工具链提供客观反馈：解释器验证计算，搜索验证事实，执行器验证 SQL，模型在"批评—编辑"循环里依据工具返回修正答案。优势是反馈可验证、不依赖模型自知之明；代价是工具生态依赖与延迟。它的适用面恰好补在第一条线的空档：凡是正确性可程序化判定的事（计算、事实、可执行性），都应走外部反馈，不走模型自评。

第三条线：跨轨迹反思。 代表是 Reflexion。前两条线在一个任务实例内部打转，这条线把反思单位放大到"一次完整的尝试轨迹"：失败后模型对整条轨迹写语言化反思，存入情景记忆，下次尝试时注入提示。论文里的说法是"语言化的强化学习"——用语言反馈替代梯度更新，用情景记忆替代参数更新，在 HumanEval 上拿到 91% pass@1。它的独特价值是复利：一次反思的教训可被后续同类任务反复使用；代价是每次失败都实打实花掉完整尝试的成本，且反思可能学错教训（把偶然成功归因为错误原因），错误教训同样会复利。

三条线不是互斥选项，生产系统常常按错误类型分流：格式与逻辑走自反思，事实与计算走工具反馈，反复失败的同类任务走跨轨迹记忆。分流的前提是先回答"这类错误谁有能力判定"，答案决定路线。

4.5.2 为什么"自己改自己"会有用

直觉上，让模型检查自己的输出像是让作者给自己审稿，应当无效；实验却反复显示有效，原因在生成与审查的信息处理方式差异。生成是单向不可撤销的：自回归模型一旦写下前文，后续所有 token 都以它为条件，早期的错误选择会被不断放大和"合理化"——这正是不加处理的幻觉成因。审查则是全局重读：前后对照、在心里执行、与任务原文逐条比对。同一个权重，两种注意力分布，效果近似两个角色。另一个常被低估的变量是反馈提示的具体化程度："检查一下有没有问题"几乎不产生增益，"列出所有未处理的边界输入，并标注行号"能显著改善修订质量。自反思的收益大头不来自"反思"这个动作，而来自提示迫使模型执行的系统性检查流程——这对提示设计的指导意义比"加个反思节点"大得多。

4.5.3 反思何时失效：天花板、偏见与过度修改

失效模式一：能力天花板。 CRITIC 的实验给出了反思模式最重要的边界：对于模型本来就不会的问题，纯自反思不仅无益，反而有害——会越改越错。机制不难理解：修订需要"正确信号"指引方向，信号不在模型内部时，改动只是在相邻错误之间游走；更糟的是每轮修订都伴随"我在改进"的过程感，循环越长输出越显得自信，错误却未必减少。工程推论：上线反思前先测基线能力——如果模型在目标领域裸跑的准确率本身很低（如极冷门领域的事实问答），自反思只会粉饰错误，必须先引入外部知识源，即转入第二条线。

失效模式二：自我强化偏见。 模型给自己输出打分时普遍偏高，批评偏软——"整体不错，只需微调"是最常见的无效评审。CoVe 的 factored 变体是针对它的结构性解法：验证环节看不到原稿，偏见失去附着的载体。工程上有三个补充手段：换模型当评审（用另一家族模型做批评者，偏见相关性低）；程序化闸门（能写测试的就不让模型自评通过）；批评强制引用（每条批评须引用原文位置与具体建议，空泛批评解析即拒）。

失效模式三：过度修改。 没有收敛闸的循环会把正确的部分也改掉：修订模型面对"继续改进"的指令，倾向于制造可见改动证明努力，用词替换、结构重排轮番上演，文风漂移，正确的事实被"改写"成错误。对抗手段是把"保持不变"写进修订提示并纳入评审维度——评审不仅检查问题是否解决，也检查未被判错部分是否原样保留。

失效模式四：收益方差。 反思的提升幅度在不同任务、模型、轮数之间波动很大，论文平均数不能直接外推到你的任务。上线前必须用自己的数据做批量 A/B：同样的输入，跑"一次生成"与"反思 N 轮"两组，比较通过率与总成本，而非单例观感。跳过这一步直接上线，是在为未知的效果支付确定的成本。

4.5.4 停止条件设计

停止条件是反思循环的骨架决策，四个闸门按序检查。硬闸在前：最大轮数（实践中 2~3 轮是性价比区间，超过 5 轮的收益极其罕见）与成本预算（任务累计 token 上限）。软闸随后：评审通过（分数超阈值且 passed 为真）；分数收敛（修订后的新分没有超过上一轮，继续改大概率原地打转）；批评收敛（连续两轮批评高度相似，说明评审员提不出新意见了）。还有个常被忽略的细节：终轮独立评审。循环内的评审读过修订历史，容易被"已经改了这么多"感染；循环结束后用一次全新、不带历史的评审做最终判定，通过的才算数——把"过程努力"从验收标准里剔除。

三个反模式：其一，无上限的"再改一遍"；其二，把反思轮数当质量证据（"我们跑了五轮反思"不是质量证明，终评分数与下游验收才是）；其三，批评维度不聚焦，每轮修不同的点、永不收敛——解法是把维度清单固化在提示里，每轮只允许报清单内的问题。

4.5.5 何时不要用

四类场景应直接放弃反思。可程序化校验的输出直接跑测试，模型自评纯属多余；延迟敏感的实时链路（对话首响、流式补全）受不了多轮串行调用；一次性低价值输出（随手摘要、内部草稿）成本超过收益；最根本的一类是基线能力不足的任务——模型裸跑都做不好的事，自己检查自己也做不好，先补外部知识或换更强的模型，再谈反思。

4.6 工程落地：实践代码示例

4.6.1 框架无关实现（完整可运行）

下面的实现带完整停止条件与错误路径：批评解析失败时降级为保守评审而非崩溃；分数不再提升即停止；终轮用一次不带历史的独立评审做最终判定。

"""反思模式：generate -> critique -> refine 循环的框架无关实现。

依赖：pip install openai
环境变量：
  AGENT_LLM_BASE_URL  OpenAI 兼容接口地址（默认 https://api.openai.com/v1）
  AGENT_LLM_API_KEY   API Key（必填）
  AGENT_LLM_MODEL     模型名（默认 gpt-4o-mini）
"""
from __future__ import annotations

import json
import os
from dataclasses import dataclass, field

from openai import OpenAI

client = OpenAI(
    base_url=os.environ.get("AGENT_LLM_BASE_URL", "https://api.openai.com/v1"),
    api_key=os.environ["AGENT_LLM_API_KEY"],
)
MODEL = os.environ.get("AGENT_LLM_MODEL", "gpt-4o-mini")


def llm(prompt: str, system: str = "", temperature: float = 0.3) -> str:
    """调用一次大模型，返回文本回复。"""
    messages = []
    if system:
        messages.append({"role": "system", "content": system})
    messages.append({"role": "user", "content": prompt})
    resp = client.chat.completions.create(
        model=MODEL, messages=messages, temperature=temperature
    )
    return resp.choices[0].message.content or ""


@dataclass
class Critique:
    """一轮结构化评审的结果。"""

    passed: bool
    score: int  # 0-100
    issues: list[str] = field(default_factory=list)
    raw: str = ""


def parse_critique(text: str) -> Critique:
    """把模型输出的评审解析为 Critique。

    错误路径：模型不一定按格式输出。解析失败时降级为"未通过、0 分"的
    保守评审，让循环走修订分支，而不是让整个程序崩溃。
    """
    cleaned = text.strip()
    try:
        if cleaned.startswith("```"):  # 容错：剥掉 markdown 代码块
            cleaned = cleaned.strip("`")
            if cleaned.startswith("json"):
                cleaned = cleaned[4:]
        data = json.loads(cleaned)
        return Critique(
            passed=bool(data["passed"]),
            score=max(0, min(100, int(data["score"]))),
            issues=[str(x) for x in data.get("issues", [])],
            raw=cleaned,
        )
    except (json.JSONDecodeError, KeyError, TypeError, ValueError):
        return Critique(
            passed=False,
            score=0,
            issues=[f"评审输出不可解析，请重新输出：{text[:200]}"],
            raw=text,
        )


CRITIQUE_SYSTEM = (
    "你是以挑剔著称的代码评审员。只报告事实问题，不奉承，"
    "每条意见必须指出具体位置和修改建议。"
)


def critique_answer(task: str, answer: str, focus: str) -> Critique:
    """让模型以评审者身份检查草稿，聚焦 focus 列出的维度。"""
    prompt = f"""请评审下面这份针对任务的解答。

【任务】{task}

【解答】
{answer}

【评审维度（只报这几点，不得发散）】{focus}

只输出一个 JSON 对象，不要输出任何其他内容：
{{"passed": true或false, "score": 0到100的整数, "issues": ["问题1（位置+修改建议）", ...]}}"""
    return parse_critique(llm(prompt, system=CRITIQUE_SYSTEM, temperature=0.1))


def refine_answer(task: str, answer: str, critique: Critique) -> str:
    """根据评审意见修订解答：逐条解决被判错的部分，未被判错的原样保留。"""
    issues = "\n".join(f"- {i}" for i in critique.issues)
    fallback = "-（无具体意见，请自查逻辑与边界）"  # 预先取出，兼容 Python 3.10 的 f-string 引号限制
    prompt = f"""请修订下面这份解答。要求：
1. 逐条解决评审意见，不得遗漏；
2. 未被评审意见涉及的部分保持原样，禁止改写措辞或调整结构；
3. 直接输出修订后的完整解答，不要解释。

【任务】{task}
【当前解答】
{answer}
【评审意见】
{issues or fallback}"""
    return llm(prompt, temperature=0.2)


def reflect_loop(
    task: str,
    focus: str,
    max_rounds: int = 3,
    pass_score: int = 85,
) -> dict:
    """generate -> critique -> refine 主循环。

    停止条件（满足其一即停）：
    1. 软闸：评审通过（passed 且 score >= pass_score）；
    2. 硬闸：达到最大轮数 max_rounds；
    3. 收敛闸：本轮分数未超过上一轮，继续修订大概率原地打转。
    返回值带出分数轨迹与停止原因，便于评估反思的真实收益。
    """
    answer = llm(f"完成任务：{task}\n直接给出解答。", temperature=0.4)
    history: list[dict] = []
    stop_reason = "达到最大轮数"
    for round_no in range(1, max_rounds + 1):
        c = critique_answer(task, answer, focus)
        history.append({"round": round_no, "score": c.score, "issues": c.issues})
        print(f"[第{round_no}轮评审] score={c.score} passed={c.passed} issues={len(c.issues)}")
        if c.passed and c.score >= pass_score:
            stop_reason = "评审通过"
            break
        if round_no > 1 and c.score <= history[-2]["score"]:
            stop_reason = "分数不再提升，触发收敛闸"
            break
        answer = refine_answer(task, answer, c)
    # 终轮独立评审：不带任何修订历史，把"过程努力"从验收标准里剔除
    final = critique_answer(task, answer, focus)
    return {
        "answer": answer,
        "history": history,
        "final_score": final.score,
        "final_passed": final.passed,
        "stop_reason": stop_reason,
    }


if __name__ == "__main__":
    result = reflect_loop(
        task=(
            "编写 Python 函数 is_balanced(s: str) -> bool，"
            "判断字符串 s 中的三种括号 ()[]{} 是否正确匹配。"
        ),
        focus=(
            "1) 算法正确性（空串、纯左括号、交叉括号如 ([)] 等边界）；"
            "2) 代码可运行、有类型标注；3) 有中文 docstring。"
        ),
    )
    print("停止原因：", result["stop_reason"])
    print("分数轨迹：", [h["score"] for h in result["history"]], "-> 终评", result["final_score"])
    print("最终通过：", result["final_passed"])
    print("最终解答：\n", result["answer"])

4.6.2 框架集成实现（LangGraph，checkpoint 循环）

LangGraph 把反思循环表达为"带条件边与回边的状态图"，checkpointer 保存每步状态，循环可暂停、恢复、回放——这是框架相对裸写的核心增量。以下按 langgraph 0.2.x + langchain-openai 0.2.x 的 API 风格编写，更高版本请以官方文档核对导入路径。

"""反思模式的 LangGraph 实现：draft -> critique -> refine 状态循环 + checkpoint。

依赖：pip install "langgraph>=0.2" langchain-openai openai
环境变量同上一节（AGENT_LLM_BASE_URL / AGENT_LLM_API_KEY / AGENT_LLM_MODEL）。
"""
from __future__ import annotations

import json
import operator
import os
from typing import Annotated, TypedDict

from langchain_openai import ChatOpenAI
from langgraph.checkpoint.memory import MemorySaver
from langgraph.graph import END, START, StateGraph

chat = ChatOpenAI(
    model=os.environ.get("AGENT_LLM_MODEL", "gpt-4o-mini"),
    base_url=os.environ.get("AGENT_LLM_BASE_URL", "https://api.openai.com/v1"),
    api_key=os.environ["AGENT_LLM_API_KEY"],
    temperature=0.2,
)

MAX_ROUNDS = 3
PASS_SCORE = 85


class ReflectionState(TypedDict):
    """循环状态：LangGraph 每个节点读写它，checkpointer 负责持久化。"""

    task: str
    draft: str
    score: int
    issues: list[str]
    round: int
    score_history: Annotated[list[int], operator.add]  # 追加式合并
    stop_reason: str


def draft_node(state: ReflectionState) -> dict:
    """初稿节点。"""
    reply = chat.invoke(f"完成任务：{state['task']}\n直接给出解答。")
    return {"draft": reply.content, "round": 0}


def critique_node(state: ReflectionState) -> dict:
    """批评节点：解析失败按错误路径处理，记为 0 分待修订。"""
    prompt = (
        f"评审以下解答，只检查正确性与边界条件。只输出 JSON："
        f'{{"passed": bool, "score": 0-100整数, "issues": ["..."]}}\n'
        f"任务：{state['task']}\n解答：\n{state['draft']}"
    )
    try:
        data = json.loads(chat.invoke(prompt).content.strip().strip("`").lstrip("json"))
        score, issues, passed = int(data["score"]), list(data["issues"]), bool(data["passed"])
    except (json.JSONDecodeError, KeyError, TypeError, ValueError):
        score, issues, passed = 0, ["评审输出不可解析，需修订重写"], False
    return {
        "score": score,
        "issues": issues,
        "round": state["round"] + 1,
        "score_history": [score],
        "stop_reason": "评审通过" if passed and score >= PASS_SCORE else "",
    }


def refine_node(state: ReflectionState) -> dict:
    """修订节点：以批评为条件重写。"""
    issues = "\n".join(f"- {i}" for i in state["issues"]) or "- 无具体意见，请自查边界"
    reply = chat.invoke(
        f"修订解答：逐条解决问题，未被判错的部分保持原样。\n"
        f"任务：{state['task']}\n当前解答：\n{state['draft']}\n问题：\n{issues}"
    )
    return {"draft": reply.content}


def should_refine(state: ReflectionState) -> str:
    """条件边：通过则结束；超轮数或分数不升则收敛退出；否则继续修订。"""
    if state["stop_reason"] == "评审通过":
        return END
    if state["round"] >= MAX_ROUNDS:
        return END
    hist = state["score_history"]
    if state["round"] > 1 and hist[-1] <= hist[-2]:
        return END  # 收敛闸：分数不再提升
    return "refine"


def build_graph():
    g = StateGraph(ReflectionState)
    g.add_node("draft", draft_node)
    g.add_node("critique", critique_node)
    g.add_node("refine", refine_node)
    g.add_edge(START, "draft")
    g.add_edge("draft", "critique")
    g.add_conditional_edges("critique", should_refine, {"refine": "refine", END: END})
    g.add_edge("refine", "critique")  # 回边：反思循环的本质
    return g.compile(checkpointer=MemorySaver())


if __name__ == "__main__":
    app = build_graph()
    config = {
        "configurable": {"thread_id": "demo-thread-1"},
        "recursion_limit": 25,  # 图级步数上限，兜底防失控循环
    }
    result = app.invoke(
        {"task": "编写函数 count_vowels(s)，统计字符串中元音字母个数，含类型标注与 docstring。"},
        config=config,
    )
    print("分数轨迹：", result["score_history"], "终评：", result["score"])
    print("停止原因：", result["stop_reason"] or "轮数/收敛闸")
    print("最终草稿：\n", result["draft"])
    # checkpoint 价值演示：同 thread_id 可回放历史状态
    snap = app.get_state(config)
    print("checkpoint 中的轮次：", snap.values["round"])

4.6.3 生产化改造清单

  • 错误处理：批评 JSON 解析失败降级为"待修订"而非中断；连续 2 次解析失败直接放弃反思、带上人工复核标记返回原稿。
  • 超时与重试：每次评审/修订调用设独立超时；对 429/超时做指数退避重试，重试预算独立于反思轮数。
  • 并发：批量任务并行跑各自的循环；批评维度可拆分并行评审后合并，降低串行延迟。
  • 缓存：以（任务哈希、草稿哈希、评审维度版本）为键缓存批评结果，重跑不重复付费。
  • 可观测：记录每轮分数、批评原文、修订 diff 与停止原因；分数轨迹非单调是首要告警信号。
  • 成本控制：评审用小模型、修订用大模型的异构组合；设任务级 token 预算，预算耗尽立即退出并如实标注。
  • 批评质量治理：定期抽样人审批评本身的对错；空泛批评（未引用原文位置）在解析层直接拒收。
  • 防自我偏爱：评审与生成使用不同模型或至少不同系统提示；可程序化校验的维度一律不走模型自评。
  • 验收口径：以终轮独立评审与下游业务指标为准，不以"反思轮数多"作为质量证明。
  • 降级开关：反思循环整体可配置关闭；故障或高峰期自动退化为单次生成，保可用性。

4.7 概览 / 核心要点 / 结论

4.7.1 本章小结

反思模式把"生成即交付"改写为"生成—批评—修订—验收"的闭环：批评者可以是同一个模型（Self-Refine、CoVe）、外部工具（CRITIC）或跨尝试的教训记忆（Reflexion），三条变体线分别覆盖表达类、事实类与策略类错误。它的收益有实验背书（平均 5%~20% 的免训练提升、HumanEval 91% pass@1），边界同样有实验背书——模型不会的问题，纯自反思越改越错。工程落地的成败不在循环本身，而在三处：批评维度的聚焦、停止条件的多重闸门、以及上线前对真实收益的批量验证。

4.7.2 核心要点

  • 反思的本质是生成者与批评者的角色分离，收益来自审查时的全局重读与系统性检查，而非"再想一遍"。
  • 三条变体线按反馈来源划分：自反思改表达，工具反馈改事实与计算，跨轨迹记忆改策略；按"谁能判定对错"分流。
  • CRITIC 的核心教训：纯自反思对模型能力之外的错误无效甚至有害，先测基线再上反思。
  • CoVe 的核心教训：验证必须独立于原稿，否则自我强化偏见让验证形同虚设。
  • 停止条件四闸门：最大轮数、成本预算、评审通过、分数/批评收敛；终轮独立评审剔除过程努力的干扰。
  • 批评必须聚焦、结构化、可执行（位置+建议），修订提示须含"未被判错的部分保持原样"；空泛批评导致循环永不收敛。
  • 上线前用自己的数据做批量 A/B，比较通过率与总成本；论文平均数不能外推。

4.7.3 结论

反思不是给模型"加一轮思考"的仪式，而是一套有明确边界条件的质量控制架构。它的价值公式很简单：当错误可被识别、模型有能力识别、且错误代价高于多次调用的成本时，反思就是正收益的；三个条件缺任何一个，它就退化为烧钱的仪式。把 CRITIC 的边界实验和停止条件的四道闸门记进工程手册，比记住任何一篇论文的名字都更能避免踩坑——前者告诉你反思帮不了什么，后者告诉你如何让它体面地停下来。
