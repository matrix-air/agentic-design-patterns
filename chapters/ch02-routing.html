第一部分 · 核心模式

第2章 路由 Routing

按输入特征把请求分流到合适的提示、模型或智能体，用前置的分类判断换取出错的隔离、成本的下降与专业度的集中。

一句话定义：在请求进入处理逻辑之前，用一个轻量的判断步骤决定它该走哪条提示、哪个模型或哪个智能体。 解决什么问题：单一处理路径无法同时满足多类任务的口径、成本与延迟要求 ｜ 适用场景：多技能客服、强弱模型混部、查询分流（闲聊/检索/工具）、敏感请求前置拦截 ｜ 核心机制：规则、分类器、语义相似度或级联信号产生路由决策，附置信度兜底 ｜ 代价：误路由有业务代价，路由器自身需要维护与监控。

本章速读　路由把"这个请求是什么、该由谁处理"拆成处理逻辑之前的独立决策点：规则、分类器、语义相似度或级联信号给出决策，请求落进路由表的一行，各通道互不干扰。三步落地：选最轻的决策信号 → 建路由表与专用通道 → 设置信度兜底与 fail-open 出口。误路由成本不对称时门槛向"宁可多升舱"倾斜；任务同质、流量太小或类目未稳时都别上路由。

2.1 模式概述

2.1.1 问题背景：为什么需要这个模式

一个客服智能体同时要处理查账单、改密码、投诉三种请求。把它们交给同一个提示、同一个模型处理，立刻出现三种互相挤压的矛盾：口径上，查账单要精确引用数据，投诉要先安抚情绪，一套提示词无法两头兼顾；成本上，一半以上的请求是"查个余额"这种简单任务，却都在为最强模型的能力付费；风险上，改密码这类敏感操作与闲聊混在同一条路径里，护栏不知道该按哪个标准拦。问题的根源是"一刀切的处理路径"与"异质的请求分布"之间的错配。

路由的解法朴素而有效：把"这个请求是什么"的判断从处理逻辑里拆出来，前移成一个独立的、可单独优化的决策点。判断本身很便宜——规则、小模型或一次向量相似度计算——但它换来的却是三条各自纯粹的处理路径：每条路径的提示只为一种任务调优，模型只为该任务的实际难度配置，护栏只为该任务的风险画像设计。

2.1.2 核心机制：它如何工作

路由器是一段"输入 → 目标通道"的映射逻辑，工程上由三部分组成。第一是决策信号：规则命中、分类器输出的意图标签、输入与路由规则的向量相似度，或级联中的实时代价信号。第二是路由表：每个目标通道对应一段提示、一个模型或一个子智能体，路由决策最终落到路由表的某一行。第三是兜底出口：当决策信号弱于阈值——置信度太低、多条规则同时沾边、解析失败——请求走默认通道（通常是最强也最稳的那条）或转人工，而不是硬塞给一个低把握的分支。执行完路由后，各通道独立处理，互不影响；路由器不参与处理本身，只负责"分诊"。

2.1.3 与相邻模式的关系与组合

路由与并行化（第 3 章）常一起出现：分流之后的多个通道往往并发执行再汇合。路由是静态结构上的分支，而动态链（第 1 章）里的条件步骤是链内的分支——前者在入口处分诊，后者在流程中途改道，两者可以叠加。级联路由与资源感知优化（第 16 章）是近亲：都关心成本与质量的权衡，区别在于级联只在"强弱模型"一维上排序，而资源感知优化把延迟、配额、上下文长度都纳入考量。路由器的决策质量本身需要评估与监控（第 19 章）来保障——路由分布的漂移往往先于业务指标恶化出现。

2.2 源起：它从哪里来

路由的前身是对话系统时代的意图分类：2010 年代的 NLU 框架（如 Rasa NLU）把"先判意图、再走对应流程"做成机器人标配，2017 年公开的 SNIPS 数据集成为标准考卷。大模型时代，路由对象从"对话流程"扩展到"提示、模型与智能体"。2023 年 5 月斯坦福的 FrugalGPT 用级联把推理成本降低约 88%~98%，首次论证"按难度分流"的价值；同年 LangChain 路由链把它变成框架级写法。2023 年末 Aurelio AI 开源 Semantic Router，实现零训练意图路由；2024 年 6 月 LMSYS 的 RouteLLM 用人类偏好数据训练路由器，同等质量成本降约 2~3 倍。决策信号的升级脉络并入 2.5 节。

2.3 发挥的作用：为什么重要

路由的价值在三个维度同时兑现。口径与质量：每条通道的提示只为一种任务调优，系统整体的专业度等于各通道专业度的加权，而不是所有任务的平均分。成本：真实流量里简单任务永远占多数，FrugalGPT 与 RouteLLM 的数据说明，把这部分流量引向便宜模型可砍掉一半以上的推理开销，而复杂任务的质量不受影响。风险隔离：敏感操作、高危意图、已知滥用模式在入口就被摘出来走专用通道（更强的模型、更严的护栏、或直接人工），其余路径无需为最坏情况过度设防。

还有一层作用常被忽视：路由是系统行为的"总开关"。上线灰度、A/B 实验、故障转移、区域隔离，都可以实现为路由表的一行改动，而不必触碰任何通道的内部逻辑。这让智能体系统的演进从"改代码"降级为"改配置"，风险与发布节奏都更可控。

2.4 实际应用与案例

  • 客服多技能分诊：入口用语义路由把请求分到查账单、办业务、投诉、闲聊四条通道，投诉通道额外接情绪安抚提示与人工升级条件。关键设计点：置信度低于阈值一律走"通用强模型"通道而非猜测意图。
  • 强弱模型级联省钱：查询先由小模型处理，机械校验（格式、引用存在性）不过关或自评置信度低时升级大模型。关键设计点：升级判据必须包含机械校验，纯置信度会被小模型的过度自信骗过。
  • RAG 查询分流：闲聊直答、事实类走单跳检索、对比分析类走多跳检索。关键设计点：检索通道返回"检索不到"时要有降级出口，避免为凑答案强行检索。
  • 编程助手任务路由：行内补全走低延迟小模型，函数级生成走中档模型，跨文件重构走最强模型并附带仓库上下文。关键设计点：路由判据用请求的结构特征（范围、涉及文件数）而非文本语义，更稳。
  • 敏感请求前置拦截：涉及个人隐私操作、医疗法律建议的请求在入口摘出，走带护栏的专用链或直接转人工。关键设计点：拦截规则宁可误伤（多拦）不可漏放，误伤由后续通道的话术回收。
  • 多租户 API 网关：按租户等级路由到不同配额的模型池与不同强度的护栏。关键设计点：路由决策要可审计，每条请求记录"为什么走这条通道"。

真实世界实例

OpenAI GPT-5 的实时路由器（ChatGPT 自动选模型）。GPT-5 被设计为一个统一系统：一个快速模型回答大多数问题、一个深度推理模型处理难题，中间由一个实时路由器依据对话类型、复杂度、工具需求与显式意图（如提示里写"再仔细想想"）即时决定把请求交给哪个模型；路由器持续用真实信号再训练——用户手动切换模型的行为、回复的偏好率与实测正确率——随时间自我改进，达到用量上限后由 mini 版本接住剩余请求。ChatGPT 界面里的"自动选择模型"正是这一生产级路由的出口。（来源：OpenAI GPT-5 System Card，2025-08，arXiv:2601.03267；官方页面 https://openai.com/index/gpt-5-system-card/）

LMSYS RouteLLM（强弱模型分流的开源框架）。UC Berkeley LMSYS 团队用 Chatbot Arena 的人类偏好数据训练了四种路由器（相似度加权排名、矩阵分解、BERT 分类器、因果 LLM 分类器），在强弱模型对之间动态分流：官方博客报告在 MT Bench 上以 95% 的 GPT-4 质量减少 85% 以上的成本（MMLU 约 45%、GSM8K 约 35%），框架以 OpenAI 兼容 API 提供、pip install routellm 即可接入，路由器与数据集全部开源。（来源：LMSYS 官方博客 https://www.lmsys.org/blog/2024-07-01-routellm/；代码仓库 https://github.com/lm-sys/RouteLLM）

Intercom Fin（企业客服 AI Agent 的意图分流与人工升级）。Fin 的架构分应用、AI、模型三层，其模型层是一组为客服场景定制的专用模型，其中专门有一个模型负责"判断何时把会话升级给人工"；运营侧通过 routing outcomes 把匹配条件的会话（如销售资格、自助引导、流程办理）路由到对应团队或工作流，无法处理时按默认升级规则移交人工。官方公布其平均解决率（resolution rate）在 12000 多家客户上约 76%——这是"意图分流 + 置信度兜底 + 人工出口"在客服工业界的规模化形态。（来源：Intercom 官方帮助中心 https://www.intercom.com/help/en/articles/7120684-fin-ai-agent-explained；https://www.intercom.com/）

2.5 深度讲解

机制细节与变体谱系：四种路由器。 第一种是规则路由：关键词、正则、长度阈值等显式条件。它零成本、完全可解释、毫秒级完成，适合封闭域里的高置信度规则（"包含退款并包含投诉的请求进售后通道"）。它的死穴是维护腐化：用户换一种说法（"钱多扣了"与"重复扣款"），规则就静默失灵，规则库只会越积越长、互相打架。第二种是分类器路由：用小模型乃至传统机器学习模型做意图分类，这是对话系统时代延续下来的标配，需要标注数据与再训练管线，类目边界清晰时表现优秀，但长尾输入与新增类目要靠持续回灌。第三种是语义路由（Semantic Router 路线）：把每条路由规则写成示例语句并编码为向量，运行时用输入的向量与规则向量做相似度匹配，超过阈值即命中。它零训练、规则可以即时增删（加一条规则只是加一行向量），代价是阈值成为核心超参——阈值松了多条规则同时沾边产生歧义命中，紧了又漏。第四种是级联路由（FrugalGPT、RouteLLM 路线）：它与前三种有本质区别——判据不是"请求是什么"这个先验，而是"处理得怎么样"这个运行时证据。便宜模型先答，答案过不了机械校验或置信度评估就升级到贵模型。级联把"路由"变成了"分级服务"，其代价是简单请求也要先付一次便宜模型的成本，且弱模型的错误有时是"自信地错"，校验器必须独立于弱模型的自我报告。

演化对照：决策信号的四次升级。 把四种路由器按时间排开，能看到判据信号的升级线：人工规则（关键词，2010 年代）→ 统计分类器（需标注数据，对话系统时代延续）→ 语义向量（零训练、规则热更新，2023 年末）→ 运行时代价信号（级联与学习型路由，2023-2024）。信号越强，路由器自身越重：规则零维护成本但静默失灵，学习型路由器降本最多但需要偏好数据与再训练管线。工程选择从来不是"用最先进的"，而是"用误路由代价能承受的最轻的"——这条判据本身就是下一小节成本矩阵思想的推论。

机制细节：误路由的成本不对称。 路由决策要按成本矩阵设计，而不是按准确率。把复杂任务路由给弱模型，代价是答案质量——可能引发返工、投诉甚至业务损失；把简单任务路由给强模型，代价只是几秒延迟与一点预算。两侧代价经常差一个数量级，因此阈值必须向"宁可多升舱"倾斜：置信度门槛设在偏高位置，兜底通道配最强模型。更隐蔽的问题是分类器的校准性——模型输出的 0.9 未必对应 90% 的正确率，过度自信是常态，置信度阈值要用本系统真实流量回放校准，不能照搬论文数值。任何路由器都必须有"我不知道"出口：解析失败、多规则冲突、置信度全面低于阈值时走默认通道，fail-open 到强模型比 fail-close 到错误通道便宜得多。

定量证据：路由的收益要按基准算，两笔代表性账。 FrugalGPT 的摘要结论：级联可以在与 GPT-4 性能相当的前提下把成本降低最高 98%，或在同等成本下把准确率再提高 4%（arXiv:2305.05176）。RouteLLM 的官方基准更贴近生产口径：在 MT Bench 上以 95% 的 GPT-4 质量减少 85% 以上的成本，MMLU 约 45%、GSM8K 约 35%（LMSYS 官方博客）；细看构成更有信息量——矩阵分解路由器只需把约 26% 的流量交给 GPT-4 就能守住 95% 质量线，叠加 LLM 裁判增强后这一比例降到约 14%。两笔账共同说明：真实流量里简单任务占大头，为它们支付最强模型的价格是系统性浪费；而"守质量、砍成本"的约束式目标（而非单纯追求路由准确率）才是可上线的目标函数。

反直觉：路由器的目标是期望成本最小，不是分类准确率最高。 用期望成本算一笔账就清楚：设误路由率 5%，其中一半是把复杂任务分给弱模型（单次损失 10 元量级：返工、投诉、业务损失），另一半是把简单任务分给强模型（超额成本 0.1 元量级），两侧差两个数量级——那 2.5% 的高危误路由贡献了几乎全部期望损失，95% 的"对称准确率"救不了它。把门槛调到宁可让 10% 的简单请求升舱，总损失反而更低；RouteLLM 的评估方式正是如此：在"质量保持 95%"的约束下求成本最小，而不是报告一个路由准确率。第二个常见误解是把模型自报的 confidence 当概率用：LLM 置信度普遍过度自信且未校准，0.9 不代表 90% 正确率——阈值必须用本系统真实流量回放来定，分类器的校准性（calibration）比分辨力更值得验收。

边界条件：路由收益何时被吃掉。 三个可核对的边界。其一，通道间成本差：强弱模型单价差低于约 2 倍时，路由器自身的调用成本、延迟与误路由损失通常吃掉全部收益（经验边界，随模型降价节奏要重算）。其二，流量结构：简单任务占比越高峰值收益越大，RouteLLM 式"两成流量给强模型"的前提是八成流量真的可被弱模型接住——你的流量若相反，级联只会有第二次调用成本。其三，样本密度：某通道流量占比低到每周几十条时，该通道的提示永远调不准，路由器成了 Rare-class 制造机。

机制细节：路由粒度与决策位置。 路由可以在三个粒度上发生：提示路由（同一模型，按意图换提示模板）、模型路由（按难度换模型）、智能体路由（按任务类型换工具集与子智能体）。粒度越粗，单次误路由的代价越大：提示路由错了还能靠模型兜底，智能体路由错了整条工具链都白跑。决策位置同理：入口路由（分诊）看 whole 请求，链中路由（条件步骤）看中间结果——第 1 章的动态链就是链中路由的特例。生产系统常见形态是两级路由：入口做粗粒度的模型/智能体路由，通道内部做细粒度的提示路由，两级各自简单，组合起来覆盖复杂分布。

失效模式与反模式。 第一个是域漂移：上线三个月后用户问法演变，规则与分类器静默劣化，而路由错误的表现是"答案质量下降"而非报错，往往要等业务指标恶化才被发现。对策是把路由分布本身做成监控指标——某个通道的流量占比突降、兜底通道占比突升，都是漂移的早期信号。第二个是级联的隐性失败：弱模型给出了格式完美、置信度很高但事实错误的答案，机械校验全部通过，错误一路下行。对策是给高风险通道叠加第二道独立信号（如引用核对、抽样人工复核），并持续审计"升级通道的捕获率"——级联真正拦下了多少次坏答案，这个数字若趋近于零，说明级联只是白白多了一次调用。第三个是语义路由的组合意图："查一下账单然后我要投诉"同时命中两条规则，路由器若不定义优先级与合并策略，就会随机选一条，用户体验随机劣化。第四个反模式是过度路由：任务本质同质却切出十几个通道，每个通道样本稀疏到无法调优，路由器本身成了最大的复杂度来源。

何时不要用。 单一任务类型的系统不需要路由，强行分流只会增加故障面。流量小到成本无关紧要时，统一用最强模型比维护路由器划算。路由类目还不稳定的产品早期（这周三类下周五类），先把所有流量打到一个通道积累数据，等分布稳定了再切——路由的价值建立在"你对流量分布有可靠认知"之上，认知未成，路由先行就是猜。

2.5.1 怎么用：运用判断

出现以下信号时，值得给系统加路由：流量分布明显偏斜——少数简单类目占大头、少数复杂类目决定质量下限；各类目的处理口径或风险画像差异大到一套提示无法兼顾；强弱模型的价差显著且简单任务的答案可以机械验证；出现了必须在入口隔离的敏感或高危请求。反过来，任务同质、流量太小、类目未稳时，任何一种路由器都是负资产（见上文"何时不要用"）。

维度 入口路由（本章） 级联路由 单一最强模型
判据 先验：请求是什么 运行时：答得怎么样 无判据
误路由形态 永久走错通道 多付一次轻模型调用后自愈 不存在
适合 类目边界清晰、口径差异大 类目模糊但答案可机械验证 流量小、类目不稳、误路由代价极高

落地三步：第一，取一周真实流量做人工标注或规则粗分，画出"类目 × 占比 × 单价"分布，确认省钱空间大于路由器自身成本；第二，从最轻的信号起步（规则或语义路由），只分"便宜通道 / 强模型兜底"两类，配上置信度兜底与 fail-open 出口（可直接抄 2.6 节骨架）；第三，上线即埋点——通道占比、兜底率、升级通道捕获率，人工纠正过的误路由样本按月回流为规则或分类器的迭代数据。

2.6 工程落地：核心源码与讲解

2.6.1 框架无关实现（按序拼接即完整可运行）

下面把客服请求分级路由器的主程序拆为 4 个片段：环境与双模型接入 → 规则层与分类层 → 通道实现 → 路由决策入口。按序拼接即完整可运行程序；误路由防线（高危规则优先、解析失败 fail-open、置信度兜底）完整保留。

"""第2章 路由：客服请求分级路由与级联（框架无关实现）。
本节 4 个片段按序拼接即完整可运行。三层：规则路由（高危转人工）-> 分类路由
（轻模型）-> 置信度兜底；分类解析失败一律 fail-open 到强模型。
环境变量：AGENT_LLM_API_KEY（必填）、AGENT_LLM_BASE_URL / AGENT_LLM_MODEL（可选）、
AGENT_LLM_MODEL_STRONG（可选，强模型）。
"""
from __future__ import annotations

import json, os, sys

from openai import OpenAI

client = OpenAI(
    base_url=os.environ.get("AGENT_LLM_BASE_URL", "https://api.openai.com/v1"),
    api_key=os.environ["AGENT_LLM_API_KEY"],
)
MODEL = os.environ.get("AGENT_LLM_MODEL", "gpt-4o-mini")        # 轻模型：分类与简单请求
MODEL_STRONG = os.environ.get("AGENT_LLM_MODEL_STRONG", MODEL)  # 强模型：兜底与复杂请求
CONFIDENCE_GATE = 0.8  # 置信度门槛：低于它一律升舱（误路由成本不对称 -> 宁可多升舱）
ESCALATE_INTENTS = {"complaint"}  # 这些意图即使高置信度也走专用通道


def llm(prompt: str, system: str = "", temperature: float = 0.3,
        model: str | None = None) -> str:
    """调用大模型；model 参数支持把不同请求路由到不同档位的模型。"""
    messages = ([{"role": "system", "content": system}] if system else []) + [
        {"role": "user", "content": prompt}
    ]
    resp = client.chat.completions.create(
        model=model or MODEL, messages=messages, temperature=temperature
    )
    return resp.choices[0].message.content or ""

▸ 代码怎么读：与第 1 章的 llm() 相比，这个版本多了一个 model 参数——路由模式的模型接入必须支持"双档位"，这是后面级联的前提。CONFIDENCE_GATE = 0.8 是全文件最重要的数字：它不是从论文抄的，而是按误路由成本矩阵定的（复杂请求错进弱通道的损失远大于简单请求多花的钱，门槛宁高勿低，见 2.5 节）。上线前该用本系统真实流量回放校准这个值：如果兜底通道占比超过一半，说明门槛或分类器有问题。ESCALATE_INTENTS 用集合而非常量，是为了让"哪些意图必须走专用通道"成为一行配置——改路由从改代码降级为改表。

# ---------- 第一层：规则路由（最高优先级，命中即停） ----------
HUMAN_ESCALATION_KEYWORDS = ("改密码", "重置密码", "注销账户", "转账")


def rule_route(query: str) -> str | None:
    """高危关键词命中返回 'human'；否则返回 None 交给后续层。可解释、零成本、毫秒级。"""
    for kw in HUMAN_ESCALATION_KEYWORDS:
        if kw in query:
            return "human"
    return None


# ---------- 第二层：分类路由（轻模型意图分类，解析失败 fail-open） ----------
def classify(query: str) -> dict:
    """轻模型输出意图与置信度；解析失败置 ('other', 0.0)——宁可让强模型多干活，不让请求走错通道（fail-open）。"""
    raw = llm(
        "对用户请求做意图分类，只输出 JSON："
        '{"intent": "billing"|"technical"|"complaint"|"other", '
        '"confidence": 0到1的小数}。\n\n'
        f"用户请求：{query}",
        system="你是意图分类器，只输出 JSON。",
        temperature=0.0,
        model=MODEL,  # 分类用轻模型：便宜、快
    )
    try:
        start, end = raw.find("{"), raw.rfind("}")
        if start == -1 or end <= start:
            raise ValueError("输出中未找到 JSON 对象")
        data = json.loads(raw[start : end + 1])
        intent = str(data.get("intent", "other"))
        confidence = min(max(float(data.get("confidence", 0.0)), 0.0), 1.0)
        if intent not in {"billing", "technical", "complaint", "other"}:
            intent, confidence = "other", 0.0
    except (ValueError, TypeError, json.JSONDecodeError) as exc:
        print(f"[classify] 解析失败，fail-open 到强模型：{exc}")
        intent, confidence = "other", 0.0
    return {"intent": intent, "confidence": confidence}

▸ 代码怎么读：两层路由器体现了"信号从轻到重"的次序——规则层零成本且完全可解释，所以放在最前面"命中即停"，高危请求根本不必花一次分类调用。classify 的 try 块是 fail-open 的样板：解析失败、字段缺失、枚举非法、置信度越界，四种坏输出统一收敛到 ("other", 0.0)——other 加上 0.0 的置信度必然低于门槛，请求自然落进强模型兜底通道，分类器的任何失灵都被转化为"多花一点钱"而不是"走错通道"。注意分类提示里 temperature=0.0：分类要的是确定性，与生成通道的 0.3 形成对照。生产环境里 print 应替换为计数上报——fail-open 率本身是路由器健康度的首要指标。

# ---------- 通道实现：三个模型通道共用一个入口，按 route 选提示与模型 ----------
CHANNEL_SYSTEM = {
    "cheap": "你是客服助手，回答控制在 100 字以内。",
    "strong": "你是资深客服专家，答复需覆盖可能的边界情况。",
    "escalate": ("你是投诉处理专员。先共情安抚，再给解决路径；"
                 "不确定的补偿方案一律说'转专员确认'，不得替公司承诺。"),
}


def handle(query: str, route: str, intent: str = "") -> str:
    """执行通道：human 返回工单文案；cheap 走轻模型；strong/escalate 走强模型。"""
    if route == "human":
        return "[已转人工 | 原因：高危操作] 工单已创建，客服将在 10 分钟内联系您。"
    return llm(
        f"用户请求：{query}\n（意图标签：{intent}）" if intent else f"用户请求：{query}",
        system=CHANNEL_SYSTEM[route],
        temperature=0.2 if route == "escalate" else 0.3,  # 投诉话术要更稳
        model=MODEL_STRONG if route in {"strong", "escalate"} else MODEL,
    )

▸ 代码怎么读：原版四个通道函数（handle_cheap/strong/escalate/human）在这里合并成一个 handle 加一张 CHANNEL_SYSTEM 提示表——通道之间的差异被压缩到它们真实的差异上：提示不同、模型档位不同、温度不同，执行骨架完全相同。这张表就是 2.1 节说的"路由表"：新增一条通道 = 加一行表项 + 决策函数里一个分支，不需要新函数。投诉通道温度取 0.2 而不是 0.3，因为安抚话术的方差直接变成客诉风险。若某通道需要专属工具（如账单查询接口），在 handle 里按 route 分发即可，路由器本身仍然不碰处理逻辑——"只分诊、不处理"的边界要保持住。

def route_and_handle(query: str) -> dict:
    """完整路由决策。停止条件明确：任何一层做出决策即停止向下判断。"""
    rule_hit = rule_route(query)
    if rule_hit:  # 第一层：规则命中 -> 立即转人工，不再问模型
        return {"route": "human", "reason": "规则命中高危操作",
                "answer": handle(query, "human")}
    cls = classify(query)  # 第二层：分类路由
    intent, confidence = cls["intent"], cls["confidence"]
    if confidence < CONFIDENCE_GATE:  # 第三层：置信度兜底（门槛向"宁可升舱"倾斜）
        return {"route": "strong", "reason": f"置信度 {confidence:.2f} 低于门槛",
                "answer": handle(query, "strong")}
    if intent in ESCALATE_INTENTS:
        return {"route": "escalate", "reason": f"意图 {intent} 走专用通道",
                "answer": handle(query, "escalate", intent)}
    if intent in {"billing", "other"}:  # 高置信度简单意图走轻模型
        return {"route": "cheap", "reason": f"意图 {intent} 高置信度",
                "answer": handle(query, "cheap", intent)}
    return {"route": "strong", "reason": f"意图 {intent} 需强模型",
            "answer": handle(query, "strong")}  # 剩余意图（如 technical）统一走强模型


if __name__ == "__main__":
    queries = [
        "我想重置登录密码",
        "这个月话费怎么多扣了 30 块？",
        "你们这服务太差了，我要投诉！",
        "帮我看看怎么把数据导出成 Excel",
    ]
    for q in queries:
        result = route_and_handle(q)
        print(f"问：{q}\n  路由 -> {result['route']}（{result['reason']}）\n"
              f"  答：{result['answer'][:60]}...\n")

▸ 代码怎么读：route_and_handle 是全系统唯一的决策点，从上到下的分支顺序就是信号优先级：规则 > 置信度 > 意图专用通道 > 默认通道，任何一层命中即 return——这个"决策即停止"的形状让执行路径一眼可审计，每条请求的 reason 字段就是"为什么走这条通道"的审计记录。注意分支次序的工程含义：置信度检查必须排在意图分支之前，否则一个"高置信度的错误意图"会绕过兜底直奔弱通道。改路由策略只动这个函数；四条测试 query 分别覆盖 human/cheap/escalate 三条通道与一次意图分类，跑通它们是对路由表最小的冒烟测试。

2.6.2 框架差异速览（LangGraph 条件边）

从本版起，原 LangGraph 完整程序收敛为速览表：LangGraph（langgraph 0.2.x / langchain-openai 0.2.x，API 以所用版本官方文档为准）对路由模式的正统表达是 conditional edges——节点产出决策依据，条件函数返回下一个节点名，与本节 route_and_handle 的"决策集中一处"完全同构：

本章概念 LangGraph 对应 一句话差异
路由决策集中一处 add_conditional_edges("classify", route_fn, mapping) 条件函数只读状态、返回下一节点名，改路由只改这个函数
分类节点 add_node("classify", fn) 节点即"状态 → 部分状态更新"的函数；fail-open 写在节点内的 try/except
三条模型通道 add_node("cheap"/"strong"/"escalate", …) 每通道一个节点，各自独立提示与模型，互不影响
路由依据 TypedDict RouteState（intent/confidence 字段） 路由依据显式入状态、类型可查，等价于 classify 的返回 dict
通道终点 add_edge("cheap", END) 等三条边 图结构表达"通道执行完即结束"，无需 if-else 串联
人工/兜底通道 再加 add_node("human", …) 与一条条件边 高危规则层也表达成图的一条边，决策优先级由条件函数保持

选择建议：路由决策本身就是图的一个节点加一个条件函数时，LangGraph 的表达最贴合；但它不提供 fail-open、置信度校准这类路由专属语义——这些仍要像 2.6.1 那样写在自己的节点函数里。

2.6.3 生产化改造清单

  • 错误处理：分类器输出解析失败、超时、限流统一 fail-open 到默认强通道；fail-open 事件要计数上报。
  • 超时：路由决策本身设硬超时（如 500 毫秒），超时视同低置信度直走兜底通道，路由器永远不成为新的延迟瓶颈。
  • 并发：级联路由的"先弱后强"会放大峰值 QPS，两段模型池要分别设配额与排队策略。
  • 缓存：对相同或高相似输入缓存路由决策；注意缓存键要含路由规则版本号，规则更新即失效。
  • 可观测：记录每条请求的路由决策、决策依据（规则名/置信度）与最终满意度；通道流量占比与兜底率是漂移的前哨指标。
  • 成本控制：级联要审计"升级通道捕获率"——升级后确有问题被拦住的比例长期为零时，重新评估是否值得多付一次轻模型调用。
  • 回灌机制：把人工纠正过的误路由样本回流为分类器/语义规则的训练或示例数据，形成月度迭代闭环。

2.7 概览 / 核心要点 / 结论

2.7.1 本章小结

路由把"这个请求是什么、该由谁处理"从处理逻辑中拆出来，变成一个独立、可监控、可迭代的决策点。它的技术谱系从对话系统时代的意图分类一路演进到 FrugalGPT 与 RouteLLM 的成本级联，四种实现——规则、分类器、语义相似度、级联——分别对应不同的维护成本与误路由代价，选择标准是"用误路由代价能承受的最轻方案"。路由的全部设计张力在于错误的不对称：分错的代价两侧常常差一个数量级，因此置信度兜底、fail-open 与漂移监控不是可选项，而是路由器能否上生产的资格线。

2.7.2 核心要点

  • 路由器只做分诊不做处理；决策逻辑集中在一处，改路由不改通道。
  • 四种路由器按维护成本排序：规则 < 分类器 < 语义 < 级联（学习型），先轻后重。
  • 误路由成本不对称，置信度门槛向"宁可多升舱"倾斜，兜底通道配最强模型。
  • 任何路由器都要有"我不知道"出口；解析失败 fail-open 到强模型，不要 fail-close。
  • 级联的升级判据必须含独立于弱模型自我报告的机械校验，防"自信地错"。
  • 监控路由分布本身：通道占比突变是域漂移的最早信号，先于业务指标恶化。
  • 通道类别不稳定的产品早期不要上路由，先在一个通道里积累流量认知。

2.7.3 结论

路由是智能体系统从"单一管道"走向"分级服务"的分水岭：它用一次廉价的判断，换回口径、成本与风险三个维度的解耦。好的路由器往往是无名的——它让简单请求安静地走便宜通道、让危险请求在入口就被摘走，系统整体因此显得又快又稳。维护这份安静的，是置信度兜底的纪律与对路由分布持续的注视。
