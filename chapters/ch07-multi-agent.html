第一部分 · 核心模式

第7章 多智能体协作 Multi-Agent Collaboration

把单个智能体拆成角色化团队，用显式消息协议与合适的拓扑结构完成单点难以胜任的大型任务。

一句话定义：让多个各自拥有独立上下文、角色提示与工具集的智能体，通过结构化消息交换与约定的拓扑结构协同完成单个智能体难以独立胜任的任务。 解决什么问题：单智能体的上下文窗口被多职责挤爆、注意力稀释、工具选择混乱、无法并行也缺乏独立制衡 ｜ 适用场景：任务可按职责拆分、环节间需要交叉验证、需要并行加速或权限分层的复杂工作流 ｜ 核心机制：角色分化 + 消息协议 + 协调拓扑 + 预算与终止控制 ｜ 代价：token 成倍增加、错误沿链路放大、调试与可观测复杂度显著上升。

本章速读　多智能体协作把"全能单体"拆成各带独立上下文、角色提示与工具集的专家团队，用结构化消息与拓扑协同。它治四类痛：上下文拥挤、自审失灵、工具混乱、无法并行。三步落地：①按正交职责切分角色；②约定消息协议（发送者/类型/关联 ID），失败显式升级；③选拓扑（生产首选星型协调器）并硬编码轮次与费用预算。一条提示能解决、对延迟敏感、要求完全可复现、任务量小——这四种情况别拆。

7.1 模式概述

7.1.1 问题背景：为什么需要这个模式

把一个"调研、分析、写作、审校"全流程塞进一次 LLM 调用，会遇到四类结构性问题。第一是上下文拥挤：系统提示里同时写着三种角色职责，加上中间产物，窗口很快被填满，模型对早期指令的遵从度下降。第二是职责冲突：让写代码的同一个上下文再去客观审查自己的代码，模型天然倾向于为自己辩护——自审几乎必然比独立审查宽松。第三是工具混乱：一个智能体挂十几个工具时，选错工具、错配参数的概率明显上升，而按职责分组后每个智能体只需面对三五个工具。第四是无法并行：单体流程只能串行推进，而拆分后的子任务可以在多个智能体上同时执行。

多智能体协作的思路与软件工程从单体走向服务化一致：不是功能变多了，而是复杂度必须用"分工 + 协议"来管理。每个智能体是一个受控的职责单元——有自己的系统提示（角色）、自己的工具子集、自己的上下文；智能体之间不共享"脑子"，只通过消息交换信息。这样，每个上下文里只出现该角色需要的东西，注意力重新变得集中，权限与风险也可以按角色切分。

需要强调的是：多智能体不是"更多智能体更好"。它是一项有真实成本的架构投资，只有在拆分收益（上下文隔离、专业化、并行、制衡）大于协调成本时才值得做。本章 7.5 节会专门讨论这笔账怎么算。

7.1.2 核心机制：它如何工作

一个可运行的多智能体系统由三部分构成。角色分化：每个智能体由"名字 + 角色提示词 + 工具集 + 可选的模型档位"定义，角色提示词写清职责边界与输出格式，职责之间尽量正交。消息通道：智能体之间交换的是结构化消息而非裸字符串——至少包含发送者、接收者、消息类型（任务/结果/升级）、正文与关联 ID（correlation_id），这是后续追踪、超时控制和审计的基础。协调机制：决定"谁在什么时候把什么消息发给谁"，即通信拓扑（流水线、星型、群聊、层次，见 7.5.1），外加三条硬控制：轮次预算（防止无限互聊）、失败路径（升级而不是静默吞掉）、终止条件（明确何时收敛、何时放弃并如实报告）。

典型执行流是：协调器接收总任务 → 拆解为子任务 → 按子任务性质路由给对应专家 → 专家执行并回传结构化结果 → 协调器聚合，必要时再交评审角色复核一轮。整个过程像一条有质检节点的流水线，而不是一群人自由聊天。

7.1.3 与相邻模式的关系与组合

多智能体协作与多个模式存在亲缘关系。提示链（串行提示接力）可以看作它的退化形态：角色固定、顺序固定、每环只有一次调用。路由与编排模式对应它的星型拓扑：协调器本质上是一个会说话的路由器。反思模式常以"独立评审智能体"的身份嵌入多智能体系统——写作者与批评者分属两个上下文，制衡才真实成立。记忆管理提供多智能体的共享工作区（黑板），让协作不依赖消息全文转发。工具使用模式则为每个角色配置专属工具箱。生产中最常见的组合形态是：星型协调器 + 各专家 + 一个独立评审者 + 共享状态存储。

7.2 源起：它从哪里来

多智能体协作的根比 LLM 早半个世纪。1973 年，MIT 的 Hewitt 等人提出 Actor 模型，首次把计算单元定义为“带邮箱、收发消息的自治实体”——今天“智能体不共享脑子、只传消息”的约定正是它的后代。1980 年出现两类协调原语：Smith 的合同网协议用“招标—投标—中标”分配任务，Hearsay-II 确立了黑板架构。三十年间缓慢演进，直到 LLM 把约定协作的成本降到一句提示：CAMEL 证明两只智能体能自主对话完成任务，AutoGen 把可对话智能体抽象为可编排对象，MetaGPT 与 ChatDev 把团队 SOP 编译成流水线，CrewAI、OpenAI Swarm 与 Google ADK 把编排推进为生产套件。

7.3 发挥的作用：为什么重要

第一，上下文隔离带来的质量提升。每个角色只携带自己需要的指令与材料，模型注意力不再被无关职责稀释；角色提示可以写得更专、更深，相当于把一位通才换成一个专家团队。第二，真实制衡。写作与评审分属两个上下文后，评审者没有"辩护自己产出"的动机偏置，交叉验证才有效。第三，并行与扩展。相互独立的子任务可以并发执行，长尾任务可以按层委托，系统的吞吐随智能体数量伸缩。第四，组织知识的编码载体。SOP 不再是文档而是可执行的角色定义与任务描述——MetaGPT 的核心洞察正在于此：把人类团队的工作程序直接翻译成多智能体流水线。第五，权限与风险的分层。不同角色授予不同工具与数据访问，高危操作收敛到少数受控角色，审计边界清晰。

7.4 实际应用与案例

软件公司式自动开发。 MetaGPT 与 ChatDev 按"产品经理→架构师→工程师→测试"编排角色，前一角色的结构化产物（需求文档、设计文档、代码）作为后一角色的输入。关键设计点：规定每个角色的产出物格式（PRD 表、类图、代码文件），使消息可被下一个角色直接消费，而不是自然语言含糊转述。

研究与写作流水线。 检索员、分析员、写手、审稿人四角色顺序接力，审稿环节允许一次回退修订。关键设计点：检索员只交付带来源的要点清单，写手不得引入清单之外的事实；审稿人独立上下文，只看成品与要点清单做一致性核对。

客服分层升级。 一线通用智能体处理常见问题，识别到退款、投诉等高风险意图时按星型路由升级给对应专家智能体，超出能力边界再转人工。关键设计点：升级（ESCALATE）是一等消息类型，必须带上下文摘要；一线智能体无退款权限，权限随角色走。

代码生成的对抗审查。 开发智能体产出代码后，由独立的测试智能体与安全审查智能体分别攻击。关键设计点：审查智能体不共享开发上下文，只拿代码与需求，避免被开发者的推理过程"带节奏"；两类审查结果合并去重后回传。

数据采集与核验并行。 多个工作智能体并行抓取不同来源，协调器聚合、去重、交校验智能体核数。关键设计点：以 correlation_id 关联同一任务的全部消息；任一 worker 失败不阻塞整体，最终报告如实列出失败子任务。

群聊式头脑风暴与红蓝对抗。 数个立场不同的角色在共享对话中互相质疑，由主持人角色控制发言次序与终止时机。关键设计点：群聊必须有主持人、轮次上限与退出条件，否则会陷入礼貌寒暄的无限循环（见 7.5.4）。

真实世界实例

Anthropic 多智能体研究系统。 Claude 的 Research 功能采用协调器-工作者模式：Claude Opus 4 担任主导智能体、Claude Sonnet 4 担任并行子智能体，在内部研究评测中比单智能体 Opus 4 高出 90.2%，token 用量单独解释了 BrowseComp 评测中 80% 的性能方差；代价同样公开——多智能体系统的 token 消耗约为普通对话的 15 倍。来源：Anthropic 工程博客《How we built our multi-agent research system》（2025-06）。

京东 OxyGent。 京东零售开源的多智能体协作框架，把工具、模型与智能体统一抽象为可插拔的原子组件 Oxy，强调全链路决策追溯与弹性扩展，已在京东内部 SOP 流转、RAG 问答、数据分析等场景落地，并在 GAIA 评测中取得 59.14 分、进入开源框架第一梯队。来源：GitHub 仓库与官网。

微软 Magentic-One。 Microsoft Research 2024 年 11 月发布的通用多智能体系统，直接构建在 AutoGen 之上：编排器维护"任务账本/进度账本"双循环，指挥网页浏览、文件操作、编码、终端执行四类专业智能体，在 GAIA 等基准上取得有竞争力的成绩，其编排模式已进入 Microsoft Agent Framework。来源：AutoGen 官方文档与技术报告 arXiv:2411.04468。

7.5 深度讲解

7.5.1 四种通信拓扑及适用性

拓扑是多智能体系统最重要的架构决策，它决定了信息流向、成本结构与故障传播方式。

顺序流水线：角色排成固定序列，上游输出即下游输入。结构最简单、行为最可预测、调试时逐环检查即可；没有协调器，也就没有协调器的幻觉路由问题。代价是全程串行、延迟线性累加，且任何一环的错误都会静默流向下游。适合结构稳定、环节清晰的加工型任务：研报生成、翻译润色、数据清洗。判据是"工作流几乎不变"——如果流程本身需要按输入动态调整，流水线就不合适。

星型协调器（协调器-工作者）：一个协调器持有全局视图，负责拆解、路由、聚合；工作者之间不直接通信。控制流清晰、上下文可裁剪（工作者只看到自己的子任务而非全部对话）、权限可集中管控，是生产环境的首选形态。代价是协调器成为单点：它路由错了，整个系统就错了；它上下文膨胀了，全局就慢了。适合任务分解结构事先不可完全预知的场景。

群聊式：所有智能体共享一份消息历史，轮流发言，通常配一个主持人控制次序与终止。好处是信息充分共享、可以相互激发与纠错，适合头脑风暴、多视角评估；坏处非常实际——每条消息所有成员都要"看一遍"，token 成本随人数近似平方增长，且容易出现串话、跑题与人格漂移。人数控制在 3~5 个、并强制主持人每轮做小结压缩历史，是群聊能用的前提。

层次式：协调器之下再有子协调器，形成树状委托链，即"经理—组长—组员"。它可以承载远超前两种拓扑的规模（例如跨几十个仓库的重构任务按目录树分层委托），权限也天然分层。代价是信息在层级间逐级损耗——子协调器只向上汇报摘要，顶层看到的永远是二手信息；延迟也随层级叠加。适合任务规模大到单层协调器拆不动、且子任务域边界清晰的场景。

7.5.2 消息协议设计

智能体间传递裸字符串是新手最常见的坑：接收方要靠猜测理解"这是任务还是闲聊、完成后回给谁、和哪个任务相关"。最小可行的消息结构只需五个字段——sender、recipient、type（TASK/RESULT/ESCALATE/QUERY）、content、correlation_id。类型字段让失败成为一等公民：专家执行失败时不返回含糊的文本，而是一显式的 ESCALATE，由协调器决定重试、换人或上报。关联 ID 让同一任务的完整消息链可以被检索与审计，这在事后归因"这个错误结论是谁给的"时不可或缺。

历史在此处值得回望：合同网协议 1980 年提出的"招标—投标—中标"，本质就是让具备不同能力的智能体先声明能力，再按任务匹配。今天协调器用 LLM 做路由，等于把"投标"换成了"模型读角色描述做选择"——当路由准确率不足时，老办法依然有效：让各智能体对子任务做可行性自评（自评即投标），协调器按自评与历史成功率分配。

7.5.3 上下文经济学

多智能体的多数成本问题可以归结为一句话：传结论，不传过程。协调器向写手交付分析结果时，应传分析员的结论要点而非其完整推理记录；层次式组织中子协调器向上汇报摘要而非流水账。群聊拓扑的平方成本，正是因为它默认"人人看全部过程"。与之相对的设计是共享工作区（黑板）：把大块中间产物写到状态存储里，消息里只带指针与摘要，需要时按需读取——这也是黑板架构在 LLM 时代重新流行的原因。协调器另一项隐性价值是上下文裁剪：工作者拿到的提示由协调器定制，天然短于"把所有历史都给每个人"。

这笔账有官方数字可对。Anthropic 公开其多智能体研究系统的实测：协调器-工作者架构在内部研究评测中比单智能体 Claude Opus 4 高出 90.2%，但多智能体系统的 token 消耗约为普通聊天的 15 倍（单智能体约 4 倍），且在 BrowseComp 评测上 token 用量一项就解释了 80% 的性能方差（Anthropic 工程博客，2025-06）。两个数字放在一起读，结论相当冷静：收益的大头不是"更多脑子"，而是"更多 token 预算"——多智能体之所以赢，很大程度上是因为它买得起并行探索；并行工具调用确实能把复杂查询的研究时间最多缩短 90%，但那是吞吐收益，不是推理质量收益。另一组实验同样指向"收益来自多样性而非智力"：《More Agents Is All You Need》（arXiv:2402.05120，TMLR）用最朴素的采样-投票让 LLaMA-2-70B 在 GSM8K 上从 54% 升到 74%（40 个智能体）、HumanEval 从 24% 升到 33%，且任务越难相对增益越大（MATH 上 70B 相对增益 120%）——但这套机制单智能体多次采样自投票同样能近似。因此，多数业务问题的第一方案应当是单智能体 + 好工具：便宜一个数量级、延迟更低、行为可复现。多智能体不可替代的收益只剩两项：上下文隔离（真制衡与专业深度）与视角多样性（独立上下文里的真分歧，而非同一上下文里的自我附和）。任务的价值密度（每 token 产出的价值）撑不起 15 倍预算时，协调器写得再漂亮也是亏损架构。

协调开销本身可以量化到调用次数：星型拓扑下一次三子任务运行至少要 1 次拆解 + 3 次路由 + 3 次专家执行 + 1 次聚合 = 8 次 LLM 调用，是单智能体直答的 8 倍起，其中 7 次是纯协调、不直接产出价值；串行链路每多一层协调就多一次往返延迟；错误沿链路放大——每环 95% 准确，五环之后整体约 77%（见 7.5.4）。消息协议、状态同步与错误传播链这三件协调基建在单智能体里根本不存在，拆分前先确认任务值得付这笔"组织税"。演化地看，税的构成也变了：Actor 模型与合同网时代（1973–1995）的工程难题是消息实现本身，LLM 把它降成一句提示词，于是预算控制、路由质量与防幻觉路由这些组织设计问题成了新的成本主体。

7.5.4 失效模式与反模式

礼貌死循环：两个智能体互相感谢、互相转交，轮次耗尽却毫无进展。AutoGen 早期演示中这是高频现象。对策：轮次预算 + 每轮必须产出实质内容的提示约束 + 主持人强裁。责任稀释：多角色都以为别人做了校验，最终报告"完成"但无人真正负责。对策：每个子任务显式指定唯一责任人，验收环节点名列出各角色的交付与缺口。错误串联放大：流水线每环 95% 准确，五环之后整体约 77%。对策：环节之间加廉价校验点（格式断言、抽样复核），把错误就地拦截而不是顺流而下。上下文污染与串话：群聊里一个角色的错误结论被其他角色当成事实引用并扩散。对策：重要结论带"来源角色+置信度"标记，主持人定期做事实小结。角色漂移：多轮之后评审者开始替写手着想，立场失效。对策：每轮调用都重新注入完整角色提示，不要依赖历史保持人设。协调器幻觉路由：把任务派给不相关的专家后得到看似流畅的错误结果。对策：路由输出强约束为白名单之一，并保留关键词兜底与"无人可派即升级"的路径。

7.5.5 何时不要用

满足以下任一条件，请保持单智能体：任务能在一条精心设计的提示加几个工具内解决；对延迟极度敏感（每加一个智能体至少多一次串行 LLM 调用）；要求行为完全确定可复现（多角色交互天然带随机性）；任务量小到协调成本永远收不回。从单智能体升级到多智能体的四个信号是：上下文装不下、职责互相冲突、存在可并行的独立子任务、需要不共享上下文的独立制衡。出现其中两个以上，再开始拆分，且先拆"评审"角色——这是收益最高、风险最低的第一刀。 边界条件可以定量化。经验法则：单次任务的产出价值低于约 50 次基础模型调用成本（星型拓扑最小调用数乘安全系数）时不值得拆；端到端延迟预算紧（实时对话、秒级响应）时，每多一层协调就多一次串行往返，直接出局；任务输入输出都能装进单个 128K 窗口、且不需要独立制衡时，拆分只增加出错面。反之，四个拆分信号（上下文装不下、职责冲突、可并行、需制衡）出现两个以上、且单次任务价值密度高（深度研究、审计、大规模生成）时，15 倍 token 的投资才可能收回。

7.5.6 怎么用：运用判断

适用信号：出现以下任一特征，再考虑拆分——①系统提示里的角色职责开始互相踩（超过两三千字还在加"另外你还负责……"）；②需要不共享上下文的独立评审（自审必然宽松）；③存在可并行的独立子任务、且单次任务价值高；④需要按角色切分权限与审计边界。

维度 星型多智能体 单智能体 + 采样自投票
成本 约 15 倍 token，8 次调用起步 3~5 次采样即有增益
收益来源 上下文隔离、真制衡、并行 采样多样性（统计聚合）
典型失效 幻觉路由、责任稀释、错误串联 多数票盲区（系统性偏见一致时全错）
选它当 子任务异构、需独立评审/权限分层 任务同构、只需提升单点质量

落地三步：①先写单智能体版并跑通一个固定评测集，拿到质量与成本基线；②只拆"独立评审"一个角色（收益风险比最高的一刀），对比基线看质量提升是否配得上成本翻倍；③确认收益真实后，再按星型拓扑补协调器与消息协议，轮次与费用预算硬编码，ESCALATE 路径写进第一版。

7.6 工程落地：核心源码与讲解

7.6.1 框架无关核心源码（按序拼接即完整可运行）

片段 1／4：模块基座与消息协议。

"""第 7 章 核心源码：星型协调器 + 专家 + 显式消息协议（按序拼接 4 片段即可运行）。"""
import json, os, uuid
from dataclasses import dataclass
from openai import OpenAI

client = OpenAI(base_url=os.environ.get("AGENT_LLM_BASE_URL", "https://api.openai.com/v1"),
                api_key=os.environ["AGENT_LLM_API_KEY"])
MODEL = os.environ.get("AGENT_LLM_MODEL", "gpt-4o-mini")

def llm(prompt: str, system: str = "", temperature: float = 0.3) -> str:
    """调用 OpenAI 兼容接口；失败只抛异常，降级决策权交给调用方。"""
    msgs = ([{"role": "system", "content": system}] if system else [])
    msgs.append({"role": "user", "content": prompt})
    resp = client.chat.completions.create(
        model=MODEL, messages=msgs, temperature=temperature)
    return resp.choices[0].message.content or ""

TASK, RESULT, ESCALATE = "TASK", "RESULT", "ESCALATE"

@dataclass
class Message:
    """最小消息信封：结构化消息让失败与审计成为一等公民。"""
    sender: str
    recipient: str
    msg_type: str  # TASK | RESULT | ESCALATE
    content: str
    correlation_id: str  # 串起同一次协作的全部消息，审计的钥匙

▸ 代码怎么读：基座只立一条规矩——失败不吞。llm() 的任何异常都向上抛，降级决策权永远在调用方，这是全书错误处理的统一约定。Message 信封里最关键的是 msg_type 与 correlation_id：前者让失败成为一等公民（TASK/RESULT/ESCALATE 三种类型显式流转），后者把一次协作的全部消息串成可审计的链路，事后才能回答“这个错误结论是谁给的”。要扩展就增加消息类型或字段，不要退回用裸字符串传语义。

片段 2／4：专家智能体与 LLM 路由。

@dataclass
class Agent:
    """专家智能体：固定角色提示 + 单一职责，不做路由也不看全局。"""
    name: str
    role_prompt: str

    def handle(self, task: str) -> str:
        """执行子任务；LLM 失败时返回 ESCALATE 前缀文本，绝不静默丢弃。"""
        try:
            return llm(task, system=self.role_prompt, temperature=0.2)
        except Exception as exc:  # 网络抖动/限流等
            return f"{ESCALATE}: LLM 调用失败（{exc}）"


class Coordinator:
    """星型协调器：负责路由与委派；拆解与聚合见片段 3 的模块级函数。"""
    def __init__(self, specialists: dict[str, Agent], max_turns: int = 5):
        self.specialists, self.max_turns = specialists, max_turns
        self.log: list[Message] = []

    def _route(self, subtask: str) -> Agent | None:
        """LLM 精路由 -> 关键词兜底 -> None 升级；temperature=0 求稳。"""
        roster = "、".join(self.specialists)
        try:
            raw = llm(f"子任务：{subtask}\n可选专家：{roster}\n只回答一个专家名字。",
                      system="你是任务路由器，只输出专家名字本身。", temperature=0.0)
            return next((a for n, a in self.specialists.items() if n in raw), None) \
                or self._keyword_route(subtask)
        except Exception:
            return self._keyword_route(subtask)  # 路由 LLM 失败：关键词兜底

    def _keyword_route(self, subtask: str) -> Agent | None:
        return next((a for n, a in self.specialists.items() if n in subtask), None)

▸ 代码怎么读：Agent.handle 把 LLM 异常转成带 ESCALATE 前缀的文本而不是抛异常对象——因为失败必须能像正常消息一样在智能体之间流转与留痕，抛异常会把降级决策绑死在本函数里。_route 是三层降级链：LLM 精路由 → 关键词粗匹配 → None 上交升级，对应 7.5.4 的“幻觉路由”对策：路由输出只做专家白名单匹配，匹配不上绝不硬派。temperature=0.0 是路由的硬要求——路由要的是稳定，不是创意。

片段 3／4：委派与任务拆解。

def delegate(coord: Coordinator, subtask: str, cid: str) -> str:
    """委派子任务：无专家可派即 ESCALATE；消息全程留日志可审计。"""
    expert = coord._route(subtask)
    if expert is None:
        reason = f"{ESCALATE}: 无匹配专家，子任务挂起：{subtask[:40]}"
        coord.log.append(Message("coordinator", "none", ESCALATE, reason, cid))
        return reason
    coord.log.append(Message("coordinator", expert.name, TASK, subtask, cid))
    answer = expert.handle(subtask)
    mtype = ESCALATE if answer.startswith(ESCALATE) else RESULT
    coord.log.append(Message(expert.name, "coordinator", mtype, answer, cid))
    return answer


def decompose(user_task: str, max_n: int = 3) -> list[str] | None:
    """把总任务拆为子任务列表；解析失败返回 None，交上层降级直答。"""
    try:
        raw = llm(f"把总任务拆成不超过 {max_n} 个可独立完成的子任务，输出 JSON 字符串数组。总任务：{user_task}",
                  system="只输出 JSON 数组。", temperature=0.1)
        parsed = json.loads(raw)
        return [str(s) for s in parsed] if isinstance(parsed, list) and parsed else None
    except Exception:
        return None  # 拆解失败是一等状态，交给上层降级

▸ 代码怎么读：delegate 的约定是“永不抛异常”：无专家可派、专家失败，都返回带 ESCALATE 前缀的文本，让上层能统一处理“部分成功”的局面。decompose 把 JSON 解析失败收敛为 None——把“拆不动”变成一等状态而不是崩溃，上层据此降级直答；max_n=3 是给拆解上的第一道预算闸，子任务越多协调调用线性膨胀。读者最先该改的是 specialists 字典：角色越正交，路由越稳。

片段 4／4：主循环与三条降级路径。

def execute(coord: Coordinator, user_task: str, max_subtasks: int = 3) -> str:
    """主入口：拆解 -> 委派 -> 聚合；三处失败均有诚实降级路径。"""
    cid = uuid.uuid4().hex[:8]
    subtasks = decompose(user_task, max_subtasks)
    if subtasks is None:  # 拆解失败：降级为单智能体直答，并明示降级事实
        try:
            return "（拆解失败，已降级为单智能体直答）\n" + llm(user_task)
        except Exception as exc:
            return f"{ESCALATE}: 拆解失败且直答失败（{exc}）"
    results, escalations = [], 0
    for i, sub in enumerate(subtasks):
        if i >= coord.max_turns:  # 轮次预算：宁可少做，不可失控
            results.append(f"预算用尽，{len(subtasks) - i} 个子任务未执行")
            break
        r = delegate(coord, sub, cid)
        escalations += r.startswith(ESCALATE)
        results.append(f"[子任务{i + 1}] {r}")
    try:  # 聚合失败：如实返回原始结果，不编造总结
        final = llm("整合子任务结果为完整交付物，保留未解决项：\n\n"
                    + "\n\n".join(results), system="你是主编，只整合不新增事实。")
    except Exception as exc:
        final = f"（聚合失败：{exc}）\n" + "\n\n".join(results)
    return final + (f"\n\n[预警] {escalations} 个子任务未解决，请人工介入。"
                    if escalations else "")

if __name__ == "__main__":
    team = {"资料检索员": Agent("资料检索员", "列出要点与公开事实，不虚构来源。"), "分析师": Agent("分析师", "做结构与利弊分析，指出假设与不确定性。")}
    print(execute(Coordinator(team), "为日均百万请求的 API 网关设计限流方案，给出要点"))

▸ 代码怎么读：execute 集中了全部错误路径：拆解失败 → 单智能体直答（并明示降级事实，不假装多智能体跑过）；专家失败 → 按 ESCALATE 计数并在交付物尾部预警；聚合失败 → 如实返回原始子结果而不编造总结。轮次预算 i >= coord.max_turns 宁可少做不可失控，直指 7.5.4 的礼貌死循环。聚合放在最后一步是因为它最贵——只有全部子结果就绪才值得花这一次调用。

同一"协调器-专家"能力在主流框架中的对应物（版本迭代快，类名以官方文档为准）：

框架 编排入口 与本章骨架的差异

7.6.3 生产化改造清单

  • 错误处理：每类失败（路由失败、专家失败、聚合失败）都定义显式降级路径与 ESCALATE 上报，禁止静默吞异常。
  • 超时与重试：每次 LLM 调用设超时；可重试错误（限流）做指数退避，最多重试 1~2 次。
  • 预算控制：轮次上限、token 上限、费用上限三层预算，超限即收敛并如实报告未完成项。
  • 并发执行：相互独立的子任务用线程池/asyncio 并行委派，聚合阶段统一汇合。
  • 缓存：相同子任务文本 + 角色的调用做缓存，流水线重跑时省掉未变化环节。
  • 可观测：全量消息日志带 correlation_id；按角色统计调用量、失败率与延迟，协调器路由决策留痕。
  • 成本控制：消息传摘要不传全文；群聊拓扑限定人数并做历史压缩；子任务结果持久化到共享存储，避免随消息反复携带。
  • 评测回归：把典型任务做成固定评测集，改角色提示或拓扑后跑回归，防止"改好一处坏三处"。

7.7 概览 / 核心要点 / 结论

本章小结

多智能体协作把"分工与协调"这一组织学问题引入 LLM 工程：角色分化提供专注的上下文，结构化消息协议让失败与审计成为一等公民，四种拓扑（流水线、星型、群聊、层次）各有明确的适用边界与失效方式。它的学术根脉从 Actor 模型、合同网与黑板系统一路延伸到 AutoGen、CrewAI 与 Google ADK；LLM 降低的是通信实现成本，没有降低的是组织设计成本。先问"该不该拆"，再问"怎么拆"：上下文过载、职责冲突、可并行、需制衡，四个信号同时出现两个以上，才是引入多智能体的时机。

核心要点

  • 多智能体的本质收益是上下文隔离、专业化、并行与独立制衡，不是"数量多"。
  • 跨智能体通信必须走结构化消息（发送者/接收者/类型/正文/关联 ID），失败用 ESCALATE 显式上报。
  • 四种拓扑的取舍核心是成本与失效方式：流水线可预测、星型可控、群聊昂贵、层次可扩展。
  • 传结论不传过程；大块中间产物走共享工作区，消息里带指针与摘要。
  • 每轮重新注入角色提示，防止多轮之后的角色漂移；评审者与执行者绝不共享上下文。
  • 错误会沿链路放大：环节之间要有廉价校验点，预算（轮次/费用）要硬编码。
  • 先从"独立评审角色"拆起，这是收益风险比最高的第一步。

结论

多智能体协作不是把一个提示拆成几个提示的语法游戏，而是把系统复杂度从"一个巨大上下文"迁移到"协议与拓扑"上的架构决策。写好一个协调器、三条专家角色与一条升级路径，往往比堆十个角色更能解决真实问题；衡量设计是否成功，看的不是角色数量，而是每个上下文是否更专注、每条消息是否可审计、每次失败是否有人接住。掌握了这个判断尺度，四种拓扑与各家框架都只是表达工具。
