第三部分 · 容错与扩展

第13章 人在回路 Human-in-the-Loop

用介入点、置信度升级路由与可恢复的审批闸门，把人放进智能体决策链的关键位置，让高风险动作有人兜底、有据可查。

一句话定义：人在回路让智能体在关键决策点上暂停并把裁决权交给人类——事前审批、事中暂停或事后抽检——人给出决定后流程从断点恢复，全程留痕可审计。 解决什么问题：模型会错且错得自信，而有些动作不可逆 ｜ 适用场景：高风险副作用动作、低置信输出、合规问责要求、需要人类反馈改进系统的场景 ｜ 核心机制：介入点设计 + 置信度升级路由 + 审批闸门协议 + 断点恢复 + 审计留痕 ｜ 代价：人的切换成本与等待成本、审批疲劳、流程吞吐上限被人手办天化。

本章速读　人在回路在不可逆动作前设闸门：模型暂停、人裁决、断点恢复、全程留痕。三步走——选介入点（事前审批/事中暂停/事后抽检），按置信度双阈值分流（高置信自动、低置信转人工），审批请求带证据、裁决用结构化返回。人是最贵的资源，规则能拦的不进人审；驳回率趋零说明闸门已橡皮图章化。完全可逆、低代价、时延极敏的场景别用。

13.1 模式概述

13.1.1 问题背景：为什么需要这个模式

前面各章给了智能体一整套自治能力：工具使用让它能执行动作，规划让它能走长流程，异常处理让它能在故障后自救。但自治有一条隐含前提——错了可以重试、可以补偿、可以回滚。现实里有一类动作不满足这个前提：给客户发的退款不可撤回，发出去的邮件收不回来，执行过的 rm -rf 没有第二次机会。模型在这类动作上的错误不是"重跑一次"能覆盖的，而模型的输出又天然带不确定性，且错得毫无心理负担——它会用同样流畅的语气给出正确答案和灾难性答案。这时系统需要的不是一个更聪明的模型，而是一个否决权：在不可逆动作发生之前，把决定权交还给承担后果的人。

第二个动因是信任的建立过程。一个新上线的智能体系统，没有历史数据证明它可靠，全自动化等于拿生产环境做实验；合理的路径是先让人盯住关键环节，用积累的实测数据逐步放宽自动化的边界。第三个动因是问责：医疗、金融、法律等行业里，"算法决定的"不是免责理由，监管要求每个决策链上有一个可追责的主体。人在回路回答的就是这个问题——不是"人要不要参与"，而是"人在哪个位置、以什么成本、按什么规则参与"。

13.1.2 核心机制：它如何工作

一套完整的人在回路机制由五个部件组成。介入点：决定"在哪里打断"——副作用执行前的审批闸门、执行中途的暂停协商、执行完成后的抽样复核，三者拦截力递减、摩擦也递减。置信度路由：决定"谁该被打断"——模型对每个输出给出置信度，高置信自动通过，中置信放行但进抽检池，低置信挂起转人工；路由的本质是把稀缺的人工注意力分配给错误代价最高的样本。闸门协议：决定"打断时呈现什么、人返回什么"——审批请求必须携带让人类能独立判断的证据（上下文、模型理由、备选项），人类返回的裁决是结构化的（批准/驳回/修正），而不是一句模糊的"嗯"。断点恢复：决定"暂停之后怎么续"——挂起不等于丢弃，流程状态要持久化，人的裁决以恢复信号的形式注回流程，执行从断点继续。审计留痕：每个分流决策和人工裁决都记录谁、何时、依据什么、改了什么——这既是合规要求，也是后续调优阈值和训练模型的数据来源。

13.1.3 与相邻模式的关系与组合

与路由模式的关系是特化：置信度升级路由就是把路由的判据从"任务类型"换成"确信程度与风险等级"，低置信工单被路由到一类特殊的处理者——人。与异常处理（第 12 章）的关系是分层：重试、熔断、降级解决"系统自己能不能扛"，升级（escalation）是异常处理的最后一层，扛不住的交给外部兜底者。与反思模式的关系是审稿人换了人：反思让模型自审，人在回路让人类审——人的审稿更贵也更可靠，通常用在反思无法自证的高风险环节。与多智能体协作的关系是"评审智能体"是人审的低成本近似：模型评审员挡掉八成明显问题，剩下两成疑难才值得人看。与记忆模式的关系是反馈的归宿：人工修正的每一条裁决都可以沉淀为记忆、少样本示例或微调数据——这正是 RLHF 的思路在工程侧的回声。

13.2 源起：它从哪里来

人在回路不是 AI 的发明，而是高风险行业纪律的移植：1935 年波音 Model 299 坠机催生飞行检查单，核电业随后有双人复核，确立“不可逆动作前强制人工确认”的原型。人因工程把它变成科学问题：NASA 记录了自动化下人的监控退化，1999 年 Skitka 等人的实验给自动化偏见下了可检验定义。机器学习侧相反：主动学习把“人看哪些样本”变成统计问题，Christiano 等人证明偏好反馈可替代奖励函数，经 InstructGPT 工程化、ChatGPT 触达大众，Constitutional AI 再以 AI 反馈替代标注。今天的功课是合流：模型侧少靠逐件人审，流程侧让人审花在刀刃上。

13.3 发挥的作用：为什么重要

第一，错误代价的保险机制。智能体系统的错误率永远不可能降到零，人在回路做的事是把"错误发生"和"错误造成损失"解耦：低置信输出在造成不可逆后果之前被拦截，一次人工裁决的成本远低于一次事故的善后成本。第二，冷启动期的信任建设。系统上线初期人工介入密度高，随着实测准确率数据积累逐步放宽阈值——"自动化率从 60% 提升到 95%"是有据可依的渐进过程，而不是拍脑袋全量放开。第三，数据飞轮的起点。人工裁决天然是高质量标注：审批人修正的每个标签、驳回的每条输出，都是带真实分布的反馈数据，可以直接回流成评估集、少样本示例或微调语料——RLHF 谱系的全部工作都建立在"人类愿意提供反馈"这个前提上。第四，合规与问责的落点。监管者问"这个决定谁负责"时，审计日志里有一条明确的记录：系统给出的建议、置信度多少、哪位审批人基于什么批准了它。没有这条记录，系统在任何受监管行业的落地都会被卡住。

13.4 实际应用与案例

编码智能体的命令审批门。 2025 年起的主流编码智能体在执行 shell 命令前默认弹出确认：呈现命令原文与影响范围，开发者批准才执行，也可配置白名单让只读命令直通。关键设计点：写操作默认拦截、只读操作白名单放行；审批界面直接给出"这条命令会改哪些文件"，降低预判成本。

客服工单分类升级。 模型把工单分类到退款、物流、产品质量等队列，低置信工单挂起转人工席，人工修正后的标签回流为训练数据。关键设计点：升级时把工单全文、模型候选标签与理由一起呈现给人工席，人工席可批准也可改标签；升级率本身就是模型健康度指标。

内容发布审核流水线。 自动审核通过的直接发布，边缘内容进人工复核队列，复核员按风险等级排序处理。关键设计点：抽检池按风险而非按数量采样；复核决定带标签（同意发布/驳回/降权），每周复盘自动通过与人工驳回的分歧样本。

金融风控交易拦截。 反洗钱模型对交易打分，超过阈值自动放行，可疑交易进调查员队列挂起账户动作直到人工裁决。关键设计点：挂起期间资金动作冻结但信息查询不受影响；每条拦截都有调查结论回流，假阳性率进入模型迭代。

医疗影像辅助诊断。 模型输出病灶标注与置信度，高置信标记供医生复核，低置信切片额外标注"建议第二意见"。关键设计点：系统的角色是"标注建议者"而非"诊断者"，最终裁决与签名责任永远在医生； disagreements（医生改动模型标注的比例）被系统记录用于持续改进。

数据标注主动学习闭环。 训练数据生产中，模型对未标注样本预测并给出不确定性，不确定性最高的样本优先送人工标注。关键设计点：用委员会分歧（ensemble disagreement）而非单一模型置信度做不确定性估计更稳；标注预算固定时，这个排序能让同等人时换到更高的模型质量。

真实世界实例

Claude Code 与 Codex CLI：编码智能体的命令审批门。 两款主流编码智能体都把"执行前确认"做成了默认交互：Claude Code 的 default 模式在文件写入与命令执行前弹出确认，常用只读操作可经 settings.json 白名单放行，高危命令（如 rm）在几乎所有模式下都会拦到人工；Codex CLI 把"审批策略"（untrusted/on-failure/on-request/never）与"沙箱档位"（read-only/workspace-write/danger-full-access）正交组合——未受信任的目录默认只读，越出沙箱的操作必须人工批准，OpenAI 还公开了企业内部安全运行 Codex 的配置实践。这正是"升级梯子先机器后人"的产品化形态：白名单是廉价的第一层，人工审批只接沙箱外的漏网请求。

GitHub Copilot coding agent：提交 PR 之后人审与合并。 把 issue 指派给 Copilot 后，它在后台自主干活并开出一个草稿 PR，随即指派人类开发者审查；人可在 PR 里评论、要求返工，批准与合并权始终在人手里——"生成"与"合入"被流程强制分离。见 GitHub 官方博客（2025-08）。它是"事后抽检 + 事前合并闸门"的组合：CI 与 AI 评审先跑，人只裁最终合入这一道门。

OpenAI Operator：敏感站点强制确认与 watch mode。 浏览器操作 agent Operator（2025 年 1 月发布，后并入 ChatGPT agent）为不可逆动作设了多层闸门：提交订单、发送邮件等有外部副作用的重大动作前必须请求用户批准；邮箱、金融类敏感站点进入 watch mode，要求用户紧盯每一步操作；银行业务这类高风险任务则直接拒接。见 OpenAI 官方发布公告。其系统卡还公开了按"风险严重度 × 可逆性"给动作分级、逐级配置人工介入的策略设计——与 13.5.1 的介入点选型判据同构。

13.5 深度讲解

13.5.1 介入点设计：事前审批、事中暂停、事后抽检

介入点是人在回路最重要的架构决策，三个位置构成一条拦截力递减、摩擦也递减的谱系。事前审批把闸门放在副作用之前：动作尚未发生，人可以否决、修改或改道，拦截力最强；代价是人必须在没有结果的情况下预判后果，审批请求的信息质量决定一切——"执行以下 SQL"和"执行以下 SQL，它将删除 orders 表约 3 万行，来自工单 T-1042 的清理需求"是两种审批体验。事中暂停允许流程走到中间某一步再打断：先让系统把上下文准备充分，人在信息最全的时点介入，裁决后从断点恢复；LangGraph 的 interrupt() 语义正是为此设计——暂停时图状态连同"要问人的问题"一起存入检查点，恢复时人的裁决作为 interrupt() 的返回值注回，被中断的节点会从头重跑。事后抽检先放行后审查：系统全速运行，人工按风险加权的比例抽样复核，发现问题再触发召回或修正流程；它的风险窗口（错误产出已生效的时间长度）是三种位置里最长的，因此只适合错误可撤销、扩散速度慢的动作。

选型判据是三个变量的乘积：动作可逆性（不可逆→必须事前）、单次错误代价（代价越高→介入点越靠前）、时延容忍（不可等待→事后抽检或降级自动）。生产系统通常三者混编：写操作事前审批、分析类输出事中暂停复核、发布类内容事后抽检，同一张流程图上三段并存。一个常见错误是把所有人工介入都做成事前审批——拦截力是够了，但人的带宽被低风险请求淹没后，真正的高风险请求反而得不到认真审查（见 13.5.3）。

13.5.2 置信度升级路由：低置信转人工

升级路由的核心公式是：人工注意力应该流向错误代价高且模型确信度低的样本。实现上是双阈值三档位：置信度高于 AUTO_THRESHOLD 的自动执行；低于 ESCALATE_THRESHOLD 的挂起转人工；中间档自动执行但进抽检池。双阈值的价值在中间档：单阈值系统里"不升级"等于"免检"，而中间档恰恰是错误率上升最快的区域——模型"有点拿不准"的输出比"完全拿不准"的输出更频繁，也更容易蒙混过关。

两个工程细节决定路由是否真的有效。其一，置信度必须校准。模型自报的置信度（让它输出 0-1 的数）系统性过自信，直接用会让人审池里塞满其实不错的样本；校准手段包括：用保留集测每个分数段的经验准确率再映射（等值回归分箱）、用多次采样的自洽率（self-consistency）代替单次自白、用独立验证器模型打分。其二，路由判据要乘上风险权重，不只看"模型有多不确定"，还要看"这里错了多贵"：同样的置信度，涉及资金动作的工单应该比咨询类工单的升级阈值高得多。形式化地说，样本升级的期望收益是"人审纠错挽回的期望损失"减去"人审成本"，阈值应该让边际样本的期望收益为零——这也是主动学习"信息量"判据的风险加权版本：人该看的不是模型最难懂的样本，而是错了最伤的样本。

校准为什么是前提，有官方证据可引。OpenAI 在 GPT-4 技术报告中给出了一组反差鲜明的事实：预训练基模型的校准近乎完美——它预测"我有 70% 把握"时正确率确实接近 70%；但经过 RLHF 后训练，校准显著退化（官方原话是"calibration is reduced"，报告图 8 中校准曲线明显偏离对角线）。原因是 RLHF 的奖励来自人类偏好，而人类评分员天然偏爱听起来果断自信的回答。工程含义直白：模型说"90% 置信"时，真实正确率完全可能只有六成——升级路由的阈值必须画在校准曲线上，而不是画在自报分数上。度量工具就是期望校准误差（ECE）：把自报置信度分箱，逐箱算"平均自报置信度与真实准确率之差"再加权求和；ECE 大的模型，先做分箱再映射（或换自洽率信号），然后才配做路由的判据。

13.5.3 审批疲劳与自动化偏见

先说一个反直觉的事实：给系统加人审并不必然更安全。大家默认"多一道人工确认总归多一道保险"，工程与实验事实是——一个被淹没、被训练出条件反射的审批人，拦截力可以低到近乎归零，而这道门还在制造"有人把关"的错觉，让上游放心地加大自动化力度。人在回路最大的敌人不是模型出错，而是人停止思考。Skitka、Mosier 与 Burdick 1999 年的实验给出了量化证据：在模拟飞行任务中，配了"非常可靠但非完美"自动辅助的实验组，整体监控表现反而差于无辅助组——漏报条件下，有辅助组正确识别并响应关键事件的比例仅约 59%，无辅助组为 97%（DOI）；错误分两类——omission（自动化没提示的事就没人管）与 commission（自动化建议与训练和其他可靠信息源冲突时仍然照办）。这不是实验室孤例，真实审批流给出的数据更冷：van der Sijs 等人对药物安全警报的系统综述发现，临床医生覆盖（override）了 49%-96% 的警报，连严重过量用药这类高危警报也有约四分之一被覆盖（转引自 JAMIA 系统综述）。早在 80 年代玻璃驾驶舱普及期，NASA 的人因研究（如 Wiener 1989 年报告）就记录了同类现象，Parasuraman 等人 1993 年将其命名为"自动化诱发的自满"（complacency）。翻译到审批场景：审批人看到第 200 条连续通过的请求后，第 201 条的批准动作退化成条件反射；系统的拦截门还在，拦截力已经归零。

对策是一组互相配合的制度设计。审批请求携带反方信息：呈现模型理由的同时呈现疑点（"该收件人不在历史往来名单中"），强制审批人做的是判断而非确认。限额与分流：升级率超过人工带宽时，正确动作是提高自动阈值或缩小系统负责的范围，而不是让审批人超载——超载的审批门比没有更糟，因为它制造了"有人把关"的错觉。金标混入：向审批流定期注入已知答案的测试样本，度量审批人的真实驳回准确率，审批质量本身成为被监控的指标。驳回率告警：驳回率长期趋近零，几乎必然意味着审批门已橡皮图章化，应当触发阈值与策略复盘。责任分离：配置审批白名单的人与日常点批准的人不应是同一人，防止自己给自己开免检通道。

这组对策里有实验背书的是"让审批人对结果负责"：Skitka 等人 2000 年的后续实验发现，让被试对整体表现或决策准确性负责（accountable）能显著降低自动化偏见的发生率（DOI）。工程翻译：审批界面应展示"你上个月驳回了多少、抽检复核发现你漏放了多少"，让每个审批人的历史质量可见——被看见的责任感是可度量的拦截力。

13.5.4 批准成本经济学

人工审批是按人时计价的稀缺资源，流程设计应该像对待 API 配额一样对待它。一次审批的真实成本远超"看一眼"：上下文切换成本（审批人放下手头工作）、等待成本（任务挂起期间业务停摆）、积压成本（审批队列越排越长，低优先级任务的时延失控）。把这些折算成账，很多"加个审批门"的决策会变成"先加校验规则，拦截不了的再升级"——机器校验一次几毫秒、成本趋近于零，能拦掉的请求就不该消耗人时。

这引出一个可操作的分层原则：升级梯子上每一层都先问"能不能用更便宜的下一层挡掉"。第一层是确定性校验（schema、枚举、数值范围），第二层是规则引擎（黑名单、限额、时段），第三层是廉价模型审核，最后才是人。人只出现在前几层的漏网之鱼上。反过来，省审批成本也有底线：涉及不可逆且高代价的动作，再贵的人审也不能省——这笔账的正确算法是"审批成本"对比"期望事故损失"，而不是对比"零"。另外，审批预算应该显式化管理：每天多少人时、按什么优先级分配、超预算时的降级策略是什么（转批处理？提高阈值？暂停非关键自动化？），这些写在运维手册里，而不是等人排满了再临时想。

13.5.5 审计留痕：不只是合规要求

审计日志在人在回路系统里承担四重职能。问责：每条被拦截或放行的动作都能回答"系统建议了什么、置信度多少、谁批准的、依据是什么"。复盘：升级样本是人审与模型分歧最集中的地方，定期复盘分歧样本是发现模型盲区性价比最高的手段。调参：升级率、抽检命中率、人工驳回率的历史曲线，是调整双阈值和介入点最直接的依据——没有留痕的调参只能靠感觉。再训练：人工修正过的样本是最贵的训练数据，没有留痕就等于每修正一条丢一条。

最小审计条目应包含：时间戳、动作类型（AUTO/SAMPLE/ESCALATE/APPROVE/REJECT）、对象标识、系统侧证据（输出、置信度、理由）、人工侧信息（审批人 ID、裁决、修正内容）。工程上有两条硬要求：一是不可篡改——审计日志只追加不修改，敏感场景写入 WORM 存储或区块链式哈希链；二是完整可回放——给定审计日志，应能离线重建任意一条工单从进入到裁决的完整决策链，回放不通的审计日志等于没写。最后别忘了审批人也在被审计：审批时延、驳回率、与后续事实（如客户二次投诉）的一致性，都是审批质量的度量维度。

13.5.6 失效模式与何时不要用

四种典型反模式。伪审批：流程上有人审环节，但审批人平均停留时间不足两秒，UI 上连上下文都不展示——这是用形式满足合规、用橡皮图章替代判断，事故复盘时它制造的责任错觉比没有审批更危险。审批替代校验：本可以用确定性规则拦下的请求（格式错误、超限、黑名单）全部涌向人工，把人审带宽消耗在机器擅长的判断上。全有或全无：要么全自动裸奔，要么凡事都请示——没有中间档位和渐进放行机制，系统永远停在"不可信"或"赌博"两个极端。单点人审：唯一审批人休假，升级队列无限积压，挂起任务把整个业务流程拖死——人审入口必须有替代人与超时升级策略。

何时可以不用这个模式：动作完全可逆且代价低（读查询、草稿生成），高频低风险环节挂人工闸门纯属自毁；模型在目标分布上的实测错误率低到期望损失可以忽略，且错误可检测可回滚；流程对时延极度敏感（毫秒级交易、实时控制），人工介入在物理上不可行——此时安全性应靠事前的规则约束与设计收敛来保证，而不是靠事中的人。判断的统一的尺子始终是期望损失：介入点的价值等于"拦截的错误期望损失"减去"人的成本加流程摩擦"，算得过来才加。

边界条件可以算成一笔人时账。假设单次人工裁决平均耗时 90 秒（读证据包加给结论），一名审批人每天有效投入 4 小时人审，日吞吐上限约 160 单——这意味着日请求量乘以升级率超过 160 的那一刻，审批门必然积压：日 10 万单的系统升级率哪怕只有 0.5%，也是每天 500 单排队。所以"该不该加人审"的第二把尺子是规模：流量小的时候双阈值路由是安全网，流量上来之后它先变成瓶颈、再变成橡皮图章（积压逼人放行）。同理，校准有半衰期——模型升级、产品改版、用户构成变化都会让旧阈值失真，阈值必须随分布漂移重标定，而不是一次调好永久沿用。

13.5.7 怎么用：运用判断

适用信号。出现以下特征中的两到三条，就该认真考虑这个模式：动作清单里存在不可逆项（对外发送、资金划转、删除、法务承诺）；模型输出的实测错误率还撑不起全自动化（上线初期几乎必然如此）；行业有问责要求，监管问得出"这个决定谁批的"；人工裁决的样本天然稀缺且贵（医疗、金融），错一个的代价远高于问一次；你在计划用人工反馈持续改进系统——顺带的收益是裁决数据回流成评估集与训练语料。反过来，全可逆、高吞吐、毫秒级时延三占其二，就该去 13.5.6 找替代方案。

与最近替代方案的对比。人在回路最常被拿来替代的是两条路：全自动化加异常兜底（第 12 章），以及模型自审（反思模式，第 6 章）。

维度 人在回路 全自动 + 异常兜底 模型自审（反思/评审智能体）
拦截不可逆错误 最强（副作用前可否决） 弱（只能事后补偿/回滚） 中（依赖评审模型自身不犯同类错）
单位成本 最高（人时 + 等待） 低（机器成本） 中（多次推理成本）
吞吐上限 被人手办天化 机器容量 机器容量
适用位置 高风险低频决策点 高频低风险全流程 高频流程中的初筛层

三者不是互斥选项而是分层：反思挡掉八成明显问题，异常处理兜住机器故障，人只裁决前两层漏掉的高风险样本——这正是 13.5.4"升级梯子"的组合用法。

落地三步。第一步，给动作分级：把系统的全部对外动作按"可逆性 × 单次代价"列表排序，圈出必须事前审批的一小撮（通常不到 10%）。第二步，搭最小闸门：为这一小撮动作实现挂起-裁决-恢复（可直接用 13.6 的骨架），审计字段照 13.5.5 的最小条目落库，人工修正样本自动入评估集。第三步，用量化指标养它：升级率、审批时延、驳回率、金标混入命中率四条曲线每周看——驳回率趋零触发阈值复盘，积压超限触发升级梯子降级；实测数据积累三个月后再决定放宽还是收紧阈值，让自动化率的每一步提升都有据可依。

13.6 工程落地：核心源码与讲解

13.6.1 核心源码与讲解（框架无关实现）

本节把置信度升级工作流的主程序拆成四个片段：环境与模型接入、数据结构与人工闸门、三档路由主流程、演示与审计回放。四个片段按序拼接即完整可运行程序（依赖 pip install openai，环境变量见片段一）。优先保留的是骨架决策与错误路径：双阈值三档分流、挂起与恢复、两条失败路径的降级转人工、审计留痕，一个都不少。

"""第 13 章 框架无关实现·片段 1/4：环境与模型接入。按序拼接四片段即完整可运行程序
（依赖 pip install openai 与三个环境变量，见 llm()/client）。"""
from __future__ import annotations
import json
import os
from dataclasses import dataclass, field
from datetime import datetime, timezone
from openai import OpenAI

client = OpenAI(
    base_url=os.environ.get("AGENT_LLM_BASE_URL", "https://api.openai.com/v1"),
    api_key=os.environ["AGENT_LLM_API_KEY"],
)
MODEL = os.environ.get("AGENT_LLM_MODEL", "gpt-4o-mini")
AUTO_THRESHOLD = 0.90      # >= 高置信：自动执行
ESCALATE_THRESHOLD = 0.60  # < 低置信：转人工；中间档自动执行 + 事后抽检
VALID_LABELS = ["退款", "物流", "产品质量", "其他"]


def llm(prompt: str, system: str = "", temperature: float = 0.3) -> str:
    """调用 OpenAI 兼容接口。失败抛异常，由调用方降级转人工——不硬失败。"""
    messages = ([{"role": "system", "content": system}] if system else []) + [
        {"role": "user", "content": prompt}
    ]
    resp = client.chat.completions.create(
        model=MODEL, messages=messages, temperature=temperature)
    return resp.choices[0].message.content or ""


def now() -> str:
    return datetime.now(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")

▸ 代码怎么读：片段一暴露三个可替换点——客户端（任何 OpenAI 兼容网关只改环境变量）、双阈值、标签集。两个阈值的取值逻辑：0.90 是自动路径的精度闸，自动执行没有人工兜底，门槛必须落在校准曲线的高置信区（见 13.5.2，先校准再选值）；0.60 之下连"放行加抽检"都不给，因为中间档恰恰是错误率上升最快的区域。llm() 刻意让异常向上抛而不内部吞掉：本模式的纪律是失败也是信息——分类失败与低置信同路，都该流向人工。读者要改的只有 VALID_LABELS 与两个阈值。

@dataclass
class Ticket:
    """待分类工单：path 记录走过的分流路径，全程可追责。"""
    ticket_id: str
    text: str
    label: str | None = None
    confidence: float = 0.0
    path: str = "pending"  # pending|auto|sampled|approved|rejected|fallback
@dataclass
class AuditEntry:
    """审计留痕：每个分流与人工决策都可回放。"""
    ts: str
    actor: str  # "system" 或审批人 ID
    ticket_id: str
    action: str  # AUTO/SAMPLE/ESCALATE/approved/rejected
    detail: str
@dataclass
class ReviewGateway:
    """人工闸门：低置信工单挂起在此，approve/reject 后恢复流程。"""
    pending: dict[str, Ticket] = field(default_factory=dict)
    audit: list[AuditEntry] = field(default_factory=list)

    def hold(self, ticket: Ticket, detail: str) -> None:
        self.pending[ticket.ticket_id] = ticket
        self.audit.append(AuditEntry(now(), "system", ticket.ticket_id, "ESCALATE", detail))

    def resume(self, ticket_id: str, decision: str, reviewer: str,
               edited_label: str | None = None) -> Ticket | None:
        ticket = self.pending.pop(ticket_id, None)
        if ticket is None:  # 错误路径：恢复不存在的挂起 -> 显式失败，不静默
            return None
        ticket.path = "approved" if decision == "approved" else "rejected"
        if decision == "approved" and edited_label:
            ticket.label = edited_label  # 人工修正标签是最贵的再训练数据
        self.audit.append(AuditEntry(now(), reviewer, ticket_id, decision,
                                     f"label={ticket.label} conf={ticket.confidence:.2f}"))
        return ticket

▸ 代码怎么读：三个数据结构各司其职。Ticket.path 是流程的轨迹字段，六个取值覆盖全部出口，审计回放时靠它还原每条工单走过的路。ReviewGateway.hold 把挂起与审计写在一起：挂起本身就是一次分流决策，同样要留痕，而不只是"等待"。resume 的 return None 分支是错误路径：恢复一个不存在的挂起（重复恢复、ID 打错）必须显式失败，静默吞掉会让上游误以为裁决已生效。edited_label 单独传递，是因为人工修正的标签是全流程最贵的训练数据，生产中要把"被修正"这个事实单独记录回流。

def classify(ticket: Ticket, gateway: ReviewGateway) -> None:
    """LLM 分类 + JSON 解析 + 三档置信度路由。所有失败路径都收敛到人工。"""
    system = '你是客服工单分类器。只输出 JSON：{"label": "<标签>", "confidence": <0到1的小数>}'
    prompt = f"标签只能取：{'、'.join(VALID_LABELS)}。工单内容：{ticket.text}"
    try:
        raw = llm(prompt, system=system, temperature=0.0)
    except Exception as exc:  # 错误路径 1：LLM 不可用 -> 降级转人工，不硬失败
        gateway.hold(ticket, f"LLM 调用失败，降级转人工（{exc}）")
        ticket.path = "fallback"
        return
    try:  # 错误路径 2：解析失败/非法标签 = 系统自报"我不知道"，与低置信同路
        fence = chr(96) * 3  # 代码围栏字面量，避免在源码里写裸三反引号
        cleaned = raw.strip().removeprefix(fence + "json").removesuffix(fence).strip()
        parsed = json.loads(cleaned)
        label, conf = str(parsed["label"]), float(parsed["confidence"])
        if label not in VALID_LABELS:
            raise ValueError(f"非法标签 {label}")
    except (json.JSONDecodeError, KeyError, ValueError) as exc:
        gateway.hold(ticket, f"输出解析失败（{exc}），原文：{raw[:60]!r}")
        ticket.path = "fallback"
        return
    ticket.label, ticket.confidence = label, conf
    if conf >= AUTO_THRESHOLD:  # 高置信：自动执行
        ticket.path = "auto"
        gateway.audit.append(AuditEntry(now(), "system", ticket.ticket_id,
                                        "AUTO", f"{label} conf={conf:.2f}"))
    elif conf >= ESCALATE_THRESHOLD:  # 中间档：照常执行，进事后抽检队列
        ticket.path = "sampled"
        gateway.audit.append(AuditEntry(now(), "system", ticket.ticket_id,
                                        "SAMPLE", f"{label} conf={conf:.2f} 进抽检队列"))
    else:  # 低置信：挂起，等人工裁决后恢复
        gateway.hold(ticket, f"低置信（{conf:.2f} < {ESCALATE_THRESHOLD}）")

▸ 代码怎么读：这是全章的骨架，注意所有失败路径的走向——LLM 调用失败（路径 1）与解析失败/非法标签（路径 2）都进 gateway.hold 转人工而不是抛异常出进程：系统的每次"我不知道"都应变成一次人工介入，而不是一次崩溃。fence 用 chr(96) 构造是本书代码的书写约定；生产中更稳的做法是开结构化输出（JSON mode），从根上消掉解析失败。三档判断从高到低：>=0.90 自动、>=0.60 照常执行加抽检、其余挂起——中间档不是暂停，是用"事后看一眼"的成本换掉"事前等待"的成本。读者要改的：资金动作类标签的阈值应整体上移（风险加权，见 13.5.2）。

if __name__ == "__main__":
    gateway = ReviewGateway()
    tickets = [
        Ticket("T-1", "我的订单三天了还没发货，物流信息一直不动。"),
        Ticket("T-2", "包装盒上没有生产日期，请问正常吗？"),
    ]
    print("== 阶段 1：自动分类与三档分流 ==")
    for t in tickets:
        classify(t, gateway)
    print("\n== 阶段 2：人工裁决挂起工单并恢复 ==")
    for tid in list(gateway.pending):
        gateway.resume(tid, "approved", reviewer="alice", edited_label="物流")
    print("\n== 阶段 3：按最终路径执行 + 审计回放 ==")
    for t in tickets:
        if t.path in {"auto", "sampled", "approved"}:
            print(f"  执行：{t.ticket_id} 按标签「{t.label}」派发")
        else:
            print(f"  {t.ticket_id} 未执行（{t.path}）——如实留在待办")
    for e in gateway.audit:
        print(f"  {e.ts} | {e.actor:6} | {e.ticket_id} | {e.action:8} | {e.detail}")

▸ 代码怎么读：演示分三阶段，对应真实系统的三个组件。阶段 2 的 resume 在真实系统中是审批 UI 的回调：裁决是结构化的（approve/reject 加修正标签），不是一句模糊的"嗯"。阶段 3 只执行 auto/sampled/approved 三种路径——rejected 与 fallback 如实留在待办，流程绝不假装完成。末尾的审计回放打印验证 13.5.5 的要求：给定日志，能离线重建每条工单从进入到裁决的完整链路。读者要改的：gateway 换成落库实现（挂起表加审计表），演示用的内存对象只适合单进程自测。

13.6.2 框架差异速览（LangGraph interrupt()）

原 LangGraph 完整示例（interrupt() 挂起 + Command(resume=...) 恢复）压缩为下表：同名能力在该框架里的函数与一句话差异，细节以 LangGraph 官方文档为准（0.2.31 起推荐 interrupt 用法，langgraph==1.2.16 实测可用）。

能力 框架无关实现（本节片段） LangGraph
挂起等人 自维护 pending 队列（生产落库） 节点内 interrupt(payload)：图暂停，状态连同提问存入检查点
裁决注入 resume() 把结构化裁决写回工单 Command(resume=裁决)：裁决成为 interrupt() 的返回值
断点语义 手工保存/恢复，粒度自定 恢复时被中断节点从头重跑，interrupt 之前的代码必须无副作用
前置条件 无 必配 checkpointer（如 InMemorySaver），interrupt 强依赖检查点
状态查看 遍历 tickets 与 audit 列表 app.get_state(config) 取图状态、历史与挂起中的 interrupt
适用判断 单流程、嵌入现有服务最轻 多分支图、需要多线程会话与状态回放

13.6.3 生产化改造清单

  • 闸门持久化：挂起队列与审计日志落库（而非内存对象），审批服务重启不丢单；挂起任务带超时，超时按升级策略转下一审批人或降级处理。
  • 审批证据包：审批 UI 呈现完整上下文（输入、模型理由、置信度、历史相似案例、风险提示），并支持修正而不只是批准/驳回二选一。
  • 校准：定期用保留集测置信度分段准确率，校准阈值；模型或分布更新后阈值重标定，不沿用旧数。
  • 并发与幂等：同一工单只允许一条在途审批；审批动作带幂等键，防止双击产生两条相反裁决。
  • 安全：审批接口走强认证；审批人身份与裁决绑定签名；白名单变更走双人复核（复核你自己的复核员）。
  • 可观测：升级率、审批时延、驳回率、抽检命中率、金标混入准确率五项做成仪表盘；驳回率趋零与积压超限都要告警。
  • 成本控制：按层拦截（规则→廉价模型→人），人审带宽显式预算化；升级超预算时按预案降级而不是让队列腐烂。
  • 数据回流：人工修正样本自动入评估集与再训练池；每条审计记录可离线回放完整决策链。

13.7 概览 / 核心要点 / 结论

本章小结

人在回路把"人"从智能体系统的对立面变成了控制面的一部分：介入点决定人在哪里出手，置信度路由决定谁值得人出手，闸门协议决定人看到什么、返回什么，断点恢复让暂停不丢状态，审计留痕让每个决定可回放可追责。这套机制的全部智慧不在于"多问人"，而恰恰在于"少问人、问对人、问得让人能答"——半个世纪的人因工程早已证明，一个被淹没的审批人比没有审批更危险。

核心要点

  • 介入点三档谱系：事前审批拦截最强摩擦最大，事中暂停信息最全需要检查点，事后抽检摩擦最小但风险窗口最长；按可逆性×代价×时延选位置。
  • 双阈值三档路由：高置信自动、中置信放行加抽检、低置信转人工；单阈值系统里"不升级"等于"免检"。
  • 置信度必须校准后才能做路由信号；路由判据是风险加权的不确定度，不是模型难度。
  • 自动化偏见有半个世纪的实证：审批人连续放行后会退化成条件反射，驳回率趋零即是闸门失效的信号。
  • 升级梯子先机器后人：规则引擎和廉价模型能拦的请求不消耗人时；人审预算显式化。
  • interrupt 恢复语义：被中断节点从头重跑，interrupt 之前的代码必须无副作用；checkpointer 必配。
  • 审计日志四职能：问责、复盘、调参、再训练；不可篡改、可离线回放才算合格。

结论

智能体的自动化程度不是非黑即白的开关，而是一条由数据和风险共同决定刻度的滑杆——人在回路就是这条滑杆的调节机构。它让系统以诚实的姿态面对自己的不可靠：拿不准就说，说不准就问，问了就记录。工程上真正困难的部分从来不是加一个确认弹窗，而是让每一次打断都值得、每一个裁决都被认真给出、每一条人工反馈都回流成系统的改进——做到这三点，人不是流程的瓶颈，而是系统可靠性的组成部分。
