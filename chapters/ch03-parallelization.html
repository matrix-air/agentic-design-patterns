第一部分 · 核心模式

第3章 并行化 Parallelization

把独立子任务并发执行后归并——切分压缩延迟，投票提升准确率，聚合器融合观点，join 阶段的归并语义决定成败。

一句话定义：把相互独立的子任务同时交给多个模型调用执行，再把结果归并为一份输出——切分求快，投票求准，聚合求全。 解决什么问题：串行链的延迟叠加与单次采样的随机失误 ｜ 适用场景：多维独立评审、批量独立任务、推理题多采样投票、多模型生成融合 ｜ 核心机制：任务切分 + 并发执行 + join 归并（拼接/投票/聚合器三种语义）｜ 代价：token 成本成倍放大，归并逻辑自身成为新的复杂度与故障点。

本章速读　并行化把独立的子任务同时发出再归并：对付延迟靠**切分**（维度/数据块各走一路），对付随机失误靠**投票**（同题多次采样取多数派），求全面靠**聚合器**融合多路意见。三步落地：验证子任务真独立 → 并发执行并隔离单路失败 → 在 join 点按拼接/投票/聚合器归并并显式实现 quorum。**有顺序依赖、单次已够可靠、或所有采样同源同偏**时别用——多数一致不等于正确。

3.1 模式概述

3.1.1 问题背景：为什么需要这个模式

串行的提示链解决了任务过载问题，却带来两样新的东西：累积的延迟，和累积的随机性。延迟好理解——三步链就是三次模型调用的耗时之和，用户等得着急。随机性则更隐蔽：大模型的输出是概率采样，同一个问题问两遍可能得到不同答案，任何一次单独调用都可能踩中一次"随机失误"——漏看一个约束、算错一步推理。对单次调用而言这是小概率，对一个每天跑百万次的系统而言是必然事件。

并行化针对这两点给出了对称的解法。对付延迟：如果子任务之间互相独立，就没有理由排队——三路评审同时发出，总耗时从三倍压缩到一倍加一点汇合开销。对付随机性：如果失误是随机的，就让多次独立采样互相暴露——同一问题问五遍，三次说 A 两次说 B，多数派比任何单次采样都更可信。这两种用法（切分与投票）加一个收尾环节（聚合器），构成了并行化的全部骨架。

3.1.2 核心机制：它如何工作

并行化的执行由三个阶段构成。切分阶段决定怎么把工作拆开：切分可以按内容维度（一份技术方案拆成技术、安全、成本三路评审）、按数据块（长文档切成章节分别翻译）、或按采样次数（同一个问题独立采样 N 次）。切分的铁律是独立性：每一路在执行时不能依赖其他路的中间结果。执行阶段用线程池、异步协程或框架的并行原语把 N 个调用同时发出，并对每一路设置超时与失败隔离——一路崩了不影响其他路。归并阶段（join）是关键：N 份输出按三种语义之一合成一份——结果天然独立时按序拼接（分块翻译）；结果互为替代品时投票（多采样推理）；结果互为素材时交给一个聚合器模型融合裁决（多维评审意见）。归并阶段还必须回答一个工程问题：部分路失败时，整体算成功还是失败——这由 quorum（法定多数）语义决定。

3.1.3 与相邻模式的关系与组合

并行化与提示链（第 1 章）互为补充：链是纵向的顺序骨架，并行化是链上某个节点的横向展开——"带并行分支的链"就是两者的复合。投票与反思（第 4 章）是提升输出质量的两种路径：反思让模型自查一次，投票让多次独立生成互相印证，实践常在投票之后再接一轮反思做最终裁决。多智能体协作（第 7 章）可以看作并行化的组织形态升级：从"一把任务撒给 N 个无差别的调用"升级为"分工、角色与协调"。聚合器与评估监控（第 19 章）共享一套思想：如何为多个输出建立可比的评价尺度。

3.2 起源与历史：最早是谁提出来的

并行化的系统化源头不在 AI 领域，而在分布式系统：2004 年 Google 的 Dean 与 Ghemawat 发表 MapReduce（OSDI 2004），把"分而治之、map 阶段并行处理、reduce 阶段归并结果"固化为一套通用编程范式。LLM 应用的并行化在结构上就是 MapReduce 的直系后代——map 是 N 路并发调用，reduce 是拼接、投票或聚合。

LLM 时代自己的里程碑是自洽性（Self-Consistency）。2022 年 3 月，Wang 等人发表 arXiv:2203.11171（后发表于 ICLR 2023）：对同一个推理问题多次采样不同的推理路径，把最终答案做多数投票，在 GSM8K 等算术与常识推理基准上带来大幅提升。这是"投票式并行"的学术原型，证明了大模型随机性可以被结构化地利用——单次采样会出错，但系统性错误很难在多次独立采样中保持同一方向。2023 年 6 月出现两个工程侧的节点：Jiang 等发表 LLM-Blender（arXiv:2306.02561，后发表于 NeurIPS 2023），先用配对排序评估多个模型的候选输出、再由融合模型合成最终答案，给出了"聚合器"的学术样板；同月 OpenAI 宣布支持并行函数调用，模型可以在单轮请求里同时发起多个工具调用，工具层面的并行从"开发者自己编排"变成了"模型自己编排"。2024 年 12 月，Anthropic《Building Effective Agents》把并行化正式分为切分（sectioning）与投票（voting）两类，完成了行业定名。

演化脉络是一条"从系统到模型再到智能体"的迁移线：MapReduce 提供结构（并行 + 归并），Self-Consistency 提供第一个为概率模型量身定制的归并语义（多数投票），LLM-Blender 与并行函数调用把并行能力下沉到工程框架与 API 层，Anthropic 的分类法则把它确立为智能体工作流的一等公民。

3.3 发挥的作用：为什么重要

并行化在两个最难缠的系统指标上直接发力。延迟：多维评审、批量处理、多路工具调用这类天然并行的负载，串行执行的时间是各路之和，并行执行的时间约等于最慢一路——五路评审从"五倍等待"变成"一倍等待"，这是不需要换更强模型就能拿到的提速。准确率：Self-Consistency 展示的提升在推理类任务上往往超过换用更大模型：单次采样像一次抛硬币，多次独立采样加多数投票像多次抛硬币看频率，方差被结构性地压了下去。对高价值决策（合同审查、医疗分诊、代码上线评审），投票还是最便宜的不确定性度量——票数分歧本身就是"这个问题难、需要人工介入"的信号。

第三重作用是能力融合：不同模型各有所长，聚合器归并让系统同时吃到了多家的红利，任何单一模型的风向变化也被稀释在组合之中。这种"不把鸡蛋放进一个模型"的稳健性，在大模型能力快速轮动的时期尤其值钱。

3.4 实际应用与案例

  • 长文档并行评审：一份技术方案按维度拆成正确性、安全性、可维护性三路并发评审，聚合器汇总为一份意见。关键设计点：各路只输出结构化问题清单，归并时按严重度排序而不是按来源罗列。
  • 推理任务自洽投票：数学应用题、逻辑谜题用高温度采样 5~10 次，答案归一化后多数投票。关键设计点：答案必须先归一化（"0.5"与"二分之一"是同一票）再计票，否则多数派被表述差异稀释。
  • 内容安全多审官：同一内容同时送多个安全评审提示（或多个模型），任一审官亮红牌即拦截。关键设计点：这里用的是"一票否决"而非多数决——安全场景的误放代价远高于误拦。
  • 代码库批量重构：数百个文件的机械重构按文件切分并发执行，每路独立跑测试校验，失败文件回滚不牵连其他。关键设计点：切分单元选"文件"这种天然无依赖的边界，并给每路配独立的失败处理。
  • 多模型生成融合：三个模型各写一版营销文案，聚合器取各版之长合成终稿。关键设计点：聚合器提示要显式说明"意见冲突时以哪个为准"（如以合规版为准），否则融合结果随机偏袒。
  • 批量数据标注提速：上万条数据按批并行标注，校验规则先于模型跑一遍过滤掉可机械判断的样本。关键设计点：并发数要贴着供应商限流配额调，盲开高并发只会换来批量超时。

真实世界实例

Anthropic 多智能体研究系统（Claude Research 功能）。2025 年 6 月 Anthropic 公开了支撑 Claude Research 功能的编排者-工人系统：主智能体（Claude Opus 4）分析查询、制定策略，把子任务派给多个专业化子智能体（Claude Sonnet 4）——各自带独立上下文窗口并发检索，只把轻量引用交回主智能体，最后归并发现。官方给出的数字：该编排在其内部研究评估上比单智能体 Claude Opus 4 高出 90.2%；同时如实标注代价——智能体约消耗普通聊天 4 倍的 token，多智能体系统约 15 倍。这是"切分 + 并发 + 聚合归并"迄今最有分量的生产级实证。（来源：Anthropic 工程博客，2025-06-13，https://www.anthropic.com/engineering/multi-agent-research-system）

Perplexity Pro Search（多路检索与汇合过滤）。Pro Search 面对复杂问题先做显式规划，再为每一步生成一批检索查询一并执行：官方帮助中心描述其"在全网执行多次搜索"，从文章、学术论文、论坛、视频等多类来源收集信息；返回的文档被分组、过滤出最相关者，再交给大模型综合成带引用的最终答案。多路查询扇出 + 汇合处过滤归并，正是本章"切分 + join"在搜索产品里的落地形态，其逐步展示中间进度的交互也印证了"用户愿意为可见的过程等待"。（来源：LangChain 官方案例研究 https://www.langchain.com/breakoutagents/perplexity；Perplexity 官方帮助中心 https://www.perplexity.ai/help-center/en/articles/10352903-what-is-pro-search）

3.5 深度讲解

机制细节：join 的三种归并语义。 并行化真正的设计难点不在"并发发请求"，而在汇合点上。第一种是拼接归并：各路结果天然独立、互不冲突（分块翻译、批量标注），归并只是保序拼接，唯一要小心的是跨块的上下文断裂——第 5 块把"上一章"翻丢了，因为切分时上下文被切断，对策是切分时留重叠区或携带边界摘要。第二种是投票归并：各路结果互为替代品，用计票消解分歧。投票的技术核心是答案归一化——必须把语义相同的输出映射到同一票面再计票，否则"多数"是表述方式的多数而非答案的多数。平局要预先定义处理规则：触发升级（重采样一轮、或送强模型仲裁）比随机挑一个好，因为平局本身就是高不确定性的证据。第三种是聚合器归并：各路结果互为素材（三份不同角度的评审意见），由一个聚合 LLM 融合裁决。聚合器是 LLM-Blender 式的角色，它带来新的风险：聚合器本身会出错、有偏好（偏爱更长的、更靠后的输入），而且成为整条路径的单点——它的提示必须显式回答"意见冲突听谁的""某路缺席怎么办"。

机制细节：切分、投票与编排者-工人三变体。 Anthropic 的两分法值得扩展成三类。切分（sectioning）的核心纪律是验证"真独立"：子任务间若共享隐式上下文，切分后互相引用就会丢失——把"第三章结论"的评审和"第三章论证"的评审拆给两路，后者拿不到前者的结论，评审就在互相矛盾的假设上进行。判断真独立的方法很机械：把每一路的输入单独打印出来，问"这路拿到的东西够它做完自己的事吗"，缺什么就把什么补进切分逻辑。投票（voting）的多样性必须是真的：同一温度、同一提示采五次，多样性来自采样噪声，便宜但浅；混合不同提示框架（prompt ensemble）或不同模型，多样性来自系统性视角差异，纠错力更强、成本更高。投票还有一个被反复验证的局限：如果所有采样共享同一个系统性偏差（同一个模型、同一份有偏见的提示），多数投票不会纠错，只会放大自信——多数派一致不等于正确，只等于"这个模型稳定地这么想"。编排者-工人（orchestrator-workers）是切分的动态版：切分方案本身由一个编排 LLM 在运行时生成，工人并发执行后交聚合器归并。它灵活，但把静态切分里"开发期就能验证的独立性"推迟到了运行时，失效模式也随之变成动态的——编排者切出了有依赖的子任务，系统就在暗处出错。

工程权衡：成本、延迟与确定性的三角。 投票的成本随采样数线性放大，k 次采样就是 k 倍 token；折中手段是提前终止（early stopping）——采到 quorum 多数一致就停，不再跑满 N 次，多数问题在前三四票就见分晓。延迟的真实上界由最慢一路与限流配额决定：五路并发里有一路超时，整体就等它，所以每路必须有独立的超时与放弃策略；供应商的速率限制则决定了并发数的硬上限，超出就是批量 429。确定性与多样性存在内生冲突：投票需要 temperature 大于 0 才有多样性，而温度高意味着同一输入两次运行结果不同——这与"可复现"的工程要求相悖，对策是用固定随机种子（若供应商支持）与结果缓存补偿，并在监控里接受"投票系统的输出天然带方差"这一事实。

失效模式与反模式。 第一个是部分失败的处理缺失：五路里两路超时，代码若无 quorum 检查就会拿三路结果当全量结论，而"缺席的两路"可能恰恰是最难的维度。quorum 语义（成功路数不足法定多数则整体失败或降级）必须显式实现，且低 quorum 通过的事件要在监控里单独曝光。第二个是假独立切分（上文已述）——它是并行化里最常见也最无声的错误。第三个是相关错误投票：同一模型的五次采样在同一个知识点上犯同一个错，五票一致地错，投票给了它五倍的自信。缓解手段是异构投票（不同模型或显著不同的提示），并把"票数与最终正确率"的关系纳入离线评估，而不是默认多数即正确。第四个反模式是把并行化当万金油用在有顺序依赖的任务上：每步依赖前步全部输出的任务（多轮谈判、迭代式调试）并行化只会制造竞态与混乱，硬并行出来的结果甚至难以复现 bug。

何时不要用。 任务强顺序依赖时不并行。单次调用已经足够可靠、且成本敏感时，投票的 N 倍花费买不来对等的质量。输出必须确定唯一又没有仲裁机制时（如直接写入账本的数值计算），带方差的投票系统反而是负债。最后，当"并行"只是为了让 N 个任务快点跑完而任务彼此毫无关系时，那叫批量调度，不需要本章的模式——直接开线程池就好。

3.6 工程落地：实践代码示例

3.6.1 框架无关实现（完整可运行）

以下实现并行化的两个核心变体：切分（三路评审并发 + 聚合器归并）与投票（同题多次采样 + 多数投票），完整演示超时、失败隔离、quorum 语义与平局升级。

"""第3章 并行化：框架无关实现——切分评审 + 自洽投票。

变体一（切分 sectioning）：一份方案三路并发评审，聚合器归并意见。
变体二（投票 voting）：同一问题独立采样 N 次，归一化后多数投票。
工程要点：线程池并发、单路失败隔离、整体超时、quorum 检查、平局升级。

运行前设置环境变量：AGENT_LLM_API_KEY（必填）、
AGENT_LLM_BASE_URL / AGENT_LLM_MODEL（可选）。
"""
from __future__ import annotations

import os
import sys
from collections import Counter
from concurrent.futures import Future, ThreadPoolExecutor, as_completed
from typing import Callable

from openai import OpenAI

client = OpenAI(
    base_url=os.environ.get("AGENT_LLM_BASE_URL", "https://api.openai.com/v1"),
    api_key=os.environ["AGENT_LLM_API_KEY"],
)
MODEL = os.environ.get("AGENT_LLM_MODEL", "gpt-4o-mini")


def llm(prompt: str, system: str = "", temperature: float = 0.3) -> str:
    """调用大模型，返回补全文本。"""
    messages: list[dict[str, str]] = []
    if system:
        messages.append({"role": "system", "content": system})
    messages.append({"role": "user", "content": prompt})
    resp = client.chat.completions.create(
        model=MODEL,
        messages=messages,
        temperature=temperature,
    )
    return resp.choices[0].message.content or ""


class QuorumError(RuntimeError):
    """成功分支数不足法定多数，整体结果不可信，归并失败。"""


class TieError(RuntimeError):
    """投票出现平局：多数意见无法决出，按约定触发升级。"""


def run_parallel(
    tasks: dict[str, Callable[[], str]], timeout: float = 60.0
) -> dict[str, str | None]:
    """并发执行一组任务并隔离单路失败。

    返回 {任务名: 结果}；失败或超时的路记为 None，不拖累其他路。
    这是 join 阶段的前置：先拿到"谁活了下来"，再谈归并语义。
    """
    results: dict[str, str | None] = {name: None for name in tasks}
    with ThreadPoolExecutor(max_workers=len(tasks)) as pool:
        futures: dict[Future[str], str] = {
            pool.submit(fn): name for name, fn in tasks.items()
        }
        try:
            for fut in as_completed(futures, timeout=timeout):
                name = futures[fut]
                try:
                    results[name] = fut.result()
                except Exception as exc:  # 单路失败只影响自己
                    print(f"[并行] 分支 {name} 失败：{exc}")
        except TimeoutError:
            print("[并行] 整体超时，未完成分支按失败处理")
    return results


# ---------- 变体一：切分（sectioning）+ 聚合器归并 ----------

REVIEW_ASPECTS: dict[str, str] = {
    "技术正确性": "检查方案中的技术断言是否成立、有无事实性错误。",
    "安全风险": "检查是否引入注入、越权、数据泄露等安全风险。",
    "可维护性": "检查可读性、可测试性与长期维护成本。",
}


def sectioning_review(design_doc: str) -> str:
    """三路评审并发执行，聚合器归并为一份最终意见。

    每路的提示自包含（含评审标准与全文），保证切分后的"真独立"。
    """
    tasks: dict[str, Callable[[], str]] = {}
    for aspect, criteria in REVIEW_ASPECTS.items():
        def make_task(a: str = aspect, c: str = criteria) -> Callable[[], str]:
            def task() -> str:
                out = llm(
                    f"请只从【{a}】角度评审以下技术方案。\n评审标准：{c}\n"
                    '只输出 JSON：{"issues": [{"point": "问题", "severity": "高|中|低"}]}，'
                    '无问题则输出 {"issues": []}。\n\n方案：\n' + design_doc,
                    system="你是严格的技术评审，只评审分配给你的维度。",
                    temperature=0.2,
                )
                return out
            return task

        tasks[aspect] = make_task()

    reviews = run_parallel(tasks, timeout=90.0)
    survived = {k: v for k, v in reviews.items() if v is not None}
    if len(survived) < 2:  # quorum 语义：三路至少活两路才允许归并
        raise QuorumError(f"评审成功路数不足：{len(survived)}/3")

    merged_input = "\n".join(f"【{k}】评审：{v}" for k, v in survived.items())
    missing = [k for k in reviews if reviews[k] is None]
    missing_note = f"（注意：{'、'.join(missing)} 维度评审缺席，不得假装已评审）" if missing else ""
    return llm(
        "以下是对同一技术方案的多维评审意见，请归并为一份最终评审报告："
        "按严重度排序列出问题，剔除重复，并对冲突意见给出裁决。\n"
        f"{missing_note}\n\n{merged_input}",
        system="你是评审组长。意见冲突时以技术正确性维度为最高优先。",
        temperature=0.2,
    )


# ---------- 变体二：投票（voting）+ quorum + 平局升级 ----------

def extract_answer(text: str) -> str | None:
    """从输出中提取【答案：X】并归一化票面。

    归一化是投票的正确性前提：'9.9' 与 '9.90' 必须是同一票。
    """
    marker = "【答案："
    idx = text.find(marker)
    if idx == -1:
        return None
    rest = text[idx + len(marker) :]
    end = rest.find("】")
    if end == -1:
        return None
    return rest[:end].strip().replace(" ", "").rstrip("0").rstrip(".") or "0"


def voting_answer(question: str, n: int = 5, quorum: int = 3) -> str:
    """同一问题独立采样 n 次，多数投票；不足 quorum 或平局则升级。

    - 成功采样数 < quorum：失败路太多，结果不可信，抛 QuorumError；
    - 最高票数 < quorum：票面分歧过大，说明问题困难，抛 TieError 交上层
      升级处理（重采样 / 强模型仲裁 / 人工），而不是硬选一个多数。
    """
    def sample() -> str | None:
        out = llm(
            f"请解答以下问题，最后一行严格按【答案：X】格式给出最终答案。\n{question}",
            temperature=0.7,  # 高温度才有采样多样性，投票的前提
        )
        return extract_answer(out)

    tasks = {f"sample_{i}": sample for i in range(n)}
    results = run_parallel(tasks, timeout=90.0)
    votes = [v for v in results.values() if v is not None]
    print(f"[投票] 有效票：{Counter(votes)}（成功 {len(votes)}/{n}）")
    if len(votes) < quorum:
        raise QuorumError(f"成功采样 {len(votes)} 次不足 quorum={quorum}")
    top, count = Counter(votes).most_common(1)[0]
    if count < quorum:
        raise TieError(f"无多数一致：{Counter(votes).most_common()}")
    return top


if __name__ == "__main__":
    design = (
        "用户反馈导入功能：上传 CSV 后由服务端解析入库。"
        "解析直接使用 eval 执行单元格公式以提高灵活性；"
        "导入失败时把错误堆栈原样返回给前端以便调试。"
    )
    print("=== 切分评审 ===")
    try:
        print(sectioning_review(design))
    except QuorumError as exc:
        print(f"评审归并失败：{exc}", file=sys.stderr)

    print("\n=== 自洽投票 ===")
    try:
        answer = voting_answer("9.11 和 9.9 哪个数字更大？")
        print(f"多数答案：{answer}")
    except (QuorumError, TieError) as exc:
        print(f"投票未决，需升级处理：{exc}", file=sys.stderr)
        sys.exit(1)

3.6.2 框架集成实现（LangChain LCEL）

LangChain LCEL 里用 RunnableParallel 表达扇出，管道下游自然汇合。以下基于 langchain-core 0.3.x 与 langchain-openai 0.2.x 编写（API 若有变动，以所用版本官方文档为准）。注意：RunnableParallel 的默认语义是"任一分支失败则整体失败"，quorum 语义需要自定义归并节点（如框架无关版所示）。

"""第3章 并行化：LangChain LCEL 实现——三路评审扇出 + 聚合归并。

依赖：pip install "langchain-core>=0.3" "langchain-openai>=0.2"
"""
from __future__ import annotations

import os
import sys

from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableLambda, RunnableParallel
from langchain_openai import ChatOpenAI

model = ChatOpenAI(
    model=os.environ.get("AGENT_LLM_MODEL", "gpt-4o-mini"),
    base_url=os.environ.get("AGENT_LLM_BASE_URL", "https://api.openai.com/v1"),
    api_key=os.environ["AGENT_LLM_API_KEY"],
    temperature=0.2,
)


def review_chain(aspect: str, criteria: str):
    """构造单路评审链，并挂带次数上限的重试（限流/瞬时错误可自愈）。"""
    prompt = ChatPromptTemplate.from_messages(
        [
            ("system", f"你是严格的技术评审，只评审【{aspect}】维度，只输出 JSON。"),
            (
                "user",
                "评审标准：{criteria}\n"
                '输出 {{"issues": [{{"point": "...", "severity": "高|中|低"}}]}}\n\n'
                "方案：\n{design_doc}",
            ),
        ]
    )
    return (prompt | model | StrOutputParser()).with_retry(stop_after_attempt=2)


# 扇出：三路评审共享同一输入 {design_doc}，并发执行
parallel_reviews = RunnableParallel(
    correctness=review_chain("技术正确性", "检查技术断言是否成立、有无事实错误。"),
    security=review_chain("安全风险", "检查注入、越权、数据泄露等风险。"),
    maintainability=review_chain("可维护性", "检查可读性、可测试性与维护成本。"),
)

# 汇合（join）：聚合器把三份意见归并为一份报告
merge_chain = (
    ChatPromptTemplate.from_messages(
        [
            ("system", "你是评审组长：按严重度排序、去重，冲突时以技术正确性为优先。"),
            (
                "user",
                "正确性评审：{correctness}\n安全评审：{security}\n"
                "可维护性评审：{maintainability}\n请输出最终评审报告。",
            ),
        ]
    )
    | model
    | StrOutputParser()
)

# 整链：扇出 -> 汇合
review_flow = parallel_reviews | merge_chain

if __name__ == "__main__":
    design_doc = (
        "用户反馈导入功能：上传 CSV 后由服务端解析入库。"
        "解析直接使用 eval 执行单元格公式以提高灵活性；"
        "导入失败时把错误堆栈原样返回给前端以便调试。"
    )
    try:
        report = review_flow.invoke({"design_doc": design_doc})
        print(report)
    except Exception as exc:
        # LCEL 默认 fail-fast：任一分支重试耗尽即整链失败；
        # 若业务需要 quorum 语义，应改用自定义 RunnableLambda 归并节点。
        print(f"并行评审失败：{exc}", file=sys.stderr)
        sys.exit(1)

3.6.3 生产化改造清单

  • 错误处理：单路失败隔离 + quorum 检查是底线；"低 quorum 通过"作为独立事件类型上报，不允许静默混入正常结果。
  • 超时：每路独立超时 + 整体 join 超时双口径；慢路超限即放弃，不让最慢的一路拖住整个汇合点。
  • 并发：并发数显式配置并贴着供应商限流配额走，配指数退避与抖动；批量场景用有界队列防止内存与请求数失控。
  • 缓存：以"任务内容哈希 + 模型 + 提示版本"为 key 缓存各路结果；投票场景可缓存历史票面用于离线评估多数派正确率。
  • 可观测：记录每路的耗时、token 数与成败；投票场景记录票面分布——票面熵突增往往意味着上游模型行为变化。
  • 成本控制：投票用提前终止（攒够多数即停）压成本；为每类任务设采样数上限，并在监控里对比"加一票带来的边际正确率"。
  • 确定性管理：投票链路接受输出方差，关键下游（如写库）前置确定性校验层；供应商支持种子时固定种子。

3.7 概览 / 核心要点 / 结论

3.7.1 本章小结

并行化把"排队等待"变成"同时开工"，把"赌一次采样"变成"让多次采样互相印证"。它的结构源自 MapReduce 的分而治之，它的归并语义由 Self-Consistency 的多数投票和 LLM-Blender 式的聚合器补全，最终在 Anthropic 的切分/投票二分法中定名。本章的核心论点是：并行的难点在汇合点——拼接、投票、聚合器三种 join 语义对应三类任务结构，而部分失败下的 quorum 判定、答案归一化、平局升级这些"汇合处的脏活"，才是并行化工程质量的真正分野。成本随路数线性放大是这个模式的天花板，提前终止与异构投票是常用的两把平衡尺。

3.7.2 核心要点

  • 切分求延迟、投票求准确、聚合器求全面，先想清楚要哪一个再选结构。
  • join 是设计的核心：拼接保序防断裂，投票先归一化再计票，聚合器要写明冲突裁决规则。
  • 切分前验证"真独立"：每路输入单独拿出来必须自足，缺上下文就补进切分逻辑。
  • quorum 语义必须显式：成功路数不足法定多数时整体失败或降级，低 quorum 通过要曝光。
  • 多数一致不等于正确：同源采样的相关错误会被投票放大，高价值场景用异构投票。
  • 平局与低置信是"问题困难"的信号，正确做法是升级（重采样/强模型/人工），不是硬选。
  • 成本与延迟的收益都要实测：投票 k 倍 token，延迟上界是最慢一路加限流排队。

3.7.3 结论

并行化是智能体工作流里最"像传统分布式系统"的一章：它不涉及模型的智能，只涉及把智能组织起来的方式。正因如此，它的成败几乎完全取决于工程判断——切分边界是否真实独立、汇合语义是否与业务对齐、失败路径是否定义清楚。把这三件事想透，五路并发的评审就比串行的单次生成更快也更可信；想不透，并行只会更快地产出一致的错误。
