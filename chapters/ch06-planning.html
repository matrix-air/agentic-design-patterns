第一部分 · 核心模式

第6章 规划 Planning

让智能体在行动前把目标分解为可执行的子任务序列，在执行偏差出现时按触发条件重规划，用显式中间结构换长程任务的稳定性与可观测性。

一句话定义：规划让智能体在行动之前把目标分解为子任务序列，在执行中跟踪状态，并在偏差出现时按明确的触发条件修订计划。 解决什么问题：长程任务超出单次生成能力，逐步即兴决策缺乏全局一致性 ｜ 适用场景：多步骤、有依赖关系、可分解的目标导向任务 ｜ 核心机制：计划生成 + 状态跟踪 + 重规划触发 + 计划验证 ｜ 代价：计划本身的生成成本、环境不符时的僵化风险、过度规划对简单任务的浪费。

本章速读　规划把长程任务从"赌模型隐式状态的稳定性"变成"管理一份显式的工作分解结构"。三步：①行动前生成子任务清单并做结构验证；②按依赖执行、逐项状态跟踪；③触发器命中（反复失败／假设证伪／环境变化／预算越界）时带证据局部重规划，全盘推翻须过门槛。何时别用：单步任务、强探索任务、环境变化快于计划周期的任务。

6.1 模式概述

6.1.1 问题背景：为什么需要这个模式

把一个二十步的任务直接交给模型逐步处理，会同时踩中三个陷阱。其一是组合漂移：每步决策都是独立采样，模型对"全局目标"的把握随上下文变长而稀释，走到第八步时常常已经忘了第三步为什么那么做。其二是错误累积：前面步骤的小偏差不被察觉，后续在错误的前提下继续建设，成品与目标相去甚远。其三是不可观测：没有显式的中间结构，失败时无法定位坏在哪一环，也无法告诉用户"完成了多少"。这三个陷阱的共同根源是"计划只存在于模型的隐式状态里"。规划模式的做法是把计划显式化：行动之前先产出一份子任务清单作为一等公民的数据结构，执行时逐项核对状态，发现偏差时带着证据修订。计划一旦显式，进度可报、失败可定位、修订有据——长程任务从"赌模型状态够稳"变成"管理一份可审计的工作分解结构"。

6.1.2 核心机制：它如何工作

规划模式的最小系统有四个部件。计划生成：把目标交给模型，产出结构化的子任务清单（通常是带顺序或依赖的 JSON 数组），每条子任务应在执行器能力范围内。执行：按序或按依赖拓扑执行，每项产出结果与状态。状态跟踪：维护每个子任务的状态（待办/完成/失败）与已完成产出，这是后续一切决策的依据。重规划：触发条件命中时——子任务反复失败、观察与计划假设不符、环境变化、预算超限——带着已完成状态与失败证据重新生成剩余计划。两个贯穿全局的设计决策是：计划与执行分离到什么程度（一次性全计划，还是边走边计划）；计划写到多细（细到每条工具调用，还是粗到里程碑）。这两问没有普适答案，6.5 节展开这些权衡。

6.1.3 与相邻模式的关系与组合

与 ReAct 的关系最微妙：ReAct 每步基于全部历史重新决策，规划隐式发生在模型内部，好处是适应快，坏处是全局一致性弱、每步昂贵。规划模式把它改成"一次计划、分步执行"，是互补而非替代——执行器内部常常就是一个 ReAct 循环。与工具使用是整体与局部：每条计划项的最小执行单元就是工具调用，计划验证的第一课是核对计划引用的工具是否真实存在。与反思是证据链：Reflexion 式的失败反思为重规划提供"为什么失败"的证据，没有反思的重规划只是换个姿势再赌一次。与 Tree of Thoughts 是搜索化：当"生成一份好计划"本身需要探索——分支、评估、回溯——规划就从序列生成升级为树搜索。与多智能体是分派：计划项是天然的分工单元，管理者智能体的核心工作就是把计划项派给合适的执行者（CrewAI 的 hierarchical 模式即此形态）。

6.2 源起：它从哪里来

LLM 时代的规划站在四十年符号 AI 的遗产上。1971 年 SRI 的 STRIPS 用"前提—添加—删除"三元组把动作与规划问题形式化；1970 年代中期 Sacerdoti 的 NOAH 开创分层任务网络（HTN）——"按方法库做任务分解"，正是今天 LLM 智能体任务分解的直接祖先。1987 年 Bratman 论证理性主体的意图具有坚持性（不因一点风吹草动就推翻重来），1991 年 Rao 与 Georgeff 把 BDI（信念—愿望—意图）形式化为可计算架构，"重规划要有门槛"的思想由此而来。2023 年范式重装登场：HuggingGPT 定下"规划—选择—执行—汇总"四阶段流水线；5 月一个月内 Plan-and-Solve（先计划再执行）、Tree of Thoughts（带评估回溯的树搜索）、ReWOO（占位符让计划一次生成）三线并出；11 月的 ADaPT 补上按需递归分解，初版没有终止条件的 BabyAGI 则成了"无停止条件规划"的反面教材。

6.3 发挥的作用：为什么重要

规划的第一价值是一致性：显式计划是跨步骤的全局约束，执行器每步只需"完成当前子任务"，不再独自背负整个目标，上下文稀释与目标遗忘被结构性缓解。第二价值是可观测：计划即进度条——"5 步中已完成 2 步，第 3 步失败，正在重试"，对用户、对运维、对审计都是透明的；失败定位也从"整个任务失败了"细化到"第 N 项失败，原因是……"。第三价值是成本结构：ReWOO 的变量占位符演示了分离式规划的经济学——计划只生成一次，执行时不必带着全部历史反复推理，长任务的 token 开销显著低于逐步即兴；计划还是天然的并行单元，无依赖子任务可并发执行。第四价值是失败管理：显式计划把"重试什么"从模糊问题变成清晰决策——重试、绕过还是分解失败项，各有明确依据与代价；没有计划，重试就退化为"从头再来"。第五价值最易被忽略：计划是人与智能体之间最有效的对齐界面——执行前让人审一眼计划，几秒钟的阅读就能拦下方向性错误，比事后检查几百轮执行轨迹便宜得多。

6.4 实际应用与案例

多跳问答与深度调研。 把"某技术路线的现状与竞争格局"分解为"界定子问题—逐项检索—交叉核实—汇总"的计划，检索子任务按依赖并行。关键设计点是计划里显式列出"需要核实的具体断言"，汇总阶段只允许引用已核实条目。

大型代码重构。 把"回调风格迁移到 async/await"分解为模块级子任务，每项含涉及文件、预期改动与验证方式（跑哪些测试）。关键设计点是每完成一项就运行验证，验证失败触发该项级重规划而非全盘重来。

旅行与日程安排。 目标分解为"定约束（日期预算）—订大项（交通住宿）—填空档（活动）—查冲突"，依赖关系决定执行顺序。关键设计点是预订类写操作前置人工确认，计划本身作为用户可见的清单可编辑。

数据分析流水线。 "取数—清洗—建模—可视化—成文"五段式计划，每段产出中间工件供下一段引用。关键设计点是 ReWOO 式占位符：计划在取数前生成，后续步骤引用"清洗结果"这个变量而非预知其内容。

客服工单跨系统处理。 退款工单分解为"核验订单—查政策—计算金额—创建退款单—发通知"，各步骤对接不同系统工具。关键设计点是写操作步骤设失败兜底（人工接管队列），计划状态同步到工单系统供人工查看。

具身与模拟环境任务。 ALFWorld 类文本环境里"把干净的杯子放到桌上"，ADaPT 的做法是先给执行器一个粗计划，发现"找到杯子"这步执行不了再递归分解为"搜索厨房—检查水槽—清洗"。关键设计点是分解深度由执行器能力决定，不做无谓的预分解。

真实世界实例

Cognition：Devin 的计划呈现与自测闭环。 官方 SWE-bench 技术报告（2024 年 3 月）把 Devin 的工作方式概括为"执行多步计划并从环境获取反馈"：接到 issue 先规划，再改代码、自己运行测试、按报错修正重跑，报告分析显示 72% 的通过用例单次要跑 10 分钟以上，"多步规划"被列为首要成功因素——长程工程任务的稳定性正来自显式计划加逐项自验。来源：Cognition 官方技术报告

Manus：todo.md 的计划外显。 官方工程博客（2025 年 7 月）披露，Manus 处理复杂任务时会创建 todo.md 文件并随执行逐步勾选、反复重写——这不是"可爱行为"，而是刻意的注意力机制：平均一个任务要经历约 50 次工具调用，模型容易漂移和遗忘目标，持续重写待办清单等于把全局计划复述到上下文末尾、放进模型最近的注意力窗口，缓解"迷失在中间"问题。计划外显让长任务不丢目标，也让用户随时可查可改。来源：Manus 官方博客

OpenAI：Operator 的计划执行与确认闸。 2025 年 1 月发布的 Operator 是由 CUA 模型（GPT-4o 视觉 + 强化学习训练）驱动的计算机使用智能体：感知截图、推理规划、执行点击/滚动/输入循环工作，遇到困难时自我修正、卡住时交还控制权；官方安全设计明确"在完成任何重要动作（提交订单、发送邮件）前应请求用户确认"——计划逐步执行加人工确认闸，正是本章所说"计划是人与智能体对齐界面"的产品化。来源：OpenAI 官方公告

6.5 深度讲解

四十年跨度的对照是理解本章的底色：符号规划解决"从形式化世界模型推出正确动作序列"，假设世界可知、动作可精确描述，因而在封闭领域成功、在开放世界失灵；LLM 规划反过来——世界模型内化在参数里，可以处理模糊目标与开放环境，但换来了正确性无法保证。今天工程上的"规划模式"，实质是用 LLM 的语义能力做分解与调度，用经典规划时代的形式纪律（状态、依赖、验证、坚持性）约束它的散漫。SHOP2 等 HTN 实用系统的分解方法库思想，则活在每一个"任务分解提示模板"里。

6.5.1 计划—执行分离 vs 交织：一个光谱而非二选一

把"何时产生计划"画成一条光谱，四个锚点各有其位。光谱左端是纯交织（ReAct 式）：没有显式计划，每步基于全部历史即时决策。优点是适应性最强——每步吸收最新观察；缺点是全局一致性弱，且每步都要重新推理全部上下文，长任务又贵又漂。第二个锚点是一次性分离（plan-and-execute，HuggingGPT、Plan-and-Solve）：开始时生成完整计划，然后逐项执行。优点是全局结构清晰、进度可报、token 经济；缺点是计划期的假设得不到执行期验证，一处假设失效就可能让整份计划作废——环境越开放，这个缺陷越致命。第三个锚点是分离但带占位符（ReWOO）：计划一次性生成，但计划里引用的中间结果写成变量（#E1、#E2），执行时才填充。这解决了分离式的一个深层矛盾：好的计划需要预知执行结果，而结果在计划时并不存在——占位符让计划可以引用未来。代价数据支持这个设计：ReWOO 论文报告相对 ReAct 式交织范式约 5 倍的 token 效率，并在 HotpotQA 多跳基准上取得约 4% 的准确率提升（arXiv:2305.18323）——省 token 与提精度同时成立，因为计划器不被工具原始输出打断，推理上下文保持干净；同一篇论文还演示了把推理从 175B 级模型卸载到 7B 小模型的可行性。第四个锚点是按需递归（ADaPT）：先给粗计划，执行器能做就做；某项失败，才对该项递归分解。ADaPT 的实验显示这种"惰性分解"在 ALFWorld、WebShop 等环境比 ReAct 与固定 plan-and-execute 的成功率高十几个到三十个百分点，具体数字（GPT-3.5 后端）：ALFWorld 71.6% 对 ReAct 43.3%，WebShop 44.0% 对 ReAct 32.0%、对固定 plan-and-execute 17.0%，自建 TextCraft 52.0% 对 ReAct 19.0%；摘要口径为三个环境相对强基线最多提升 28.3、27、33 个百分点（arXiv:2311.05772）。它的洞察是：分解粒度应该由执行器实际能力决定，而能力只有试了才知道——论文的深度分析还显示，最大分解深度为 1 时成绩与 ReAct 基线几乎重合，深度 1→2→3 逐级爬升："要不要细分解"本身就该交给执行结果去回答。工程上的选择经验：环境稳定、步骤清晰的任务用分离式；环境多变、探索性强的任务用交织式或按需递归；大多数生产系统取中——顶层计划分离、底层执行交织，即"计划管方向，ReAct 管脚下"。

6.5.2 计划粒度：细到哪一步算合适

大家默认"计划越细，执行越稳"，工程事实恰恰相反：细计划是把不确定性提前固化。计划在执行前生成，而最有价值的信息（哪个文件真的要改、哪个接口真的可用）只会在执行期出现——细到工具调用级的计划等于宣布"执行期的信息一概不用"，环境一变全线报废。粒度是规划里最考验手感的参数，两头都是坑。太细（细到每条工具调用）等于把执行也计划完了：计划生成的 token 成本暴涨，对执行期信息的利用率为零——执行器变成照本宣科的傀儡，环境一变计划全线报废。太粗（"第一步：研究；第二步：写作"）等于没计划：执行器面对的仍是原始复杂度，规划的全部收益（可观测、可定位、可重试）消失，执行期的漂移无人纠偏。合适的粒度有一条可操作判据：每条计划项应是执行器一次可验证的能力单元——一个 LLM 调用或一小组工具调用能完成，且有明确的是非判据；比这更细就是浪费，比这更粗就是漂移隐患。粒度还应随执行器能力浮动：执行器更强，粒度可放粗（ADaPT 的动态适应本质就是自动寻找匹配点）；计划项之间保留顺序依赖而非全序（哪些必须串行、哪些可并行要显式区分），过强的全序约束会杀掉并行机会，也让局部重排变难。

6.5.3 重规划触发条件与修订纪律

重规划比不规划更危险的地方在于：它可能把好的部分也推翻。因此触发条件必须显式、可判定，修订必须带纪律。四个标准触发器。其一是子任务反复失败：同一计划项重试超过阈值（通常 2 次），说明不是运气问题而是计划问题——该分解、换路或放弃。其二是假设被证伪：计划建立在对环境的假设上（如"API 支持批量查询"），执行观察与假设冲突时应立即触发，而不是硬推到失败为止。其三是外部变化：长程任务中环境更新、用户改需求。其四是预算越界：步数或成本过半而进度不足一半，说明工作量估计错了。修订纪律有三条。带证据重规划：新计划的输入必须包含已完成项及结果、失败项及原因——白板重规划等于抹掉状态、重复烧钱。意图坚持性：源自 BDI 的原则——局部失败默认局部修订（分解或绕过该项），全盘推翻需过明确的理由门槛，否则智能体会陷入"计划抖动"，每遇挫折就重来，永远走不远。修订留痕：每次重规划记录版本与理由，这是事后审计"为什么走到这一步"的唯一依据。

6.5.4 计划验证：执行前与执行中

计划在执行前就该过一遍验证，性价比极高。结构验证是第一层：计划非空、描述非空、无循环依赖、引用的工具/资源存在于注册表——这些检查不需要 LLM，几行代码即可。可行性评审是第二层：让模型（或人）以评审视角检查——每项可执行吗？依赖顺序对吗？有无遗漏步骤与明显冗余？Tree of Thoughts 的思路在此适用：对关键计划做多候选生成加评估，取最优而非首生成。执行中验证是第三层：每完成一项，用产出对照该项的完成判据；观察与预期不符（哪怕这项"成功"了）也记为计划风险信号。第四层防"计划—执行漂移"：长任务中执行器可能悄悄偏离计划自作主张，状态跟踪必须以计划为锚——执行结果回填到对应计划项，对不上号的就是漂移警报。

6.5.5 失效模式与何时不要规划

三个典型失效。计划幻觉：计划引用不存在的工具、不存在的数据源，或包含逻辑上不可达的步骤——结构验证能拦下大半。过度坚持：计划已明显失效仍硬推到底，这是 BDI 坚持性矫枉过正的镜像，解法是把 6.5.3 的触发器写成硬性检查而非模型自觉。计划抖动：与过度坚持相反，遇挫即全盘重规划，在"重来"与"硬推"之间震荡——解法是意图坚持性加修订门槛。何时不要规划也要说清：单步任务规划是纯开销；强探索性任务（"看看这个代码库哪里有问题"）探索本身就是任务，预设计划反而限制视野；环境变化快于计划周期的任务，计划在生成时就过期了，交织式决策更诚实。规划的正确姿态是把它当可选项：判断"这个任务要不要显式计划"，本身就是智能体路由的第一步。

6.5.6 怎么用：运用判断

适用信号：①任务天然分多步且有依赖——后一步的输入依赖前一步的产出；②需要向用户或运维报告进度、失败要能定位到"第几步"；③错误代价高、走错方向回滚昂贵；④环境相对稳定，计划周期短于环境变化周期。四条命中两条以上，就值得显式规划。

与最近替代方案的对比：

方案 与显式规划的关键差异
ReAct 纯交织 每步即时决策、无全局计划：适应快但易漂移，每步重读全部历史，长任务贵且不可观测
提示链（第 1 章） 固定顺序的单向分解：无状态跟踪与重规划，适合结构已知且固定的流水线
Tree of Thoughts 把规划做成树搜索：关键决策多候选、评估、回溯，效果更好但成本数倍，留给高风险计划

落地三步：①给计划定一个最小 JSON schema（description + 依赖 + 完成判据），先写结构验证器（非空、条目上限、依赖无环、引用工具与注册表对账）——几十行代码拦下大半计划幻觉；②顶层计划分离、底层执行交织：每条计划项交给一个带工具的小执行循环，完成判据不过就计失败，不做无谓预分解（ADaPT 原则）；③把四个重规划触发器与"带证据、局部优先、版本留痕"纪律写进代码，并在执行前把计划展示给人确认——这是全章性价比最高的一步。

6.6 工程落地：核心源码与讲解

6.6.1 框架无关实现（片段 + 讲解）

主程序按原文件顺序拆成四个片段：状态定义、计划生成与结构验证、执行与局部重规划、主状态机。四片按序拼接即完整可运行程序，依赖与环境变量见片 1 文档串。

"""规划模式：plan -> execute -> replan 状态机（四片按序拼接即完整可运行程序）。

依赖：pip install openai；环境变量 AGENT_LLM_BASE_URL / AGENT_LLM_API_KEY / AGENT_LLM_MODEL。
"""
import json
import os
from dataclasses import dataclass, field

from openai import OpenAI

client = OpenAI(base_url=os.environ.get("AGENT_LLM_BASE_URL", "https://api.openai.com/v1"),
                api_key=os.environ["AGENT_LLM_API_KEY"])
MODEL = os.environ.get("AGENT_LLM_MODEL", "gpt-4o-mini")


def llm(prompt: str, system: str = "", temperature: float = 0.3) -> str:
    """调用一次大模型，返回文本回复。"""
    msgs = ([{"role": "system", "content": system}] if system else []) + [{"role": "user", "content": prompt}]
    resp = client.chat.completions.create(model=MODEL, messages=msgs, temperature=temperature)
    return resp.choices[0].message.content or ""


@dataclass
class Step:
    """计划项：一条子任务及其执行状态。"""
    description: str
    status: str = "pending"  # pending / done / failed
    attempts: int = 0
    result: str = ""


@dataclass
class PlanState:
    """整个任务的状态机状态。"""
    goal: str
    steps: list[Step] = field(default_factory=list)
    replans: int = 0
    outcome: str = "running"  # running / success / failed

▸ 代码怎么读：两个 dataclass 就是"计划显式化"的落点——Step 的 status 与 attempts 让每次失败都有账可查（重试额度、失败原因），PlanState.replans 给重规划次数硬上限提供了计数位置。状态保持最小：pending / done / failed 三态够用，状态越多越难对账；6.5.4 说的"以计划为锚"就体现在执行结果只回填到对应 Step 的 result 字段，对不上号即是漂移。

PLAN_SYSTEM = ("你是任务规划器。把目标分解为子任务清单：每条是一个执行器一次可完成的"
               "能力单元；只分解、不执行；按执行顺序排列。")


def make_plan(goal: str, context: str = "") -> list[Step]:
    """生成计划。结构验证（非空 / 条目上限 / 描述非空）失败时带错误重试一次。"""
    prompt = (f"【目标】{goal}\n" + (f"【已知进展与教训】\n{context}\n" if context else "")
              + '只输出 JSON 数组：[{"description": "子任务描述"}, ...]，3 到 6 条。')
    last_err = ""
    for _ in range(2):  # 错误路径：解析/验证失败，把原因喂回下一轮重试
        raw = llm(prompt, system=PLAN_SYSTEM + (f"\n上轮问题：{last_err}" if last_err else ""))
        try:
            text = raw.strip()
            if text.startswith(chr(96) * 3):  # 围栏用 chr 构造，防裸反引号截断文档
                text = text.strip(chr(96)).lstrip("json")
            steps = [Step(description=str(item["description"])) for item in json.loads(text)]
            if not steps or len(steps) > 8:
                raise ValueError(f"计划为空或条目过多（{len(steps)}），请给 3 到 6 条")
            if any(not s.description.strip() for s in steps):
                raise ValueError("存在空描述的计划项")
            return steps
        except (json.JSONDecodeError, KeyError, TypeError, ValueError) as exc:
            last_err = f"{type(exc).__name__}: {exc}，请严格按 JSON 数组格式输出"
    raise RuntimeError(f"计划生成失败：{last_err}")

▸ 代码怎么读：make_plan 演示"计划本身也要验证"——结构验证（非空、条目上限、无空描述）不依赖 LLM，几行代码即成，对应 6.5.4 的第一层计划验证；验证失败把具体错误喂回下一轮提示重试一次，两次都失败抛异常交调用方降级。提示里"3 到 6 条"与代码里 8 条上限，是把 6.5.2 的粒度判据（每条是执行器一次可完成的能力单元）压进协议的粗粒度近似——粒度太细的清单在这里被直接打回。context 参数是重规划的接口：新计划的输入必须带已完成结果与失败原因，函数签名层面就禁掉了白板重规划。

def execute_step(step: Step, state: PlanState) -> None:
    """执行单个计划项。成功标准可判定：无法完成必须显式输出 [UNRESOLVED]。"""
    done = "\n".join(f"- {s.description} -> {s.result}" for s in state.steps if s.status == "done")
    reply = llm(f"完成子任务：{step.description}\n【总体目标】{state.goal}\n"
                f"【已完成子任务及结果】\n{done or '（无）'}\n"
                "无法完成时输出必须以 [UNRESOLVED]: 开头并说明原因；否则直接给出成果。")
    step.attempts += 1
    if "[UNRESOLVED]" in reply[:30]:
        step.result = reply.strip()
        print(f"  执行失败(第{step.attempts}次)：{reply[:60]}")
    else:
        step.status, step.result = "done", reply.strip()
        print(f"  完成：{step.description[:40]} -> {step.result[:50]}")


def replan(state: PlanState) -> None:
    """局部重规划：只重排未完成部分，已完成结果与失败原因全部携带。"""
    failed = "\n".join(f"-「{s.description}」失败原因：{s.result}"
                       for s in state.steps if s.status == "failed")
    done = "\n".join(f"- {s.description} -> {s.result}" for s in state.steps if s.status == "done")
    context = (f"以下子任务已完成，新计划必须复用其结果、不得重复：\n{done}\n"
               f"以下子任务多次失败，新计划应换路线、拆细或绕过：\n{failed}")
    state.steps = [s for s in state.steps if s.status == "done"] + make_plan(goal=state.goal, context=context)
    print(f"[重规划 #{state.replans}] 新计划：",
          "；".join(s.description[:30] for s in state.steps if s.status == "pending"))

▸ 代码怎么读：execute_step 的关键设计是"成功标准可判定"——执行器无法完成时必须显式输出 [UNRESOLVED]，不许含糊其辞；含糊的"已完成"正是计划—执行漂移的源头（6.5.4 第四层防的就是它）。提示里带上总体目标与已完成结果，执行器不必独自背负全局，也避免重复造轮子。replan 的纪律写在数据流里：done 项原样保留、只把失败项连同原因交给规划器重排——对应 6.5.3 修订纪律的"带证据、局部优先"两条；全盘推翻在这里根本没有入口。

def run(goal: str, max_attempts: int = 2, max_replans: int = 2) -> PlanState:
    """plan -> execute -> replan 主状态机：单项连续失败 max_attempts 次 -> 局部重规划；
    重规划次数耗尽即如实报失败（硬闸）。
    """
    state = PlanState(goal=goal)
    state.steps = make_plan(goal)
    print("[初始计划]", "；".join(f"{i}.{s.description[:30]}" for i, s in enumerate(state.steps, 1)))
    while state.outcome == "running":
        pending = [s for s in state.steps if s.status == "pending"]
        if not pending:
            state.outcome = "success"
            break
        step = pending[0]
        execute_step(step, state)
        if step.status != "done" and step.attempts >= max_attempts:
            step.status = "failed"  # 重试额度用尽：判定为计划问题而非运气
            state.replans += 1
            if state.replans > max_replans:
                state.outcome = "failed"  # 硬闸：重规划耗尽，如实报告
                break
            replan(state)
        if all(s.status == "done" for s in state.steps):
            state.outcome = "success"
    return state


if __name__ == "__main__":
    result = run(goal=("为'团队周报自动化'写一份实施方案：数据从哪来、汇总什么指标、"
                       "如何自动分发给五个部门。要求分点、可直接执行。"))
    print("结局：", result.outcome, "| 重规划次数：", result.replans)
    for s in result.steps:
        print(f"[{s.status}] {s.description[:40]}")

▸ 代码怎么读：主状态机把三个决策参数集中在一处：max_attempts=2（单项重试上限，超过即从"运气问题"升级为"计划问题"，触发重规划）与 max_replans=2（重规划硬上限，防 6.5.5 说的计划抖动）。循环体就是 6.1.2 的四个部件：取首项执行、失败计数、命中触发器做局部重规划、全部完成即成功。重规划耗尽时如实返回 failed 与已完成状态，把部分成果交还调用方——好过一个假装成功。接真实执行器时把 execute_step 里的 llm 换成你的工具调用循环即可，状态机不动。

6.6.2 框架差异速览（CrewAI）

CrewAI 的 hierarchical 模式是"计划—分派—验收"分离的最短实现（按 crewai 0.x 2024–2025 系列公开 API；版本迭代快，参数名以所装版本官方文档为准）：

CrewAI 构件 在规划模式中的角色 一句话差异
Process.hierarchical "计划—分派—验收"分离 计划由 manager 运行时动态生成，非预先 JSON 清单
manager_llm 规划器：分解、派工、验收 粒度与结构验证不可控，需外层自行补校验
Task(expected_output=...) 计划项的完成判据 验收标准声明式交给框架，逐任务判定
Crew.kickoff(inputs=...) 执行整个计划 无内置重规划硬闸，重试与门槛需在调用侧包装

6.6.3 生产化改造清单

  • 错误处理：计划 JSON 解析失败带错误重试一次，再失败降级为单步执行并标注"无计划模式"；执行异常计为该项失败而非中断任务。
  • 超时：计划生成设独立超时（计划是关键路径）；每个计划项执行设超时并计入失败重试。
  • 并发：依赖关系解析后，无依赖计划项并发执行；写操作项保持串行与业务顺序。
  • 缓存：计划按（目标、上下文哈希）缓存；已完成计划项结果持久化，重跑任务从断点续做而非从头再来。
  • 可观测：记录计划版本、每项状态流转、重规划触发原因；"重规划次数高"与"单项反复失败"是首要告警。
  • 成本控制：计划用强模型、执行按项难度选模型；设任务级步数与 token 预算，预算过半进度不足时主动触发重评估。
  • 计划验证：结构验证代码化（非空、条目上限、依赖无环）；引用的工具/资源与注册表对账；执行前一次模型可行性评审。
  • 重规划治理：修订必须携带已完成状态与失败原因；全盘重规划设更高门槛与审批；版本留痕可审计。
  • 人工介入点：计划执行前展示给用户确认（对齐性价比最高的一步）；写操作项与高风险项设审批闸。
  • 评测：建任务分解评测集（可执行性、粒度、依赖正确性、完成率），换模型或改提示后回归。

6.7 概览 / 核心要点 / 结论

6.7.1 本章小结

规划模式把长程任务从"赌模型隐式状态的稳定性"改写为"管理一份显式的工作分解结构"：计划生成、状态跟踪、重规划触发、计划验证四个部件各司其职。计划—执行的分离程度是一条光谱——从 ReAct 的纯交织，到一次性分离（HuggingGPT、Plan-and-Solve）、占位符分离（ReWOO），再到按需递归（ADaPT）——选择依据是环境的稳定性与执行器的能力，工程上最常见的答案是"计划管方向、ReAct 管脚下"。四十年经典规划留下的形式纪律（STRIPS 的状态形式化、HTN 的分解方法库、BDI 的意图坚持性）在 LLM 时代不是古董，而是治住计划幻觉、过度坚持与计划抖动的药方。

6.7.2 核心要点

  • 显式计划的三重收益：跨步骤全局一致、进度可观测可定位、失败可局部重试而非从头再来。
  • 计划—执行分离是光谱不是二选一：环境稳定用分离式，环境多变用交织或按需递归，生产常见形态是顶层分离、底层交织。
  • 计划粒度的判据：每条计划项是执行器一次可验证的能力单元；粒度随执行器能力浮动（ADaPT 的核心洞察）。
  • ReWOO 的占位符解决了分离式的深层矛盾：计划可以引用尚未产生的执行结果，一次生成、不必预知。
  • 重规划四触发器：子任务反复失败、假设被证伪、环境变化、预算越界；修订纪律是带证据、局部优先、版本留痕；意图坚持性（BDI 遗产）要求局部失败默认局部修订，全盘推翻需过门槛。
  • 计划验证四层：结构验证（代码化）、可行性评审、执行中对判据、防计划—执行漂移。
  • 三种失效要有对策：计划幻觉靠结构验证，过度坚持靠硬性触发器，计划抖动靠修订门槛。
  • 单步任务、强探索任务、环境快变任务不要规划；"是否需要计划"本身就是路由的第一步。

6.7.3 结论

规划的价值不在"有一份计划"这个形式，而在它把长程任务的失败模式从不可诊断的"整体跑偏"变成可管理的"第 N 项需要处理"。LLM 让生成一份像样的计划变得便宜，但计划的好坏——粒度是否匹配执行器、依赖是否真实、假设是否站得住——仍然取决于工程纪律。实践者的功课是记住两个决策、一条纪律：分离与交织怎么选看环境，粒度粗细怎么看执行器，重规划必须带着证据与门槛。做到这三点，规划就从一篇"看起来周密的文字"变成智能体系统里最硬的那根骨架。
